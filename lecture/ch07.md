### 학습 목표

- 스트리밍을 보완하는 배치 워크플로의 역할(확정 통계·보고 자동화)을 설명하고 설계한다

- 태스크 분할 경계·배치 주기·실행 시각·재시도 정책을 요구사항에서 도출하고, 각 값의 근거와 그 설계가 깨지는 조건을 적는다

### 1. 배치 처리가 필요한 공공 업무 (11분)

#### 1-1. 스트리밍이 있는데 배치가 필요한 이유

○ **상황판(스트리밍)과 월간 보고서(배치)는 다른 산출물이다**
  - 상황판 수치: 빠르되 미확정 — 6장 update 모드에서 지연 이벤트가 오면 건수가 3→4로 바뀜
  - 보고서 수치: 늦어도 되지만 바뀌면 안 됨 — 제출한 통계가 소급으로 흔들리면 보고를 신뢰할 수 없게 됨

○ **6장 실측이 보여주는 차이**
  - watermark 10분 설정에서 21:49 발생 이벤트(LATE_DROP)가 폐기됨 → 스트리밍 집계에 영원히 빠짐
  - 배치는 마감 후(예: 다음 날 새벽) 그날 도착분 전체를 다시 읽으므로 지연분까지 포함해 재집계 가능
  - 3장에서 설계한 하이브리드(스트리밍+배치 병행)의 실체가 이 역할 분담

○ **마감(cutoff) 방식의 차이**
  - 스트리밍(6장): 데이터가 마감을 정함 — 관측된 최대 이벤트 시각에서 지연 허용을 뺀 만큼 기다림(watermark)
  - 배치(7장): 달력이 마감을 정함 — "7/1 데이터는 7/2 새벽에 마감하고 계산"
  - 달력 마감은 느리지만 예측 가능하고, 마감까지 도착한 모든 지연분을 포함
  - 두 시스템은 대체재가 아니라 보완재

#### 1-2. 핵심 개념

○ **확정성(finality)**
  - 배치는 데이터 구간의 마감을 기다린 뒤 전체를 계산 → 산출물이 "그 시점 입력의 최종 결과"
  - 스트리밍 근사치를 배치가 사후 검증하는 구조 → 정기 대조 감시 지표가 됨

○ **재실행 가능(re-runnable)**
  - 실패하면 그 날짜를 다시 돌림 — 단, 결과가 이중으로 쌓이면 안 됨
  - 5장의 멱등성이 배치의 전제 조건으로 되돌아옴(7.4에서 실측)

○ **전체 조망**
  - 그날 데이터 전부를 한 번에 보므로 전체 정렬·중복 전수 검사·원천 대사가 자연스러움

○ **지연·처리량의 절충**
  - 배치 지연은 실행 주기만큼 큼(일 배치면 최대 하루)
  - 그 대가로 큰 데이터를 효율적으로 처리하고 산출물을 확정

**표 7.1** 스트리밍과 배치의 역할 분담(6장·7장 실습 기준)

| 항목 | 스트리밍(6장) | 배치(7장) |
|---|---|---|
| 목적 | 상황 감시·조기 경보 | 확정 통계·보고서·정산 |
| 수치의 지위 | 근사치(지연분 수용 중, 갱신됨) | 확정치(마감 후 전체 계산) |
| 지연 데이터 | watermark 안만 수용, 밖은 폐기 | 마감 시점까지 도착분 전부 포함 |
| 실패 시 | 체크포인트(checkpoint)에서 재개 | 해당 날짜 재실행(멱등 전제) |
| 산출물 | 갱신되는 집계 스트림 | 불변 보고서 파일 |

#### 1-3. 주기와 실행 시각은 무엇에서 정하는가

○ **주기 = 신선도 요구(수요) ↔ 비용(공급)의 절충**
  - 신선도는 산출물을 쓰는 사람이 정함 — 매일 아침 회의에서 전날 통계를 쓰면 일 배치, 월보만 만들면 일 배치는 30번 돌려 1번 쓰는 셈
  - 비용은 자원만이 아님 — 주기를 절반으로 줄이면 실행 횟수와 함께 실패·재실행·알림도 두 배
  - 주기는 산출물의 이름·파티션·재실행 단위를 함께 정하므로 나중에 바꾸기 어려움

○ **실행 시각 = 원천 확정 시점에서 역산**
  - 7/1치를 7/2 00시에 돌리면 자정 직전 접수분이 아직 적재 전 → 누락
  - 야간 적재가 새벽 1시에 끝나면 배치 시작은 그 뒤, 아침 8시 회의에 쓰려면 실행 시간 + 복구 여유가 그 사이에 들어가야 함
  - 고르는 구간: `[원천 확정 시각, 산출물 필요 시각 − 실행 시간 − 복구 여유]`
  - 구간이 비면 시각이 아니라 **주기나 마감 규약**을 다시 정함

#### 1-4. 민간 마감 배치 → 공공 확정 보고

○ **민간의 마감 배치(day-close batch)** 세 가지
  - 매출·정산 마감: 그날 팔린 것과 환불된 것을 대사해 최종 매출 확정
  - 광고 리포트 일 배치: 어제의 노출·클릭·비용을 확정 리포트로 발송
  - DW(데이터 웨어하우스) 야간 적재(nightly load): 여러 운영 DB 데이터를 새벽에 한 번에 모아 분석용 표를 다시 만듦

○ **공통점**: 실시간 대시보드가 대략의 수치를 이미 보여줘도, 밤에 한 번 더 전량을 확정

○ **공공에서 마감 정정 비용이 더 큰 이유**
  - 민간: 틀리면 다음 분기 실적에 반영해 정정
  - 공공: 확정치가 감사·국회 보고·정보공개청구 대상 → 한번 확정한 수치를 바꾸는 일 자체가 사건
  - 누가·언제·어떤 데이터로 수치를 만들었고 왜 최종인지 설명할 수 있어야 함
  - 재현성·원천 보존·마감 규약의 명시를 더 강하게 요구

**표 7.1a** 민간 마감 배치의 공공 적용

| 민간 현장 방법 | 확정 대상 | 공공 대응물 | 공공 특수성 |
|---|---|---|---|
| 매출·정산 마감(day close) | 최종 매출·정산액 | 회계 결산, 세입·세출 마감 | 감사·결산 검사 대상 — 정정 시 개정 이력·사유 필요 |
| 광고 리포트 일 배치 | 어제의 확정 성과 | 민원 일일 마감 보고 | 배포 후 수치 변동이 불신 요인(7.4 재현성) |
| DW 야간 적재(nightly load) | 분석용 확정 데이터셋 | 통계 월보·연보, 정책 기초통계 | 표준 코드로 기관 간 통합(7.2) |

#### 1-5. 공공 사례

○ 지자체 민원 상황실: 6장 스트리밍으로 "최근 10분 지역별 신고" 파악
○ 기획 부서: 7장 배치로 "어제의 확정 일별 통계"와 "주간 보고서" 수령
○ 감사 관점: 두 수치가 다를 수 있고, 달라도 되는 이유가 문서화되어 있으면 결함이 아니라 설계

### 2. 데이터 정제와 표준 코드 매핑 (11분)

#### 2-1. 표기 변형 문제

○ **사람 눈에는 같지만 groupby에는 다르다**
  - 7/1 파일에 강남구 민원이 세 표기: `"강남구"`, `" 강남구 "`(공백), `"강남"`(약칭)
  - 정제 없이 지역별 건수를 세면 강남구 8건이 세 줄로 쪼개짐 → 보고서 수치가 전부 틀려짐

○ **표준 코드의 필요성**
  - 지역"명"은 기관·시스템·담당자마다 표기가 흔들리는 자연어
  - 행정표준코드(법정동코드, code.go.kr 관리): 서울 강남구 = `11680`, 마포구 = `11440`, 관악구 = `11620`
  - 코드를 집계·결합의 키로 쓰면 다른 기관 데이터(인구·예산·시설)와도 같은 키로 결합 가능
  - "이름이 아니라 코드로 붙인다"는 원칙 = 표기 문제의 근본 해결 + 기관 간 상호운용의 전제

○ **(민간) 같은 문제, 다른 표준의 출처**
  - 채널마다 다른 이름·ID로 들어온 상품 → 표준 SKU(Stock Keeping Unit, 재고 관리 단위)로 통일
  - 표준값을 만들고 유지하는 시스템 = MDM(Master Data Management, 마스터 데이터 관리)
  - 공공은 국가가 관리하는 코드를 받아 씀 / 민간은 자기 마스터를 스스로 만듦
  - 그래서 질문이 갈림 — 공공: "왜 표준 코드를 안 썼는가" / 민간: "마스터가 최신인가"

#### 2-2. 정제의 네 갈래 출구

○ **절대 버리지 않기** — 매핑 실패 레코드를 조용히 건너뛰는 코드가 가장 위험
  - 4장 시나리오 B의 유실, 6장 watermark 폐기처럼 — 정제 drop도 스스로 알리지 않음
  - 보고서 총계가 원천보다 조금 작은데 아무도 모르는 상태 = 감사에서 가장 곤란한 결함

○ **네 갈래**
  1. **매핑 성공**: 표준 코드가 붙어 집계에 들어감
  2. **지역 미기재(missing)**: 지역 필드가 비어 있음 → 건수와 민원 ID를 분리 기록
  3. **매핑 실패(unmapped)**: 표준 코드 사전에 없는 표기(예: `판교`) → 원문 그대로 분리 기록
  4. **중복 제거(dup)**: 같은 민원 ID의 재전송은 먼저 온 것만 남김(5장 원칙)

○ **총계 보존식으로 검증**
  - `입력 = 매핑 + 미기재 + 미매핑 + 중복제거`
  - 7/1 실측: `20 = 18 + 1 + 1 + 0`
  - 이 등식이 성립하지 않으면 레코드가 조용히 사라진 것 → 품질 게이트가 배치 자체를 실패시킴(7.3)

○ **각 항이 그대로 운영 지표 — 매핑률 = 매핑 ÷ 입력**
  - 떨어지면 사전에 없는 표기가 늘었다는 뜻 — 관할이 넓어졌거나 접수 화면이 바뀌었거나
  - (민간) 상품 카탈로그 매핑률 하락 = 신상품 미등록 / 캠페인 ID 매핑률 하락 = 신규 캠페인 누락
  - 비율만으로는 원인을 모름 → 떨어진 날의 미매핑 원문 목록(`excluded.json`)을 함께 봄

#### 2-3. 워크드 예제: 7/1 20건의 정제(실측)

**표 7.2** 정제 규칙표(7/1 실측)

| 순서 | 규칙 | 예시 | 적용 실측 |
|---|---|---|---|
| 1 | 중복 접수 제거(같은 민원 ID는 첫 건만) | — (7/1에는 없음) | 0건 |
| 2 | 앞뒤 공백 제거 | `" 강남구 "` → `강남구` | 1건 |
| 3 | 약칭 보정(별칭 사전) | `강남` → `강남구` | 4건 |
| 4 | 표준 코드 매핑 | `강남구` → `11680` | 18건 성공 |
| 5 | 지역 미기재 분리 | 지역 필드 없음 | 1건 |
| 6 | 매핑 실패 분리(원문 보존) | `판교` — 서울 사전에 없음 | 1건 |

○ 검산: 18건 매핑(강남구 8 + 마포구 5 + 관악구 5) + 미기재 1 + 미매핑 1 + 중복 0 = 입력 20건
○ 사흘 전체: 매핑 54, 미기재 2, 미매핑 3(판교·성남시·김포), 중복 제거 1 → 원천 60건 남김없이 설명

○ **미매핑 처리 원칙**
  - `판교`, `성남시`, `김포`는 오타가 아니라 서울 자치구 사전에 없는 유효 지명일 수 있음
  - 자동으로 "가장 비슷한 자치구"에 매핑하면 데이터 조작
  - 원문 그대로 분리 보고 → 사람이 사전 보강인지 접수 오류인지 판단

#### 2-4. 핵심 코드(3줄)

elif not name:      missing.append(cid)         # 미기재 — 분리 기록

#### 2-5. 현장 방법: 총계 보존식과 데이터 품질 프레임워크

○ **Great Expectations**: 기대(expectation)를 규칙 목록으로 선언 → 데이터가 통과했는지 리포트
○ **dbt 데이터 테스트**: 변환 결과 표에 유일성·비결측·참조 무결성 검증을 테스트로 선언
○ 두 도구 모두 방법론 차용 — 이 실습의 총계 보존식은 프레임워크 없이 손으로 구현한 최소판
○ 요점: 정제 성공을 "에러가 안 났다"가 아니라 "선언한 기대를 데이터가 만족했다"로 판정하고 기록
○ **목적의 무게가 다름** — 민간: 틀린 데이터가 하류로 흐르지 못하게 멈추는 것이 일차 목적 / 공공: 거기에 "몇 건이 왜 빠졌는가"의 보고가 더 붙음

### 3. Airflow DAG의 태스크와 의존성 (16분)

#### 3-1. 왜 오케스트레이터(orchestrator)가 필요한가

○ 정제와 집계를 하나의 스크립트로 이어 붙이면 운영에서 곧 질문이 옴
  - 어제 새벽 배치가 집계 단계에서 죽었는데 어디서부터 다시 돌리나?
  - 정제가 실패했는데 보고서 단계가 낡은 파일로 돌지 않았나?
  - 매일 새벽 2시에 누가 실행하나?

○ **워크플로 오케스트레이터(Airflow)**가 구조로 답함
  - 절차를 **태스크**(무엇을)와 **의존성**(어떤 순서로)의 그래프로 선언
  - 엔진이 순서 보장·실패 전파·재시도·스케줄을 맡음
  - 6장의 "질의만 선언하면 증분 계산은 엔진이 맡는다"와 같은 구도 — 선언과 실행의 분리

○ **DAG(Directed Acyclic Graph, 방향 비순환 그래프)**
  - 방향: "정제가 끝나야 집계한다"는 순서
  - 비순환: "A가 B를 기다리고 B가 A를 기다리는" 교착이 없다는 보장

#### 3-2. 실습 DAG 구조

```
                         ┌─> aggregate_daily ─┐
validate_input ─> clean_and_map               ├─> write_report
                         └─> check_quality ───┘

daily_complaint_report (@daily): 검증 → 정제·매핑 → (집계 ∥ 품질 게이트) → 보고서
weekly_complaint_rollup (@weekly): rollup_weekly (일별 산출물 합산)
```

○ 갈림에 주목: 집계(aggregate_daily)와 품질 점검(check_quality)은 둘 다 정제 결과만 필요하고 서로를 필요로 하지 않음 → 의존성 미선언
○ 보고서(write_report)는 둘 다 필요 → 두 갈래가 다시 합쳐짐

```python
t_validate >> t_clean >> [t_aggregate, t_quality] >> t_report
```

#### 3-3. 태스크를 몇 개로 쪼갤 것인가

○ 같은 일을 태스크 1개로도, 10개로도 쓸 수 있음 — 경계를 정하는 근거는 둘

○ **재실행 단위** — 태스크 = 실패 시 다시 돌리는 최소 단위
  - 정제와 집계를 묶으면 집계에서 죽어도 정제부터 다시 돎(정제가 10분이면 매번 10분을 다시 냄)
  - 한 줄 연산까지 쪼개면 태스크 기동 부담(프로세스·상태 기록)이 실제 계산보다 커짐
  - 경계는 "여기서 죽으면 앞을 다시 하고 싶지 않다"는 지점

○ **실패 격리** — 서로 다른 이유로 실패하는 일은 다른 태스크로
  - 입력 검증은 파일이 없어서, 품질 점검은 데이터가 규칙을 어겨서 실패
  - 묶으면 실패 상태만으로 원인 구분 불가 → 표 7.4의 2단계(원인 분류)가 로그 뒤지기가 됨
  - `check_quality`를 집계에서 떼어 낸 이유

○ **반대로 묶어야 하는 경우** — 중간 산출물을 남길 이유가 없고 항상 함께 실패하는 단계
  - `clean_and_map`이 공백 보정·약칭 보정·코드 매핑을 한 태스크에 담은 이유

#### 3-4. logical date: "언제 돌았나"가 아니라 "어느 날짜의 데이터인가"

○ DAG 실행(run)에 붙는 이름표 — 이 실행이 처리하는 데이터 구간의 날짜
  - 7/1 데이터를 처리한 실행: logical date = 2026-07-01, 실제 실행일 = 7/7

○ 2장의 이벤트 시간(발생)과 처리 시간(도착) 구분이 배치로 오면 "데이터의 날짜"와 "실행된 시각"의 구분

○ **두 가지 핵심 능력**
  - 재실행: "7/1 실행을 다시 돌려라"가 명확한 명령 — 어느 입력을 읽고 어느 산출물을 쓸지 이름표가 정함
  - 소급 실행(backfill): 파이프라인을 오늘 만들었어도 지난주 날짜들의 run을 소급 생성해 과거 구간 채움

○ **재실행과 소급 실행은 다른 일**
  - 재실행(rerun): 이미 있는 run을 같은 logical date로 다시 돌림 — **고치는 일**
  - 소급 실행(backfill): 만들어진 적 없는 과거 날짜의 run을 새로 생성 — **없던 것을 만드는 일**
  - 갈리는 지점 셋 — ① 재실행은 덮어쓰기라 기존 산출물이 바뀜(재현성 없으면 진본 분쟁) ② backfill은 수십·수백 run이 한꺼번에 생성돼 원천에 부하가 몰림(동시 실행 수 제한 필요) ③ backfill은 오늘 코드로 과거를 계산 → 규칙이 달라졌으면 값이 원래 보고값과 달라짐 → 개정판 표기

| DAG run의 logical date | 실제 실행일(실측) | 읽은 입력 |
|---|---|---|
| 2026-07-01 | 2026-07-07 | `2026-07-01.jsonl` |
| 2026-07-02 | 2026-07-07 | `2026-07-02.jsonl` |
| 2026-07-03 | 2026-07-07 | `2026-07-03.jsonl` |

#### 3-5. 실패 전파 관찰(실측)

○ **의존성은 지켜지고, 갈림의 순서는 보장되지 않는다**
  - 갈림 두 태스크(집계·품질 점검)의 선후가 실행마다 달라짐 — 오류가 아니라 정상
  - 선언하지 않은 순서는 엔진이 보장하지 않음

○ **실패 전파 — 7/4 실행(입력 파일 없음)**

**표 7.3** 실패 전파 관찰(2026-07-04 실행, 실측)

| 태스크 | 상태 | 의미 |
|---|---|---|
| validate_input | **failed** | 입력 파일 없음 — 예외 발생으로 실패 |
| clean_and_map | **upstream_failed** | 상류 실패로 실행되지 않음 |
| aggregate_daily | **upstream_failed** | 상류 실패로 실행되지 않음 |
| check_quality | **upstream_failed** | 상류 실패로 실행되지 않음 |
| write_report | **upstream_failed** | 상류 실패로 실행되지 않음 |
| (DAG run 전체) | **failed** | 하나의 실패가 run 전체의 실패로 기록 |

○ **두 가지 읽을 것**
  - 하류 4개 태스크는 아예 실행되지 않음(upstream_failed) → 낡은 산출물로 돌아 버리는 사고를 구조적으로 차단
  - 실패가 상태로 기록됨 → 4장의 조용한 유실, 6장의 조용한 폐기와 달리 오케스트레이터의 실패는 시끄러움

○ **품질 게이트**: `check_quality`가 총계 보존식 위반 시 스스로 예외를 던짐 → 보고서 태스크가 upstream_failed로 멈춤 → 틀린 보고서가 아예 만들어지지 않음

○ **게이트 발동률** = 전체 실행 중 품질 게이트로 실패한 비율
  - 오르는 추세 = 원천 데이터 품질 악화 신호
  - 0에 붙어 있는 것도 정보 — 데이터가 깨끗한 것인지, 게이트가 동작하는지 확인된 적이 없는 것인지 모름
  - 규칙을 일부러 어긴 입력을 한 번 넣어 배치가 멈추는지 확인(6.4의 침묵 감시와 같은 문제)

#### 3-6. 재시도 횟수와 간격은 무엇에서 정하는가

○ **횟수는 실패의 성질에서 정함** — 재시도가 의미 있는 실패는 저절로 낫는 실패뿐
  - 낫는 실패: 원천 DB 연결 순간 끊김, 네트워크 타임아웃, 일시적 잠금 충돌
  - 안 낫는 실패: 입력 파일 없음(7/4) — 파일이 오기 전에는 몇 번을 돌려도 같음
  - 일시 장애 여지가 없으면 0이 맞음 → 실패가 곧바로 사람에게 감

○ **간격은 장애 복구 시간에서 정함**
  - 원천이 보통 몇 분 늦으면 5분 간격 2~3회로 흡수 / 30분 늦는 환경에서는 5분 간격 3회로는 못 기다림
  - 총 대기(횟수 × 간격)가 예상 복구 시간을 덮되 산출물 필요 시각을 넘기면 안 됨 — 1-3의 복구 여유가 여기서 쓰임

○ **전제: 재시도는 멱등한 태스크에만 안전**
  - 절반 쓰다 죽은 태스크가 이어 붙이면 재시도가 이중 집계를 만듦
  - 산출물 덮어쓰기(4-2)는 재현성의 조건이자 재시도의 안전 조건

#### 3-7. 스케줄·catchup·실행 방식

○ `schedule="@daily"` + `catchup=False`: 활성화 시점 이전의 미실행 구간을 자동 소급 생성하지 않음
○ 과거 구간이 필요하면 backfill로 명시적으로 채움
○ 실습은 `dag.test()`로 실행 — Airflow 공식 디버깅·테스트 방식, DAG를 단일 프로세스에서 실행

○ **완료 시각(day-close completion time)도 운영 지표**
  - "아침 8시까지 전날 통계 배포"의 측정값 = DAG 마지막 태스크 종료 시각
  - 조금씩 밀리는 추세 = 데이터가 늘고 있다는 신호 → 약속 시각을 넘기기 전에 태스크를 나누거나 자원을 늘림(11장)
  - 오케스트레이터가 Dagster·Prefect여도 지표와 감시 방식은 그대로 — 도구가 아니라 배치 운영이 요구하는 것

### 4. 일별·주별 리포트 자동화 (12분)

#### 4-1. 입력·출력 계약

| 구분 | 계약 | 실습 값 |
|---|---|---|
| 입력 경로 | 날짜별 원천 파일 위치·이름 규약 | `data/input/complaints/{YYYY-MM-DD}.jsonl` |
| 입력 형식 | 필드·타입 | complaint_id, region_raw, category, created_at |
| 출력(일별) | 확정 요약 + 품질 기록 + 보고서 | `daily/{날짜}/daily_summary.json`, `quality_check.json`, `report.md` |
| 출력(주별) | 일별 산출물 롤업(rollup) | `weekly/{창 끝 날짜}/weekly_summary.json`, `weekly_report.md` |
| 실패 규약 | 입력 없음·품질 위반 시 `_SUCCESS` 마커 미생성 | 7.3의 실패 전파·품질 게이트 |

○ 입력 계약 → "수집 시스템이 파일을 어디에 어떤 이름으로 놓아야 하는가"가 두 팀 간 합의
○ 출력 계약 → 후속 시스템(대시보드·기관 보고)이 무엇을 기대해도 되는지 확정
○ 계약 없는 자동화 = 담당자 머릿속 규약 → 인사이동이 있으면 함께 사라짐

#### 4-2. 재현성: 같은 입력, 같은 보고서 — 바이트 단위로

○ 7/1 실행 산출물 해시를 기록 → 같은 날짜 재실행 → 해시 재비교
  - `daily_summary.json` sha256 앞 16자리: `88a34af5412b4723` — 재실행 전후 동일
  - `report.md`: `ba2787da6c5b8a47` — 재실행 전후 동일

○ **재현성을 만드는 세 가지 설계**
  1. 보고서에 생성 시각 같은 비결정 요소를 넣지 않음 — 내용은 입력의 순수 함수
  2. JSON 직렬화의 키 순서를 고정 — 같은 내용이 다른 바이트가 되는 것을 차단
  3. 산출물은 추가(append)가 아니라 덮어쓰기(overwrite) — 재실행이 이중 집계를 만들지 않음(5장 Upsert의 파일판)

○ **재현성은 한 번 확인하고 끝나는 성질이 아님**
  - 정제 규칙·보고서 서식을 고치면 그날부터 같은 입력이 다른 바이트를 냄
  - (민간) 해시 비교를 CI(Continuous Integration, 지속 통합) 테스트로 넣음 — 표본 입력의 산출물 해시를 기준값으로 저장, 코드 변경 시 재계산·비교
  - 값이 달라지면 빌드 실패 → 의도한 변경인지 사고인지 병합 전에 가름
  - 공공에서는 그 판정 기록이 "확정치의 계산 규칙이 바뀐 날짜"의 근거가 됨

#### 4-3. 주별 롤업: 원천을 다시 읽지 않는다

○ **계층화 원칙**: 각 계층은 아래 계층의 확정 산출물만 읽음
  - 일별 산출물 = 품질 게이트 통과한 확정치
  - 주간이 원천을 재정제하면 비용 이중 + 정제 규칙 버전 차이로 일별·주간 어긋남 위험

○ **확정 판별: `_SUCCESS` 마커 규약**
  - 일별 DAG 첫 태스크가 재실행 시 마커 제거 → 마지막 태스크 성공 시에만 재기록
  - 주간 롤업은 마커 있는 날짜만 합산, 없는 날짜는 결측 기록

○ **주간 롤업 실측**
  - 사흘 합산: 60건 = 매핑 54 + 미기재 2 + 미매핑 3 + 중복 제거 1 — 총계 보존 성립
  - 지역별: 강남구 23, 마포구 16, 관악구 15
  - 유형별: 도로 21, 소음 15, 환경 10, 청소 8

○ **(민간) 같은 규율이 경영 보고에도 필요**
  - 일별 확정치를 주별·월별·분기별로 올려 쌓음 — 상위 집계가 원천을 다시 읽으면 같은 문제
  - 월간 합계가 일별 합과 안 맞는데 양쪽 다 "제대로 계산된" 상황이 됨
  - 계층을 어기는 순간 두 보고서의 정합은 우연에 맡겨짐

#### 4-4. 배치 실패 대응 체크리스트

**표 7.4** 배치 실패 대응 체크리스트

| 단계 | 점검 항목 | 실습 근거 |
|---|---|---|
| 1. 발견 | 실패한 run의 날짜(logical date)와 태스크를 특정 | 7/4 run: validate_input failed |
| 2. 원인 분류 | 입력 문제/품질 게이트/코드 결함/인프라 중 무엇인가 | 입력 파일 없음(FileNotFoundError) |
| 3. 영향 범위 | 하류 태스크·후속 보고가 낡은 산출물로 돌지 않았는가 | 하류 4개 전부 upstream_failed — 미생성 |
| 4. 재실행 판단 | 원인 해소 후 해당 날짜만 재실행하면 되는가 | logical date 단위 재실행 |
| 5. 재실행 안전 | 이중 집계·산출물 분기를 만들지 않는가 | 해시 동일 실측(재현성) |
| 6. 상위 산출물 | 주간 등 롤업 계층의 재생성이 필요한가 | 일별 복구 후 재롤업 |
| 7. 재발 방지 | 같은 원인의 실패를 알림·검증으로 앞당길 수 있는가 | 11장 모니터링으로 확장 |

#### 4-5. 역방향 — 이 장의 설계를 민간 현장으로

○ **일매출 집계·정산 파이프라인** — 이 장의 일별 DAG와 골격이 같음
  - 자정 이후 결제·환불·취소를 전량 읽어 최종 매출 확정 → 회계 원장에 기록
  - 마감을 자정+N시간으로 잡는 이유 = 1-3의 실행 시각 역산(환불이 결제보다 늦게 도착)
  - 바뀌는 것은 근거 — 공공은 감사·정보공개, 민간은 마감한 회계 기간을 흔들 수 없다는 회계 규율

○ **추천 모델 재학습 배치** — 태스크가 길어질 뿐 구조가 같음
  - `validate_logs → clean_and_map → build_features → train_model → evaluate → deploy`
  - `evaluate`가 `check_quality` 자리 — 성능이 기준 이하면 `deploy`를 upstream_failed로 멈춤
  - "틀린 보고서를 안 만든다"가 "나쁜 모델을 안 내보낸다"로 바뀔 뿐 원리는 하나(9장)

○ **야간 ETL 적재·BI 리포트 자동화** — 2절과 4절이 함께 옮겨 감
  - 여러 운영 DB(주문·재고·회원·물류) → 새벽 추출 → 데이터 웨어하우스 적재
  - 상품명·카테고리 표기 변형을 SKU로 통일 = 2절의 표준 코드 매핑
  - 일별 확정 데이터를 주별·월별 롤업 = 4-3의 계층화 / 손으로 짠 총계 보존식이 dbt test로 선언될 뿐

○ **관통하는 하나** — 태스크 분할 경계 / 스케줄 주기·실행 시각 / 재시도 정책 / 멱등성 확보 방식, 이 네 결정은 공공이든 민간이든 똑같이 내린다. **근거만 도메인이 바꾼다**(공공: 감사·형평성·법적 보고 의무 / 민간: 매출·비용·SLA)

○ **방향은 비대칭** — 민간→공공은 재현 증거·원천 스냅숏·개정 이력이 한 겹 얹히지만, 공공→민간은 그 겹을 벗겨도 손해가 없다(재현성 검증 → CI 테스트, 미매핑 분리 보고 → 마스터 데이터 보강 목록)

### 실습 7.1: 일별 민원 요약 DAG 작성(★★★☆☆)

남이 정해 준 DAG를 그대로 돌리면 태스크가 왜 5개인지, 재시도를 왜 그 값으로 두었는지 묻지 않게 된다. 먼저 자기 판단으로 분할 경계와 운영 정책을 정하고 실패 전파를 예측한 다음 실행 결과와 맞춰 본다. 어긋난 지점이 곧 자기 설계의 결함이다.

#### 3단계 대조(8분) — 예측과 실측 맞춰 보기

예측표의 "실제" 열을 시나리오 C의 결과(표 7.3)로 채운다. `validate_input`은 failed, 나머지 넷은 upstream_failed다.

○ **"다섯 개 모두 failed"로 적었다면** — 하류 넷은 실행됐다가 실패한 것이 아니라 **아예 실행되지 않았다**
  - 갈리는 지점은 산출물 — 실행됐다면 절반쯤 쓰다 만 보고서가 남고 다음 롤업에 섞여 들어감
  - 실행되지 않았으므로 그런 파일이 없고 `_SUCCESS` 마커도 없음

○ **"validate_input만 failed, 나머지는 그냥 건너뜀"으로 적었다면** — 절반 맞다
  - 남은 절반은 그 건너뜀이 **상태로 기록된다**는 것
  - 상태가 없으면 "돌지 않았다"와 "돌 필요가 없었다"를 구분 못 함 → 표 7.4의 1단계가 성립하지 않음

○ **재실행 범위** — 답은 "그 날짜의 run 전체"
  - 파일이 도착한 뒤 7/4 run을 다시 돌림, 다른 날짜는 자기 logical date의 입력만 읽었으므로 무관
  - 다만 7/4가 주간 창 안에 들어가면 롤업도 재실행 — `_SUCCESS`가 생기면 합산 대상이 하나 늘어 수치가 바뀜

○ **설계표로 돌아가기** — 시나리오 C가 보여 준 것은 **입력 없음이 재시도로 낫지 않는 실패**라는 사실
  - `validate_input`의 재시도를 넉넉히 잡았다면, 그것은 파일 도착을 기다리는 장치일 수도(원천이 몇 분 늦을 때) 실패 통보를 늦추기만 하는 장치일 수도 있음(파일이 아예 안 올 때)
  - 어느 쪽인지는 원천의 지연 패턴이 정함 — 요구사항의 "늦으면 새벽 2시를 넘기는 날도 있다"가 근거
  - → 표 7.5의 재시도 칸과 "깨지는 조건" 칸을 다시 쓴다. **제출하는 설계표는 이 수정을 반영한 최종본이다.**

#### 4단계 위험 식별(7분) — 설계와 증거를 검수 언어로

검수·감사가 요구하는 형태는 "무엇이 잘못될 수 있는가 / 근거가 어느 산출물의 어느 값인가 / 무엇으로 막는가"다. 앞 네 행은 실행 증거에서, 마지막 행은 1단계 설계에서 나온다.

| 위험 | 실습 근거 | 대응 방향 |
|---|---|---|
| 정제 단계의 조용한 레코드 유실 | 총계 보존식 검증(60 = 54+2+3+1) | 품질 게이트로 보존 위반 시 배치 실패 |
| 낡은 산출물로 하류 실행 | 7/4: 하류 전부 upstream_failed로 미실행 | 의존성 선언 + 실패 전파 확인 |
| 재실행 시 산출물 분기 | 해시 동일 실측 | 결정적 산출물 + 덮어쓰기 설계 |
| 미매핑의 자동 끼워 맞춤 | 판교·성남시·김포 분리 보고 | 원문 보존·후속 조치 절차화 |

대응 방향에 "모니터링한다"만 적으면 그 행은 검수 문서에서 쓸모가 없다. **바꿀 설정값이나 바꿀 설계 결정**을 적는다.
