### 1. 데이터 엔지니어링이란 무엇인가 (15분)

#### 1-1. 스크립트와 파이프라인 사이

○ **출발 장면**
  - 어느 부서 담당자가 매주 월요일 아침 공공 API를 호출해 엑셀로 정리하는 파이썬 스크립트를 갖고 있다
  - 이 스크립트는 잘 동작한다 — 그런데 네 가지 상황을 못 견딘다
    1. 담당자가 휴가를 가면 그 주 데이터가 없다 (사람 의존)
    2. 어느 주에 API가 빈 응답을 줬는데 아무도 눈치채지 못한다 (검증 부재)
    3. 1년 뒤 감사에서 "그 수치는 어떤 데이터로 만들었는가"를 물으면 답할 원본이 없다 (원천 미보존)
    4. 담당자가 인사이동으로 떠나면 스크립트를 어떻게 돌리는지 아무도 모른다 (문서·버전 부재)

○ **DE의 정의**
  - DE는 데이터를 다루는 코드를 짜는 일이 아니라, **사람이 매번 개입하지 않아도 데이터가 신뢰할 수 있는 품질로, 예측 가능한 시간에, 통제된 권한 아래 흐르게 만드는 운영 설계**다
  - 위 네 가지 약점을 각각 스케줄링, 검증과 알림, 원천 보존과 재처리, 버전과 문서라는 시스템 요구사항으로 바꾸는 일이다

**표 1.1** DE 4단계와 대표 실패 모드

| 단계 | 핵심 질문 | 대표 실패 모드 |
|---|---|---|
| 수집 | 언제든 같은 방식으로 받아올 수 있는가 | 중복, 지연 이벤트, 인증 실패, 유실 |
| 저장 | 원천을 보존하며 접근을 통제할 수 있는가 | 저장 위치 난립, 권한 혼선 |
| 변환 | 의미를 유지하며 표준화할 수 있는가 | 스키마 불일치, 결측/이상치, 조용한 유실 |
| 제공 | 소비자가 예측 가능하게 쓸 수 있는가 | 하위호환 붕괴, 계약 없는 변경 |

#### 1-2. 수집: 공공 API의 네 가지 현실

○ **인증은 코드 밖에서도 깨진다**
  - 활용신청이 승인된 직후에도 한동안 403(권한 없음)이 나오다가 200(성공)으로 바뀌는 경우가 있다 (이 교재의 실습 1.1 준비 과정에서 관찰된 사례는 약 2분 — 상황에 따라 달라질 수 있는 일회 관찰)
  - "인증 실패"는 코드 버그만이 아니라 승인 상태·키 만료·전파 지연이라는 **운영 사건**이다

○ **호출량에는 한도가 있다**
  - 공공 API는 일일 호출 한도(쿼터)를 둔다 — 1분마다 부를지 1시간마다 부를지는 신선도와 쿼터 소진 속도를 맞바꾸는 결정이다

○ **응답은 페이지로 나뉜다**
  - 에어코리아 응답에는 `totalCount`(전체 건수), `numOfRows`(페이지당 건수)가 함께 온다
  - 첫 페이지만 읽는 코드는 `totalCount`가 `numOfRows`를 넘는 순간부터 나머지를 **조용히** 버린다

○ **재시도는 중복을 낳는다**
  - "응답을 못 받았다"와 "서버가 처리하지 않았다"는 다르다 — 요청은 처리됐는데 응답만 유실됐다면, 재시도는 같은 데이터를 두 번 만든다
  - 4장 실측: 같은 이벤트 스트림을 커밋 시점 한 줄만 바꿔 수집하면, 한쪽 설계(at-most-once)는 크래시 시 20건을 오류 로그 없이 유실했고, 다른 쪽(at-least-once)은 10건을 중복 수신했다
  - 중복은 버그가 아니라 전달 보증의 정의대로의 동작이다 — 그래서 재시도와 멱등성(같은 작업을 여러 번 해도 결과가 한 번과 같은 성질)은 한 쌍으로 설계된다

#### 1-3. 저장·변환·제공에서 반복되는 위험

○ **저장 — 원천 보존이 필요한 세 가지 이유**
  - 재처리(변환 로직 버그가 나중에 발견되면 원천으로 다시 만든다), 감사(요약본은 증거가 못 된다), 새 요구(요약 시점에 버린 필드는 되살릴 수 없다)
  - 예산이 못 견디므로 접근 빈도에 따라 핫/웜/콜드로 나눠 두는 계층형 저장이 현장의 타협이다

○ **변환 — 형 변환이 아니라 의미 변환**
  - 측정값은 숫자가 아니라 문자열 `"21"`로 온다 — 형 변환을 빠뜨리면 조용히 오염된다
  - 결측은 `"-"`나 `null`로 온다 — 이를 0으로 바꾸면 평균이 실제보다 낮아진다(값을 만들어내는 것과 같다)
  - 현장 방법: **버린 것을 센다** — 7장 실측에서 민원 60건 정제 시 60 = 정상 매핑 54 + 지역 미기재 2 + 매핑 실패 3 + 중복 1이라는 총계 보존식을 검증하고, 등식이 깨지면 배치를 실패시킨다

○ **제공 — 침묵 실패(silent failure)**
  - 제공 단계의 산출물은 데이터가 아니라 **약속**(데이터 계약: 스키마·의미·품질·변경 절차)이다
  - 필드명이 바뀌어도 소비자 파서는 에러 없이 None을 돌려주고, 집계는 계속 돌지만 결측률만 조용히 100%가 된다 — 이것이 침묵 실패다
  - 8장 실측: 피처 적재 명령이 정상 종료 로그를 남겼지만 실제로는 **0건 적재**됐다 — 발견은 한참 하류의 조회 코드에서야 이뤄졌다
  - 죽는 실패는 알림이 오지만 침묵 실패는 누군가 의심하기 전까지 발견되지 않는다 — 그래서 죽는 실패보다 위험하다

### 2. MLOps란 무엇인가 (15분)

#### 2-1. 모델은 만들어지는 것이 아니라 운영되는 것

○ **정의**(Kreuzberger, Kühl, Hirschl, 2023)
  - MLOps는 ML 제품의 종단간(구상·구현·모니터링·배포·확장)을 다루는 모범 사례·개념·개발 문화를 아우르는 방법론이다
  - 핵심은 두 가지 — 특정 도구가 아니라 원칙·문화까지 포함하고, 대상이 "모델"이 아니라 배포되고 운영되고 낡아가는 "ML 제품"이다

○ **끝나지 않는 루프**(Shankar 외, 2022)
  - ① 데이터 수집·라벨링 → ② 성능 개선 실험 → ③ 다단계 배포 평가 → ④ 프로덕션 성능 하락 모니터링, 그리고 다시 ①로
  - "모델 개발 완료"라는 종착점이 없다 — 이것이 MLOps가 프로젝트가 아니라 운영인 이유다

#### 2-2. DevOps와 다른 이유 — 하나를 바꾸면 전부 바뀐다

**표 1.2** DevOps와 MLOps의 차이

| 관점 | DevOps | MLOps |
|---|---|---|
| 변화의 단위 | 코드와 설정 | 코드 + 데이터 + 모델 |
| 실패 신호 | 오류/다운타임 | 오류 + 성능 저하 + 분포 변화 |
| 테스트 대상 | 함수·통합·시스템 | 위 + 데이터 검증 + 모델 검증 |

○ **CACE 원칙**(Sculley 외, 2015) — "Changing Anything Changes Everything"
  - 일반 소프트웨어는 코드만 바뀌므로 모듈 경계와 코드 리뷰로 변경 영향을 가둘 수 있다
  - 모델은 다르다 — 입력 피처 하나의 분포가 바뀌면 나머지 피처들의 가중치와 상호작용까지 함께 변한다
  - 그래서 "어떤 데이터·코드·환경·파라미터로 이 모델이 나왔는가"를 기록하는 일은 도덕적 권고가 아니라 운영 필수품이다

#### 2-3. 성숙도 모델 — 우리 기관은 어디에 있는가

**표 1.3** MLOps 성숙도 모델(Google 기준)

| 수준 | 내용 |
|---|---|
| 수준 0: 수동 프로세스 | 학습·배포 전 단계가 수동. 노트북에서 학습한 모델을 파일로 전달 |
| 수준 1: ML 파이프라인 자동화 | 학습 파이프라인이 자동화되어 지속 학습 가능. 데이터·모델 검증이 파이프라인 안에 |
| 수준 2: CI/CD 파이프라인 자동화 | 파이프라인 자체의 빌드·테스트·배포까지 자동화 |

○ **현장 감각**: 수준 0은 부끄러운 상태가 아니라 보편적 출발점이다
  - 문제는 수준 0에 머무는 것 자체가 아니라, 수동 절차가 기록 없이 수행되어 재현·감사가 불가능해지는 것이다
  - 이 교재의 실습이 만드는 것이 정확히 0에서 1로 오르는 사다리다 (9장 실험 추적, 10장 배포 자동화, 11장 모니터링)

#### 2-4. 현장은 무엇이 성공을 가른다고 보는가

○ **3V**(Shankar 외, 2022 — 18명 ML 엔지니어 인터뷰)
  - **Velocity(속도)**: 실험 아이디어를 빠르게 돌려보는 반복 능력
  - **Validation(검증)**: 가능한 한 이르고 여러 단계에서 실패를 잡는 능력
  - **Versioning(버전 관리)**: 데이터·모델의 과거 버전을 보관해 언제든 되돌릴 수 있는 능력
  - 이 3V가 이 교재의 9장(실험 추적·레지스트리), 10장(배포 게이트), 13장(변경 관리)과 그대로 대응한다

○ **국내 현장 강연**(메타코드M, 2026 — 카카오 추천팀 출신 데이터 엔지니어)
  - "ETL 자체는 쉽고, 유실·중복이 발생하지 않는 파이프라인 설계가 고급 기술"이라는 강조 — 이 교재가 4·5장을 별도로 두는 이유
  - "도구가 이렇게 하라던데요"로 기술 선택을 정당화하면 장애 시 대처도 성장도 없다는 지적 — 근거 기반 의사결정

### 3. DE와 MLOps가 만나는 지점 — 실패는 어떻게 퍼지는가 (10분)

#### 3-1. 실패의 연쇄: 코드 개편 시나리오

○ 아래는 수치 없는 구조 시나리오다 — 실측이 아니라 실패가 퍼지는 구조를 보여주기 위한 구성이며, 각 단계의 감지 장치는 이 교재의 다른 장들과 연결된다
  - D−14: 민원 유형 코드 체계 개편이 타 부서에서 확정된다
  - D−7: 개편 공지가 파이프라인 담당까지 전달되지 않는다 — **문제의 시작은 기술이 아니라 조직의 변경 관리다**
  - D-day: 신규 코드가 매핑 테이블에 없어 전부 "기타"로 분류된다 — 시스템은 죽지 않는다(침묵 실패)
  - D+1: 대시보드의 "기타" 비율이 튀지만, 보는 사람이 없거나 임계·알림이 없으면 지나간다
  - D+7: 모델 입력의 범주 분포가 무너져 예측 품질이 저하된다
  - D+10: 민원 배정 오류에 대한 민원이 들어온다 — 실패가 시민에게 도달했다
  - D+11~: 역추적 시작 — 데이터→피처→모델→예측의 연결 기록(라인리지)이 없으면 몇 주가 걸린다

○ **교훈**: 발원지(공지 누락)와 발현지(모델 품질)가 멀수록, 발현지만 보는 조직은 원인을 못 찾는다 — 감지 지점이 상류에 있을수록 실패는 싸게 끝난다

#### 3-2. 학습-서빙 불일치(training-serving skew)

○ 학습은 과거 데이터 위에서 배치로, 서빙은 현재 데이터 위에서 실시간으로 일어난다 — 두 경로가 피처를 **서로 다른 코드로** 계산하면 미세한 차이(결측 처리, 집계 창, 반올림)가 스며든다
○ 모델은 학습 때 본 계산 방식을 전제하므로, 서빙의 다른 계산은 에러가 아니라 성능 저하로 나타난다 — 역시 침묵 실패다
○ 구조적 해법이 피처 스토어(8장)다 — 피처의 정의·계산을 한곳에 두고 학습과 서빙이 같은 정의를 소비하게 한다
○ 시간 축의 함정: 학습 데이터를 만들 때 "그 시점에 알 수 있었던 값"만 조인해야 한다 — 8장 실습에서 시점 조인 시 4행 중 1행이 탈락하는데, 이는 버그가 아니라 그 시점에 존재하지 않았던 피처를 미래에서 끌어오지 않았다는 증거다

#### 3-3. 이름 붙은 숨은 기술 부채(Sculley 외, 2015)

○ **글루 코드(glue code)**: 범용 도구를 잇는 접착 코드가 시스템 대부분을 차지 — 학습 코드는 일부이고 나머지가 데이터를 옮기고 형식을 바꾸는 코드인데, 테스트·리뷰는 학습 코드에 몰리기 쉽다
○ **파이프라인 정글(pipeline jungles)**: 요구가 생길 때마다 정제 경로를 덧대면 어떤 데이터가 어떤 경로를 거치는지 아무도 전체를 모르게 된다 — 비용은 장애 시 역추적 불가로 청구된다
○ **미신고 소비자(undeclared consumers)**: 내 출력을 누가 쓰는지 모르는 상태 — 출력 형식을 "개선"했더니 이름 모를 하류 시스템이 무너진다. 방어는 소비자 등록(13장 피처 카탈로그)

### 4. 공공이라서 달라지는 것 (10분)

#### 4-1. 규제 — 조문이 설계를 결정한다

○ "개인정보를 보호해야 한다"는 문장은 설계에 쓸 수 없다 — 설계에 쓰이는 것은 구체 조문이다
  - **제18조**(목적 외 이용·제공 제한): 접근 정책에 "무슨 목적으로"가 들어가야 하고, 목적 외 조회는 거부·기록되어야 한다
  - **제23조**(민감정보 처리 제한): 건강 등 민감정보 한정 — 일반 개인정보의 목적 제한(제18조)과 범위를 섞으면 안 된다
  - **제33조**(개인정보 영향평가): 개인 단위 데이터 시스템은 코드를 짜기 전에 영향평가 대상 여부를 먼저 판정한다
  - **제37조의2**(자동화된 결정에 대한 권리, 2024년 3월 시행): AI가 배정·우선순위를 자동 결정하면 이의 제기 창구와 설명 절차가 시스템 요구사항이 된다
  - AI기본법이 2026년 1월 22일 시행되었고, EU AI Act(Regulation 2024/1689)는 위험 수준별로 의무를 차등 부과한다 — **규제는 배포 직전 체크리스트가 아니라 설계 시작 시점의 입력이다**

#### 4-2. 감사·투명성 — 재현할 수 없으면 증거가 아니다

○ 공공 감사 요구는 한 문장으로 환원된다 — "그때 그 데이터로 그 판단을 다시 만들어낼 수 있는가"
  - 증거를 사람이 사후에 쓰는 문서가 아니라 **시스템이 실행 중에 만드는 산출물**로 둔다(9장 지문, 13장 감사표)
○ 투명성을 "모델 설명 기법 도입"으로 환원하면 순서가 뒤집힌다
  - 16장 실측: 민원 예측 모델이 고민원 지역을 일관되게 과소예측했는데, 원인은 복잡한 알고리즘이 아니라 모델이 지역을 구분할 어떤 피처도 쓰지 않았다는 사실(피처 중요도 0.0)이었다
  - 설명해야 할 것은 모델 내부보다 먼저 "이 피처가 무엇을 의미하고 어떻게 집계되었는가"다

#### 4-3. 조달·검수와 예산 — 검수 가능해야 하고, 측정 후 증설한다

○ 검수 관점의 핵심은 **요구사항의 검수 가능성**이다
  - 검수 불가: "실시간 처리를 지원할 것"
  - 검수 가능: "지연 이벤트의 수용·폐기 규칙을 제시하고 폐기 건수를 지표로 노출할 것"
○ 공공 예산은 연간 편성에 묶여 "필요하면 늘린다"가 통하지 않는다 — **측정 후 증설** 원칙이 필요하다
  - 12장 실측: 서빙 워커를 1개에서 2개로 늘렸을 때 처리량은 2배가 아니라 1.26배였다(부하 조건과 자원 경합 때문) — 실측 없이 "2배 증설=2배 처리"를 가정한 예산은 틀린다

**표 1.4** 민간 방법의 공공 번역(일부)

| 민간 현장 방법 | 공공 대응물 | 공공 특수성에 따른 변형 |
|---|---|---|
| A/B 테스트(트래픽 분할 비교) | 섀도 배포(전원 동일 서비스, 후보는 로그로만 평가) | 시민마다 다른 서비스 제공은 형평성·법적 문제 소지 |
| 유실·중복 없는 파이프라인 | 동일(민원 1건 유실 = 처리 누락) | 정합의 증거(총계 보존·감사 로그)까지 산출물로 요구 |
| 트래픽 폭증 대비 부하 테스트 | 재난·마감일 접수 폭증 대비 | 용량 천장·포화 자원의 실측 보고가 검수 항목 |

### 실습 1.1: 공개 API 응답 구조 확인 및 JSON 탐색

#### 실습 목표
- 실제 공공 API(한국환경공단 에어코리아 대기오염정보)를 호출해 응답 구조를 직접 확인한다
- 응답을 헤더(처리 결과)와 바디(데이터)로 나눠 읽고, 레코드 배열에서 필드를 추출한다
- 운영·검수 관점에서 "이 응답에서 무엇이 깨질 수 있는가"를 식별한다

#### 실행 환경
- Python 3.10 이상, `requests` 설치(`pip install -r code/requirements.txt`)
- 공공데이터포털 활용신청 후 발급되는 인증키를 환경변수 `DATA_GO_KR_API_KEY`로 전달(코드·문서에 평문으로 남기지 않는다)
- 키가 없으면 `--simulate` 옵션으로 오프라인 재현 가능 — 이 경우 결과 파일에 `source: "simulator"`가 표기되어 실제 데이터와 구분된다

#### 실행 명령

```bash
cd practice/chapter1
export DATA_GO_KR_API_KEY="..."   # Windows(PowerShell): $env:DATA_GO_KR_API_KEY="..."
python3 -m venv venv && source venv/bin/activate
pip install -r code/requirements.txt
python3 code/1-1-public-api.py --sido 서울 --rows 100
```

#### 핵심 코드

```python
payload = fetch_airkorea(api_key, sido="서울", rows=100)  # 실제 호출
items = extract_items(payload)                            # response.body.items
write_json(out_path, summarize_live(items))               # 측정소 요약
```

_전체 코드는 practice/chapter1/code/1-1-public-api.py 참고_

#### 실행 결과 확인 사항

에어코리아 응답은 "처리 결과(header)"와 "데이터(body)"로 나뉘며, 성공 판정은 HTTP 200이 아니라 헤더의 `resultCode`다. 아래는 실제 호출 1회(`ch1_api_summary.json`, `source: "live"`)의 결과다 — 실시간 데이터이므로 값은 호출 시점마다 달라지고, 변하지 않는 것은 "구조"다.

1. **측정소 수**: 40개(서울, `station_count`)
2. **PM10 평균** 20.0㎍/㎥, **PM2.5 평균** 12.7㎍/㎥, **결측** 0건(`pm10_missing`/`pm25_missing`)
3. **표본 레코드**: 정릉로 측정소 — `pm10Value` 21, `pm25Value` 12, `o3Value` 0.040, `khaiValue` 59
4. **필드 구성**(`available_fields`): 측정 항목마다 `pm10Value`/`pm10Grade`/`pm10Flag`처럼 값·등급·플래그가 한 묶음으로 제공됨

#### 관찰 과제

○ **관찰 1**: 성공 판정 기준
  - 게이트웨이는 HTTP 200을 주면서도 헤더에 오류 코드를 담을 수 있다 — 그래서 수집기는 HTTP 상태와 헤더의 `resultCode`를 모두 확인해야 한다
  - 코드가 HTTP 상태만 보고 "성공"이라 판단하면, 실제로는 실패한 호출을 성공으로 기록하는 침묵 실패가 생긴다

○ **관찰 2**: 타입과 결측 표기
  - 측정값이 숫자가 아니라 문자열(`"21"`)로 온다 — 형 변환을 빠뜨리면 평균 계산이 조용히 틀어진다
  - 결측·점검 중인 측정소는 값이 `"-"`나 `null`로 온다 — 이번 스냅샷은 결측 0건이지만, 이는 "이 시각에 없었다"이지 "앞으로도 없을 것이다"가 아니다. 수집기는 결측이 있는 시각을 전제로 짜야 한다

○ **관찰 3**: 페이지네이션
  - 이번 조회는 측정소 40개가 `numOfRows=100` 한 페이지에 다 들어온다 — 그런데 전국 조회처럼 `totalCount`가 `numOfRows`를 넘으면, 첫 페이지만 읽는 코드는 나머지를 조용히 버린다
  - 구조를 아는 것과 매 응답에서 `totalCount ≤ numOfRows`를 확인하는 코드를 짜는 것은 다르다

#### 확장 과제 (선택)

1. `--sido`를 바꿔 호출하고 측정소 수·결측률을 다른 시도와 비교한다
2. 같은 호출을 1시간 간격으로 2회 수행해 "값은 변하고 구조는 같다"를 확인한다(2장에서 같은 데이터로 드리프트 검정을 다룬다)
3. `--simulate --count 30 --seed 42`로 오프라인 재현 결과를 만들고, `source` 필드로 실제 데이터와 구분되는지 확인한다

## 비즈니스 적용 노트

> 이 장의 기법이 민간 비즈니스에서 어떤 지표·목표·도구로 쓰이는지 정리한다.

### 공공 → 비즈니스 대응표

| 공공 맥락 | 비즈니스 맥락 | 차이점 |
|---|---|---|
| 민원·재난 실시간 데이터 수집 | 주문·결제·클릭스트림 실시간 수집 | 공공은 감사·재현 의무가 법적 근거를 가지고, 비즈니스는 매출·전환율 최적화가 수집 설계의 핵심 동기다 |
| MLOps 성숙도(수준 0→2) | ML 프로덕션 성숙도(추천·검색·광고 파이프라인) | 공공은 투명성·형평성이 승격 기준에 추가되고, 비즈니스는 A/B 테스트 전환율이 승격 기준이다 |
| 침묵 실패(필드 변경 후 결측률 100%) | 침묵 실패(피처 드리프트로 클릭률 하락) | 발견 경로가 다르다. 공공은 민원·감사로 발현하고, 비즈니스는 매출 하락·이탈률 증가로 발현한다 |
| 감사 추적(재현 가능한 산출물) | 모델 거버넌스(실험 기록·배포 이력·롤백 증적) | 공공은 외부 감사 대응이 법적 의무이고, 비즈니스는 내부 컴플라이언스가 동기다 |
| 섀도 배포(형평성 문제로 A/B 대신 사용) | A/B 테스트 + 카나리 배포 | 비즈니스는 트래픽을 나눠 직접 비교하는 것이 표준이고, 공공의 형평성 제약이 없다 |

### 비즈니스에서의 핵심 지표

○ **ML 프로덕션 성숙도 지표**
  - 배포 빈도: 모델을 프로덕션에 올리는 횟수(주·월 단위)
  - 실험-배포 리드 타임: 실험 아이디어에서 프로덕션 반영까지 걸리는 시간(3V 중 Velocity에 해당)
  - 롤백 소요 시간: 문제 발견 후 이전 모델로 되돌리는 데 걸리는 시간

○ **데이터 파이프라인 운영 지표**
  - 데이터 신선도: 최신 데이터가 서빙 계층에 도달하기까지의 지연
  - 침묵 실패 탐지 시간(MTTD, Mean Time To Detect): 데이터 품질 문제를 발견하기까지 걸리는 시간, 짧을수록 하류 피해가 작다

○ **모델 운영 지표**
  - 온라인 지표: CTR(클릭 전환율), CVR(구매 전환율), ARPU(사용자당 평균 매출) 등 비즈니스 KPI(핵심 성과 지표)
  - 오프라인-온라인 일관성: 오프라인 평가 지표와 온라인 A/B 결과의 방향이 일치하는 비율

### 실무 적용 사례

○ **이커머스 추천 시스템 운영**
  - 이 장의 DE 4단계(수집-저장-변환-제공)가 그대로 적용된다. 수집은 클릭·구매 이벤트, 저장은 행동 로그 원천 보존, 변환은 피처 계산, 제공은 추천 API 서빙이다
  - 학습-서빙 불일치가 특히 자주 발생한다. 학습은 배치 집계 피처를, 서빙은 실시간 집계 피처를 쓰면 값이 어긋난다 — 피처 스토어(8장)가 해법이다

○ **광고 플랫폼 실시간 파이프라인**
  - "사람 없이도 신뢰·정시·통제된 흐름"이 광고 입찰·과금 시스템의 기본 요구다
  - 재시도와 멱등성 설계는 과금 중복 방지에 직결된다 — 클릭 과금이 중복 집계되면 광고주에게 이중 청구가 발생한다

○ **금융 ML 운영**
  - 침묵 실패 개념이 그대로 적용된다. 신용평가 모델의 입력 스키마가 바뀌어도 점수는 계속 나오되, 정확도가 조용히 하락한다
  - 3V 중 Versioning(버전 관리)이 특히 중요하다 — 감독기관이 "6개월 전 그 대출 거절은 어떤 모델·데이터로 내린 판단인가"를 물을 수 있기 때문이다
