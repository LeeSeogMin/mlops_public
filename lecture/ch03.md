# 제3장 데이터 파이프라인 아키텍처 설계

---

## [전반부] 이론 강의
---

### 학습 목표

- 배치·스트리밍·하이브리드(Lambda/Kappa) 아키텍처를 트레이드오프로 비교한다
- 파이프라인 5계층(수집·저장·처리·서빙·모니터링)의 역할을 이해한다
- 공공 요구사항(보안·감사·개인정보·장애 대응)을 설계 산출물로 전환한다
- 요구사항에서 로컬 구성 계획(계층·서비스·포트·의존성)을 도출하고 각 선택의 근거를 적는다

### 1. 배치·스트리밍·하이브리드 아키텍처
#### 1-1. 세 가지 처리 방식

○ **배치(batch)**
  - 데이터를 일정 기간 모았다가 한꺼번에 처리
  - 강점: 정확성, 재현성(reproducibility) — 늦게 도착한 이벤트까지 포함해 확정치를 낼 수 있음
  - 약점: 지연 — "지금 무슨 일이 벌어지는가"에 답할 수 없음
  - 예: 월간·분기 통계 보고

○ **스트리밍(streaming)**
  - 이벤트가 도착하는 즉시 처리
  - 강점: 즉시성 — 재난 신고 건수를 초 단위로 갱신 가능
  - 약점: 정확한 집계 부담 — 지연 이벤트(발생 23:58, 도착 00:03)를 어떻게 처리할지의 문제
  - 예: 재난 상황실 실시간 현황판

○ **하이브리드(hybrid)**
  - 배치 + 스트리밍을 결합 → "빠른 근사치 + 정확한 확정치" 동시 제공
  - 공공 업무의 이중성에서 필요: 실시간 대응(스트리밍) + 사후 감사·통계(배치)
  - 두 가지 설계 방식: Lambda와 Kappa

#### 1-2. Lambda 아키텍처

○ 구조
  - **배치 레이어**: 원천 데이터 전체를 주기적으로 재계산 → 확정치
  - **스피드 레이어**: 도착 즉시 실시간 처리 → 근사치
  - 조회 시 둘을 합침: "확정된 과거 + 근사한 최근"

○ 장점
  - 정확한 확정치와 빠른 근사치를 동시에 얻음

○ 약점 — 로직 이중화 부채
  - 같은 집계 로직을 **두 벌**(배치용 + 스트리밍용)로 유지해야 함
  - 하나만 수정하고 다른 쪽을 빠뜨리면 → 확정치와 근사치가 어긋남(침묵 실패)
  - 1장의 CACE 원칙(Changing Anything Changes Everything)과 직결

○ 민간도 같은 부채를 진다
  - 배치는 dbt, 스트리밍은 Flink로 짜면 두 벌을 계속 맞추는 인건비가 든다
  - 관리 지표: **로직 동기화율** — 두 코드가 같은 입력에 같은 결과를 내는지 검증한 항목의 비율
  - 100%가 아니면 어긋난 항목이 침묵 실패 후보. 공공은 그 값이 인력 배치·예산 근거라 확인 주기를 더 짧게 잡는다

○ 이 교재에서의 실물
  - 스피드 레이어 → 6장 스트리밍 실습
  - 배치 레이어 → 7장 배치 정제 실습

#### 1-3. Kappa 아키텍처

○ 구조
  - 배치 레이어를 두지 않고 **스트리밍 단일 레이어**만 유지
  - 재처리가 필요하면 과거 이벤트를 처음부터 다시 흘려보냄(리플레이, replay)
  - 로직이 한 벌 → 배치·스트리밍 불일치가 구조적으로 사라짐

○ 전제 조건
  - 이벤트 로그의 보존과 재생 가능성 (예: Kafka 오프셋)

○ 한계
  - 대규모 과거 데이터 재생은 배치 스캔보다 비효율적일 수 있음
  - 복잡한 다차원 집계·대규모 조인은 배치 엔진이 유리

○ Lambda vs Kappa: 기술 우열이 아니라 **선택**
  - 로직 이중화 부채를 감수할 것인가 vs 리플레이 비용을 감수할 것인가

○ 민간에서의 Kappa — 이벤트 소싱(event sourcing)과 짝
  - 현재 상태를 저장하는 대신 상태를 바꾼 사건을 순서대로 남기고, 필요할 때 다시 흘려 현재 상태를 만든다
  - 결과: 주문 상태 추적, 결제 이력 재구성
  - 공공의 감사 재현과 **구조가 같다** — 남기는 것은 결과가 아니라 사건. 다른 것은 목적(분쟁 처리 vs 감사 대응)

![Lambda와 Kappa의 재처리 경로 비교](assets/ch03/fig3-1-lambda-kappa.png)

**그림 3.1** Lambda와 Kappa: 재처리를 어디서 감당하는가

○ 그림 읽는 법
  - 위쪽 절반은 두 청사진이 같다 — 같은 이벤트, 같은 수집 로그
  - 갈라지는 지점은 그 아래: Lambda는 경로가 둘, Kappa는 하나
  - 오른쪽 초록 화살표가 리플레이 — 로그를 되감아 같은 코드로 다시 흘린다
  - 선택의 축: 재처리를 **로직 이중화**로 감당할 것인가, **리플레이 비용**으로 감당할 것인가

---

#### 1-4. 리플레이와 감사

○ 민간에서 리플레이: 버그 수정·로직 개선을 위한 재계산
○ **공공에서 리플레이**: 감사 대응 능력
  - 감사관: "왜 이 통계가 이렇게 나왔는가?"
  - 답: "그 시점에 들어온 그 데이터로 그 계산을 다시 만들어낼 수 있는가"
  - 로그 보존 + 오프셋으로 되감아 재생할 수 있는 아키텍처 → "재현해 보이겠습니다"
  - 요약본만 남긴 아키텍처 → 답할 수 없음

○ 선택을 수치로 좁히는 지표 2개
  - **재처리 소요 시간**: Lambda는 배치 재실행 시간, Kappa는 로그 리플레이 시간으로 잰다. 확정치를 며칠 안에 다시 내야 하는지가 두 방식의 상한을 가른다
  - **종단 지연(end-to-end latency)**: 발생부터 서빙까지. 민간은 실시간 추천 100ms 이하·광고 입찰 10ms 이하를 목표로 잡는 경우가 많다
  - 공공에서 종단 지연의 기준은 사업 성과가 아니라 **대응 시한** — 상황실이 몇 초 안에 갱신된 건수를 봐야 하는가

**표 3.1** 배치·스트리밍·하이브리드 비교

| 항목 | 배치 | 스트리밍 | Lambda | Kappa |
|---|---|---|---|---|
| 처리 시점 | 주기적 일괄 | 도착 즉시 | 배치+스피드 병렬 | 스트리밍 단일 |
| 지연 | 큼(분·시간) | 작음(초 이하) | 확정 크고 근사 작음 | 작음 |
| 재처리 | 배치 재실행 | 별도 설계 필요 | 배치 레이어 담당 | 로그 리플레이 |
| 로직 관리 | 한 벌 | 한 벌 | **두 벌(부채)** | 한 벌 |
| 공공 적용 | 정기 보고 | 재난·교통 실시간 | 대응+보고 동시 | 재처리·감사 |

### 2. 파이프라인 5계층
#### 핵심 원칙
- 계층은 제품 이름의 나열이 아니라 **"없으면 무엇이 실패하는가"**로 이해하는 역할 분해

#### 2-1. 수집 계층
- **역할**: 생산과 소비의 속도 차이를 흡수, 완충 로그를 두어 "빠르게 받고 천천히 처리"
- **없으면**: 속도 차이가 곧 장애(요청 거부, 데이터 유실)
- **대표 도구**: Kafka — 오프셋이 매겨진 로그로 보관, 컨슈머(consumer)가 자기 속도로 읽고 되감기 가능
- **실측(4장)**: 커밋 시점 한 줄만 바꾸면 at-most-once는 20건 유실, at-least-once는 10건 중복

#### 2-2. 저장 계층
- **역할**: 원천 데이터·가공 데이터 보존 + 접근 통제
- **없으면**: 재처리 불가, 감사 대응 불가, 새 요구 대응 불가
- **현장 방법**: 계층형 저장(핫/웜/콜드) — 예산과 접근 빈도에 따라 분배
- **최신 개념**: 레이크하우스(lakehouse) — 레이크(원천 보관) + 웨어하우스(정형 분석)를 한 계층으로 통합

#### 2-3. 처리 계층
- **역할**: 수집된 데이터를 스트리밍 또는 배치로 변환·집계
- **없으면**: 원천 이벤트가 그대로는 의미 있는 지표가 되지 못함
- **핵심 문제**: 지연 이벤트 — watermark로 "얼마나 기다렸다 창을 닫을지" 결정
- **실측**: 6장(스트리밍 watermark), 7장(배치 정제 — 총계 보존식 검증)

#### 2-4. 서빙 계층
- **역할**: 조회·리포팅·ML 예측 요구에 데이터를 통제된 성능으로 제공
- **없으면**: 데이터가 있어도 서비스가 안 됨
- **핵심 질문**: "새 모델을 어떻게 넣는가"보다 **"잘못됐을 때 어떻게 되돌리는가"**
- **공공 전략**: 섀도 배포(shadow deployment) — 이용자에게는 기존 모델, 로그에는 후보 모델 예측을 조용히 적재
- **실측(10장)**: champion 예측 6.0 vs challenger 예측 7.3636

#### 2-5. 모니터링 계층
- **역할**: 메트릭·대시보드로 시스템·모델의 상태를 관측 가능하게 함
- **없으면**: 침묵 실패가 발견되지 않음
- **골든 시그널(Golden Signals, Google SRE)**: 지연, 트래픽, 오류, 포화
- **대표 도구**: Prometheus(수집) + Grafana(시각화)
- **실측**: 11장(PSI 0.3324 — 단일 지표로 판단하면 안 되는 사례), 12장(CPU 106.3% 포화)

**표 3.2** 5계층 요약

| 계층 | 없으면 실패하는 것 | 대표 도구 | 이 교재 실측 |
|---|---|---|---|
| 수집 | 유실·과부하 | Kafka | 4장 |
| 저장 | 재처리·감사 불가 | Postgres | 5장, 13장 |
| 처리 | 의미 없는 원천 | Spark, Airflow | 6장, 7장 |
| 서빙 | 서비스 불가 | FastAPI | 10장 |
| 모니터링 | 침묵 실패 미발견 | Prometheus, Grafana | 11장 |

#### 2-6. 계층별 도구는 어떻게 고르는가

○ 표의 대표 도구는 정답이 아니다 — 고를 때 따지는 세 가지
  - ① 그 계층이 없을 때 실패하는 것을 이 제품이 실제로 막는가 (읽으면 지워지는 큐 → 리플레이 불가 → 감사 재현 요구 미충족)
  - ② 운영 인력이 감당하는가 (Kafka 직접 운영 = 전담 인력, 관리형 = 비용이 그 자리를 대신함)
  - ③ 뒤 계층의 선택을 얼마나 묶는가 (저장 포맷을 벤더에 묶으면 처리 엔진 선택지가 준다)

○ 민간은 네 번째 축으로 **비용**을 더한다
  - 수집·저장·처리·서빙 비용을 계층별로 분리 추적, 이벤트 1건당 비용(cost per event)으로 아키텍처 안 비교
  - 공공에서 이 축이 약한 이유는 비용이 덜 중요해서가 아니라 예산이 연간으로 묶여 월 단위 최적화 여지가 적기 때문

#### 2-7. 민간 실시간 아키텍처의 공공 적용

○ **이벤트 기반 아키텍처**: 서비스를 직접 호출로 잇지 않고 이벤트 발행·구독으로 느슨하게 연결 → 공공은 수집 계층(Kafka)을 중심에 두고 집계·알림·예측이 각자 구독(14장에서 격리 검증)
○ **멀티테넌시(multi-tenancy)**: 한 인프라 위 여러 고객사 격리 → 공공은 기관·지자체 격리
  - 격리의 **근거**가 다르다: 민간은 계약 격리(SLA·NDA(비밀유지계약)), 공공은 법적 격리(개인정보보호법 제18조)
  - 민간은 배상 범위를 계약이 정하고, 공공은 배상이 아니라 처분의 문제 → "경계를 넘지 않았다"를 로그로 증명할 의무가 한 겹 더(13장)
○ **실시간 대시보드**: 민간은 매출·트래픽 지표 → 공공은 민원·재난 현황판 + **형평 축**(지역·집단별 분해, 16장)

### 3. 공공 요구사항 → 설계 산출물
#### 3-1. 보안: 원칙이 아니라 설정으로
- TLS 전송 암호화, 저장 암호화, RBAC(역할 기반 접근 제어), 네트워크 분리
- **12-factor App 원칙**: 비밀은 코드·구성 파일이 아니라 환경(환경변수·시크릿 저장소)에 둔다
- 이유: 파일에 있으면 버전 관리 저장소에 커밋돼 노출, 회수 어려움

#### 3-2. 감사: 재현할 수 없으면 증거가 아니다
- 접근 로그, 변경 이력, 라인리지(lineage, 데이터→피처→모델→결과 추적), 보관 정책
- 핵심: 증거를 사람이 사후에 쓰는 문서가 아니라 **시스템이 실행 중에 만드는 산출물**로 둠
- 실측(13장): 허용 8건·거부 4건의 접근 판정 → 감사 점검표 10항목 자동 생성

#### 3-3. 개인정보: 조문이 설계를 결정한다
- 제18조(목적 외 이용·제공 제한): 접근 정책에 "무슨 목적으로"가 들어가야 함
- 제23조(민감정보 처리 제한): 건강 등 민감정보 한정 — 일반 개인정보에 확대 적용 금지
- 제33조(영향평가): 개인 단위 데이터 시스템은 파이프라인 이전에 영향평가 선행
- 제37조의2(자동화된 결정에 대한 권리, 2024년 3월 시행): 이의 제기 창구·설명 절차 필수

#### 3-4. 장애 대응: 고장을 내 봐야 확인된다
- 재시도·멱등 처리, 이중화, 백업·복구(DR)
- "비기능 요구는 고장을 일부러 내 보기 전에는 확인되지 않는다"
- 실측(14장): 오염 이벤트 격리, 중복 재전송 흡수, 부분 실패 격리 — 3종 드릴
- **복구 목표를 숫자로**: RTO(Recovery Time Objective, 복구까지 허용하는 시간), 가용성 99.9%(연 약 8.7시간 정지 허용)·99.99%(약 52분)
- 민간은 위약금 산정을 위해, 공공은 "이 업무가 몇 시간 멈춰도 되는가"를 업무 성격으로 정한다 — 재난 접수와 월간 통계를 한 등급으로 묶으면 예산도 설계도 어긋난다

#### 3-5. 요구사항은 검수 가능해야 한다
- 검수 불가: "실시간 처리를 지원할 것"
- 검수 가능: "지연 이벤트의 수용·폐기 규칙을 제시하고 폐기 건수를 지표로 노출할 것"
- 민간도 같은 문장 규율 — 데이터 신선도 SLA: "주문 이벤트는 발생 후 5초 이내에 처리 계층에 도달해야 한다"
- 문장 형태는 같고 **동기가 다르다**: 민간은 위약금, 공공은 감사 지적·인수 거부

**표 3.3** 공공 요구사항 → 설계 산출물

| 요구사항 | 설계 산출물 | 이 교재 실물 |
|---|---|---|
| 보안 | TLS, RBAC, 시크릿 분리 | 실습 3.1 경고 |
| 감사 | 라인리지, 변경 이력, 데이터 지문 | 9장 지문, 13장 감사표 |
| 개인정보 | 목적 포함 접근 정책, 마스킹 | 13장 거부 4건 |

### 4. 로컬 최소 구성과 선언적 구성
○ **최소 구성의 기준**: "이 장의 개념을 눈으로 확인할 수 있는가"
  - 3장에서 세우는 것: 수집(Kafka·Zookeeper), 저장(Postgres), 모니터링(Prometheus·Grafana)
  - 뒤로 미루는 것: 처리(Spark → 6장), 오케스트레이션(Airflow → 7장)
  - 생략이 아니라 범위 조정에 따른 설계 판단

○ **무엇을 남기고 무엇을 미룰지 — 세 질문**
  - ① 이 계층을 빼면 이 장에서 보여 주려는 것이 안 보이는가 (수집·저장·모니터링을 빼면 "계층이 나뉘어 있다"가 관찰되지 않음)
  - ② 이 계층이 없어도 뒤 실습이 막히지 않는가 (처리 계층은 6장에서 처음 필요 → 3~5장은 진행됨)
  - ③ 올렸을 때 드는 학습 부하가 그 계층에서 얻는 관찰보다 큰가 (Spark·Airflow는 설정 항목이 많아 이 장에서는 부하가 관찰을 넘어섬)
  - 뒤집으면 추가 시점도 정해진다 — **실습이 막히는 시점이 그 계층을 더할 시점**

○ **Docker란 무엇인가**
  - 애플리케이션과 실행에 필요한 파일·라이브러리·설정을 하나로 묶어 **컨테이너(container)**라는 격리된 실행 공간에서 돌리는 도구
  - 격리 = "컴퓨터 안의 또 다른 컴퓨터"가 아니라, 호스트 OS 자원을 함께 쓰면서 프로세스·네트워크·파일 공간만 구분하는 방식

| 용어 | 쉬운 뜻 | 비유 |
|---|---|---|
| 이미지(image) | 컨테이너를 만들 때 쓰는 읽기 전용 패키지 | 재료와 조리법이 든 포장 세트 |
| 컨테이너(container) | 이미지를 실제로 실행한 인스턴스 | 포장 세트로 만든 한 그릇의 음식 |
| Docker Engine | 이미지를 내려받고 컨테이너를 시작·중지하는 실행 프로그램 | 주방과 조리 도구 |

  - 실행 흐름: ① 레지스트리에서 이미지를 내려받거나(`pull`) Dockerfile로 직접 만든다 → ② 이미지에서 컨테이너를 만든다 → ③ 포트·환경변수·볼륨·네트워크를 연결해 실행한다 → ④ 작업이 끝나면 중지·삭제한다(보존할 데이터는 볼륨에 남긴다)
  - `docker run` = 컨테이너 하나를 실행하는 명령, `docker compose` = 여러 컨테이너와 그 연결 관계를 한 번에 관리하는 명령
  - Docker는 "내 컴퓨터에서는 되는데 다른 컴퓨터에서는 안 되는" 문제를 줄여 주지만, 호스트의 CPU·메모리·포트, 이미지 버전, 비밀값 설정까지 대신 정해 주지는 않는다

○ **선언적 구성(Docker Compose)**
  - "무엇이 있어야 하는가"의 최종 상태를 기술 → 구성 자체가 문서이자 실행 가능한 설계도
  - 공공 검수에서 중요: 발주자가 같은 파일로 재현해 확인 가능

○ **비용 원칙**: 측정한 뒤에 증설한다
  - "5배 증설 = 5배 처리"는 직관일 뿐 → 실측(12장)에서 확인해야 함
  - 비용은 계층별로 나눠 봐야 새는 곳이 보인다 — 수집·저장·처리·서빙 분리 추적, 저장 안에서는 핫·웜·콜드 비율
  - 공공에서 쓸모: 예산 항목과 대응시킬 수 있다 — "저장 비용이 늘었다"보다 "보관 기간을 늘린 만큼 콜드 저장 비용이 얼마 늘었다"가 증액 근거로 통한다

#### 역방향 — 이 장의 아키텍처를 민간 현장으로

○ **실시간 추천 시스템** — Lambda가 그대로 재현되는 현장
  - 스피드 레이어: 클릭·구매 실시간 집계로 추천 피처 갱신 / 배치 레이어: 전일 전체 로그 재처리로 모델 재학습·오프라인 피처 확정
  - 로직 이중화 부채도 그대로 — "최근 7일 구매 횟수"의 창(window) 경계 처리가 두 코드에서 어긋나면 추천 품질 하락
  - 공공 대시보드의 확정치·근사치 불일치와 같은 실패. 다른 것은 드러나는 방식 — 공공은 감사가, 민간은 지표 하락이 잡는다

○ **광고 플랫폼** — 리플레이의 쓰임이 바뀌는 현장
  - 실시간 대시보드는 근사치, 자정 이후 재집계는 확정 과금액
  - 감사 대응 능력이던 리플레이가 여기서는 **과금 분쟁 해결 수단** — "그 시간대 노출 수가 맞는가"에 되감아 재집계한 결과로 답한다
  - 요구하는 사람이 감사관에서 거래 상대로 바뀔 뿐, 아키텍처에 요구되는 성질(원천 로그 보존·같은 코드 재생)은 같다

○ **이커머스** — 이벤트 기반 + 멀티테넌시가 함께 쓰이는 현장
  - "주문 접수" 이벤트를 재고·결제·알림이 각자 구독, 한 서비스 장애가 번지지 않게 격리
  - 마켓플레이스의 판매자별 데이터 격리 = 멀티테넌시의 실물(판매자 A 매출이 B에게 보이면 계약 위반)
  - 골든 시그널 4가지가 SRE(사이트 신뢰성 엔지니어링) 대시보드의 기본 구성

○ **관통하는 하나** — 이 장의 핵심 결정 네 가지(재처리를 이중화로 감당할지 리플레이로 감당할지 / 계층을 어디까지 나눌지 / 어느 계층을 미룰지 / 비밀과 구성을 어디에 둘지)는 도메인과 무관하게 똑같이 내린다. **근거만 도메인이 바꾼다**(공공: 감사 재현·형평성·법적 의무 / 민간: 매출·비용·SLA)

○ **방향은 비대칭** — 민간→공공은 증거 산출 의무가 한 겹 얹히지만, 공공→민간은 그 겹을 벗겨도 손해가 없다(감사용 리플레이 → 분쟁 증거, 재현 가능한 구성 파일 → 배포 신뢰도)

### 실습 3.1: Docker Compose 기반 파이프라인 구성 분석

**진행 순서: 설계 → 실행 → 대조 → 관찰·검수**

남이 만든 compose 파일을 먼저 열면 거기 적힌 서비스 목록이 정답처럼 보이고 "왜 이 여섯 개인가"를 묻지 않게 된다. 파일을 열기 전에 5계층 모델에서 필요한 서비스를 먼저 적고, 그다음 실제 파일과 맞춰 본다.

#### 실행 결과 확인 사항

1. **서비스 목록**: zookeeper, kafka, postgres, prometheus, grafana, kafka-ui (6개)
2. **호스트 포트**: 2181, 3000, 5432, 8080, 9090, 9092, 29092 (7개)
3. **의존성**: grafana → prometheus, kafka-ui → kafka
4. **보안 경고**: postgres·grafana의 평문 패스워드 (2건)

#### 3단계 대조 — 예측과 산출물 맞춰 보기

예측표의 "실제" 줄을 채운다 — 서비스 6개, 호스트 포트 7개, 추출된 의존성 2개.

○ **예측한 서비스 수가 실제(6개)보다 적었다면** — 계층 하나를 서비스 하나로 셈했기 때문이다. 수집에 kafka·zookeeper 둘, 모니터링에 prometheus·grafana·kafka-ui 셋. 계층과 서비스는 1대 1이 아니다
○ **처리·서빙을 "예"로 적었다면** — 실제 구성에는 그 자리가 비어 있다. 처리(Spark)·오케스트레이션(Airflow)은 6·7장, 서빙 API는 10장에서 붙는다. 요구사항 셋째 줄이 그 판단의 근거였다
○ **포트가 서비스보다 하나 많은 이유** — kafka가 9092·29092 둘을 연다(9092 = 호스트 접속용 `PLAINTEXT_HOST`, 29092 = 컨테이너 사이 `PLAINTEXT`). "서비스 하나에 포트 하나"라는 예측은 여기서 깨진다
○ **의존성을 3으로 예측했다면 그 예측이 맞다** — 파일에는 `kafka → zookeeper`, `grafana → prometheus`, `kafka-ui → kafka` 셋이 있는데 산출물에는 둘뿐이다. 어긋난 것은 설계가 아니라 **도구**다(관찰 2)

→ 예측과 산출물이 어긋났을 때 자기 판단을 고칠지 도구를 고칠지는 원본과 대조해야 정해진다. 설계를 먼저 적지 않으면 "의존성 2개"를 그대로 받아 적고 넘어가게 된다.

#### 관찰 과제
○ **관찰 1**: 보안 경고가 무엇을 가리키는가?
  - 값이 복잡한지가 아니라 **비밀번호가 파일에 평문으로 들어 있다는 사실**을 경고하는 것
  - `POSTGRES_PASSWORD=secure_password`도 경고 — 값이 그럴듯해도 파일에 평문이면 위험
  - 12-factor config 원칙의 실물: 운영에서는 환경변수·시크릿 저장소로 분리

○ **관찰 2**: 도구가 보여주는 것 vs 실제
  - 추출된 의존성 2개 vs 실제 compose 파일의 의존성(kafka → zookeeper 누락)
  - 원인: `depends_on`을 map-form(헬스체크 조건)으로 쓴 서비스는 간단한 파서가 못 잡음
  - 교훈: **도구의 출력은 원본과 대조되어야 하며, 이 대조 자체가 검수 절차의 일부**

#### 확장 과제 (선택)

1. compose 파일에 워커(worker) 서비스 1개를 추가하고 재추출 → 서비스·포트가 어떻게 변하는지 확인
2. `depends_on`을 map-form으로 바꾼 서비스를 파서가 포착하도록 코드 보강
3. 호스트 포트를 일부러 중복시켜 충돌을 만들고, 사전 점검이 이를 잡는지 확인
