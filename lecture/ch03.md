### 1. 배치·스트리밍·하이브리드 아키텍처 (20분)

#### 1-1. 세 가지 처리 방식

○ **배치(batch)**
  - 데이터를 일정 기간 모았다가 한꺼번에 처리
  - 강점: 정확성, 재현성 — 늦게 도착한 이벤트까지 포함해 확정치를 낼 수 있음
  - 약점: 지연 — "지금 무슨 일이 벌어지는가"에 답할 수 없음
  - 예: 월간·분기 통계 보고

○ **스트리밍(streaming)**
  - 이벤트가 도착하는 즉시 처리
  - 강점: 즉시성 — 재난 신고 건수를 초 단위로 갱신 가능
  - 약점: 정확한 집계 부담 — 지연 이벤트(발생 23:58, 도착 00:03)를 어떻게 처리할지의 문제
  - 예: 재난 상황실 실시간 현황판

○ **하이브리드(hybrid)**
  - 배치 + 스트리밍을 결합 → "빠른 근사치 + 정확한 확정치" 동시 제공
  - 공공 업무의 이중성에서 필요: 실시간 대응(스트리밍) + 사후 감사·통계(배치)
  - 두 가지 설계 방식: Lambda와 Kappa

#### 1-2. Lambda 아키텍처

○ 구조
  - **배치 레이어**: 원천 데이터 전체를 주기적으로 재계산 → 확정치
  - **스피드 레이어**: 도착 즉시 실시간 처리 → 근사치
  - 조회 시 둘을 합침: "확정된 과거 + 근사한 최근"

○ 장점
  - 정확한 확정치와 빠른 근사치를 동시에 얻음

○ 약점 — 로직 이중화 부채
  - 같은 집계 로직을 **두 벌**(배치용 + 스트리밍용)로 유지해야 함
  - 하나만 수정하고 다른 쪽을 빠뜨리면 → 확정치와 근사치가 어긋남(침묵 실패)
  - 1장의 CACE 원칙(Changing Anything Changes Everything)과 직결

○ 이 교재에서의 실물
  - 스피드 레이어 → 6장 스트리밍 실습
  - 배치 레이어 → 7장 배치 정제 실습

#### 1-3. Kappa 아키텍처

○ 구조
  - 배치 레이어를 두지 않고 **스트리밍 단일 레이어**만 유지
  - 재처리가 필요하면 과거 이벤트를 처음부터 다시 흘려보냄(리플레이, replay)
  - 로직이 한 벌 → 배치·스트리밍 불일치가 구조적으로 사라짐

○ 전제 조건
  - 이벤트 로그의 보존과 재생 가능성 (예: Kafka 오프셋)

○ 한계
  - 대규모 과거 데이터 재생은 배치 스캔보다 비효율적일 수 있음
  - 복잡한 다차원 집계·대규모 조인은 배치 엔진이 유리

○ Lambda vs Kappa: 기술 우열이 아니라 **선택**
  - 로직 이중화 부채를 감수할 것인가 vs 리플레이 비용을 감수할 것인가

#### 1-4. 리플레이와 감사

○ 민간에서 리플레이: 버그 수정·로직 개선을 위한 재계산
○ **공공에서 리플레이**: 감사 대응 능력
  - 감사관: "왜 이 통계가 이렇게 나왔는가?"
  - 답: "그 시점에 들어온 그 데이터로 그 계산을 다시 만들어낼 수 있는가"
  - 로그 보존 + 오프셋으로 되감아 재생할 수 있는 아키텍처 → "재현해 보이겠습니다"
  - 요약본만 남긴 아키텍처 → 답할 수 없음

**표 3.1** 배치·스트리밍·하이브리드 비교

| 항목 | 배치 | 스트리밍 | Lambda | Kappa |
|---|---|---|---|---|
| 처리 시점 | 주기적 일괄 | 도착 즉시 | 배치+스피드 병렬 | 스트리밍 단일 |
| 지연 | 큼(분·시간) | 작음(초 이하) | 확정 크고 근사 작음 | 작음 |
| 재처리 | 배치 재실행 | 별도 설계 필요 | 배치 레이어 담당 | 로그 리플레이 |
| 로직 관리 | 한 벌 | 한 벌 | **두 벌(부채)** | 한 벌 |
| 공공 적용 | 정기 보고 | 재난·교통 실시간 | 대응+보고 동시 | 재처리·감사 |

### 2. 파이프라인 5계층 (15분)

#### 핵심 원칙
- 계층은 제품 이름의 나열이 아니라 **"없으면 무엇이 깨지는가"**로 이해하는 역할 분해

#### 2-1. 수집 계층
- **역할**: 생산과 소비의 속도 차이를 흡수, 완충 로그를 두어 "빠르게 받고 천천히 처리"
- **없으면**: 속도 차이가 곧 장애(요청 거부, 데이터 유실)
- **대표 도구**: Kafka — 오프셋이 매겨진 로그로 보관, 컨슈머가 자기 속도로 읽고 되감기 가능
- **실측(4장)**: 커밋 시점 한 줄만 바꾸면 at-most-once는 20건 유실, at-least-once는 10건 중복

#### 2-2. 저장 계층
- **역할**: 원천 데이터·가공 데이터 보존 + 접근 통제
- **없으면**: 재처리 불가, 감사 대응 불가, 새 요구 대응 불가
- **현장 방법**: 계층형 저장(핫/웜/콜드) — 예산과 접근 빈도에 따라 분배
- **최신 개념**: 레이크하우스 — 레이크(원천 보관) + 웨어하우스(정형 분석)를 한 계층으로 통합

#### 2-3. 처리 계층
- **역할**: 수집된 데이터를 스트리밍 또는 배치로 변환·집계
- **없으면**: 원천 이벤트가 그대로는 의미 있는 지표가 되지 못함
- **핵심 문제**: 지연 이벤트 — watermark로 "얼마나 기다렸다 창을 닫을지" 결정
- **실측**: 6장(스트리밍 watermark), 7장(배치 정제 — 총계 보존식 검증)

#### 2-4. 서빙 계층
- **역할**: 조회·리포팅·ML 예측 요구에 데이터를 통제된 성능으로 제공
- **없으면**: 데이터가 있어도 서비스가 안 됨
- **핵심 질문**: "새 모델을 어떻게 넣는가"보다 **"잘못됐을 때 어떻게 되돌리는가"**
- **공공 전략**: 섀도 배포 — 이용자에게는 기존 모델, 로그에는 후보 모델 예측을 조용히 적재
- **실측(10장)**: champion 예측 6.0 vs challenger 예측 7.3636

#### 2-5. 모니터링 계층
- **역할**: 메트릭·대시보드로 시스템·모델의 상태를 관측 가능하게 함
- **없으면**: 침묵 실패가 발견되지 않음
- **골든 시그널(Google SRE)**: 지연, 트래픽, 오류, 포화
- **대표 도구**: Prometheus(수집) + Grafana(시각화)
- **실측**: 11장(PSI 0.3324 — 단일 지표로 판단하면 안 되는 사례), 12장(CPU 106.3% 포화)

**표 3.2** 5계층 요약

| 계층 | 없으면 깨지는 것 | 대표 도구 | 이 교재 실측 |
|---|---|---|---|
| 수집 | 유실·과부하 | Kafka | 4장 |
| 저장 | 재처리·감사 불가 | Postgres | 5장, 13장 |
| 처리 | 의미 없는 원천 | Spark, Airflow | 6장, 7장 |
| 서빙 | 서비스 불가 | FastAPI | 10장 |
| 모니터링 | 침묵 실패 미발견 | Prometheus, Grafana | 11장 |

### 3. 공공 요구사항 → 설계 산출물 (10분)

#### 3-1. 보안: 원칙이 아니라 설정으로
- TLS 전송 암호화, 저장 암호화, RBAC(역할 기반 접근 제어), 네트워크 분리
- **12-factor App 원칙**: 비밀은 코드·구성 파일이 아니라 환경(환경변수·시크릿 저장소)에 둔다
- 이유: 파일에 있으면 버전 관리 저장소에 커밋돼 노출, 회수 어려움

#### 3-2. 감사: 재현할 수 없으면 증거가 아니다
- 접근 로그, 변경 이력, 라인리지(데이터→피처→모델→결과 추적), 보관 정책
- 핵심: 증거를 사람이 사후에 쓰는 문서가 아니라 **시스템이 실행 중에 만드는 산출물**로 둠
- 실측(13장): 허용 8건·거부 4건의 접근 판정 → 감사 점검표 10항목 자동 생성

#### 3-3. 개인정보: 조문이 설계를 결정한다
- 제18조(목적 외 이용·제공 제한): 접근 정책에 "무슨 목적으로"가 들어가야 함
- 제23조(민감정보 처리 제한): 건강 등 민감정보 한정 — 일반 개인정보에 확대 적용 금지
- 제33조(영향평가): 개인 단위 데이터 시스템은 파이프라인 이전에 영향평가 선행
- 제37조의2(자동화된 결정에 대한 권리, 2024년 3월 시행): 이의 제기 창구·설명 절차 필수

#### 3-4. 장애 대응: 고장을 내 봐야 확인된다
- 재시도·멱등 처리, 이중화, 백업·복구(DR)
- "비기능 요구는 고장을 일부러 내 보기 전에는 확인되지 않는다"
- 실측(14장): 오염 이벤트 격리, 중복 재전송 흡수, 부분 실패 격리 — 3종 드릴

#### 3-5. 요구사항은 검수 가능해야 한다
- 검수 불가: "실시간 처리를 지원할 것"
- 검수 가능: "지연 이벤트의 수용·폐기 규칙을 제시하고 폐기 건수를 지표로 노출할 것"

**표 3.3** 공공 요구사항 → 설계 산출물

| 요구사항 | 설계 산출물 | 이 교재 실물 |
|---|---|---|
| 보안 | TLS, RBAC, 시크릿 분리 | 실습 3.1 경고 |
| 감사 | 라인리지, 변경 이력, 데이터 지문 | 9장 지문, 13장 감사표 |
| 개인정보 | 목적 포함 접근 정책, 마스킹 | 13장 거부 4건 |
| 장애 대응 | 재시도·멱등키, 격리 큐 | 14장 드릴 3종 |
| 검수 가능성 | 검수표, 수치 임계, 드릴 시나리오 | 14장 검수표 16항목 |

### 4. 로컬 최소 구성과 선언적 구성 (5분)

○ **최소 구성의 기준**: "이 장의 개념을 눈으로 확인할 수 있는가"
  - 3장에서 세우는 것: 수집(Kafka·Zookeeper), 저장(Postgres), 모니터링(Prometheus·Grafana)
  - 뒤로 미루는 것: 처리(Spark → 6장), 오케스트레이션(Airflow → 7장)
  - 생략이 아니라 범위 조정에 따른 설계 판단

○ **선언적 구성(Docker Compose)**
  - "무엇이 있어야 하는가"의 최종 상태를 기술 → 구성 자체가 문서이자 실행 가능한 설계도
  - 공공 검수에서 중요: 발주자가 같은 파일로 재현해 확인 가능

○ **비용 원칙**: 측정한 뒤에 증설한다
  - "5배 증설 = 5배 처리"는 직관일 뿐 → 실측(12장)에서 확인해야 함

### 실습 3.1: Docker Compose 기반 파이프라인 구성 분석

#### 실습 목표
- `docker-compose.yml`에서 서비스·포트·의존성을 추출해 "구성 계획"을 산출물로 만든다
- 기본 보안 점검(약한 기본 패스워드 등)을 산출물로 남기고, 그 한계까지 관찰한다

#### 실행 환경
- Python 3.10+, PyYAML 설치
- Docker Desktop 설치 (compose 파일 파싱만 하므로 Docker 실행은 불필요)

#### 실행 명령

```bash
cd practice/chapter3
python3 code/3-1-compose-plan.py
```

#### 핵심 코드

```python
data = yaml.safe_load(COMPOSE_PATH.read_text(encoding="utf-8"))
services = data.get("services", {})
OUTPUT_PATH.write_text(json.dumps(plan, ensure_ascii=False, indent=2) + "\n")
```

_전체 코드는 practice/chapter3/code/3-1-compose-plan.py 참고_

#### 실행 결과 확인 사항

1. **서비스 목록**: zookeeper, kafka, postgres, prometheus, grafana, kafka-ui (6개)
2. **호스트 포트**: 2181, 3000, 5432, 8080, 9090, 9092, 29092 (7개)
3. **의존성**: grafana → prometheus, kafka-ui → kafka
4. **보안 경고**: postgres·grafana의 평문 패스워드 (2건)

#### 관찰 과제

○ **관찰 1**: 보안 경고가 무엇을 짚는가?
  - 값이 복잡한지가 아니라 **비밀번호가 파일에 평문으로 들어 있다는 사실**을 경고하는 것
  - `POSTGRES_PASSWORD=secure_password`도 경고 — 값이 그럴듯해도 파일에 평문이면 위험
  - 12-factor config 원칙의 실물: 운영에서는 환경변수·시크릿 저장소로 분리

○ **관찰 2**: 도구가 보여주는 것 vs 실제
  - 추출된 의존성 2개 vs 실제 compose 파일의 의존성(kafka → zookeeper 누락)
  - 원인: `depends_on`을 map-form(헬스체크 조건)으로 쓴 서비스는 간단한 파서가 못 잡음
  - 교훈: **도구의 출력은 원본과 대조되어야 하며, 이 대조 자체가 검수 절차의 일부**

#### 확장 과제 (선택)

1. compose 파일에 워커 서비스 1개를 추가하고 재추출 → 서비스·포트가 어떻게 변하는지 확인
2. `depends_on`을 map-form으로 바꾼 서비스를 파서가 포착하도록 코드 보강
3. 호스트 포트를 일부러 중복시켜 충돌을 만들고, 사전 점검이 이를 잡는지 확인

## 비즈니스 적용 노트

> 이 장의 기법이 민간 비즈니스에서 어떤 지표·목표·도구로 쓰이는지 정리한다.

### 공공 → 비즈니스 대응표

| 공공 맥락 | 비즈니스 맥락 | 차이점 |
|---|---|---|
| 배치(정기 통계 보고) + 스트리밍(재난 실시간 대응) 하이브리드 | 배치(일별 정산·리포팅) + 스트리밍(실시간 추천·광고 입찰) 하이브리드 | 공공은 감사 재현이 하이브리드 선택의 핵심 요인이고, 비즈니스는 비용 최적화와 SLA(서비스 수준 합의) 충족이 핵심 요인이다 |
| Lambda 아키텍처(배치+스피드 레이어) | Lambda 아키텍처(일별 정산 배치 + 실시간 근사 집계) | 로직 이중화 부채는 동일하다. 비즈니스에서는 dbt(배치)와 Flink(스트리밍) 두 벌 유지의 인건비가 대표적 비용이다 |
| Kappa 아키텍처(리플레이 기반 재처리 + 감사 재현) | Kappa 아키텍처(이벤트 소싱 + 로그 리플레이 재처리) | 비즈니스에서 Kappa는 이벤트 소싱(event sourcing) 패턴과 결합해 주문 상태 추적·결제 이력 재구성에 쓰인다 |
| 5계층(수집·저장·처리·서빙·모니터링) | 동일 5계층 + 비용 계층(클라우드 비용 추적) | 비즈니스에서는 각 계층의 클라우드 비용이 설계 결정의 주요 제약이다 |
| 보안·감사·개인정보·장애 대응 | 보안·컴플라이언스·개인정보(GDPR/CCPA)·SLA 보장 | 공공은 감사관 대응이, 비즈니스는 고객 SLA 위반 시 위약금이 설계 산출물의 동기다 |
| 멀티테넌시(기관·지자체 데이터 격리) | 멀티테넌시(고객사 데이터 격리) | 공공은 법적 격리(개인정보보호법 제18조), 비즈니스는 계약 격리(SLA·NDA(비밀유지계약))다 |

### 비즈니스에서의 핵심 지표

○ **아키텍처 선택 기준 지표**
  - 종단 지연(end-to-end latency): 이벤트 발생부터 서빙까지 걸리는 시간. 실시간 추천은 100ms 이하, 광고 입찰은 10ms 이하를 목표로 잡는다
  - 재처리 소요 시간: Lambda는 배치 재실행 시간, Kappa는 로그 리플레이 시간으로 측정한다
  - 로직 동기화율: Lambda에서 배치 코드와 스트리밍 코드가 같은 결과를 내는지 검증한 비율

○ **파이프라인 운영 비용 지표**
  - 계층별 클라우드 비용: 수집·저장·처리·서빙을 분리 추적한다
  - 비용 대비 처리량(cost per event): 이벤트 1건을 수집-처리-서빙하는 데 드는 비용
  - 저장 계층 비용 최적화: 핫·웜·콜드 비율을 추적해 불필요한 핫 저장 비용을 줄인다

○ **SLA 준수 지표**
  - 가용성(uptime): 99.9%~99.99%를 서비스 등급에 따라 설정한다
  - 데이터 신선도 SLA: 이벤트 발생 후 처리 계층 도달까지의 목표 시간
  - 복구 시간 목표(RTO, Recovery Time Objective): 장애 발생 후 서비스 복구까지의 목표 시간

### 실무 적용 사례

○ **실시간 추천 시스템의 Lambda 적용**
  - 스피드 레이어: 사용자 클릭·구매를 실시간 집계해 추천 피처를 갱신한다
  - 배치 레이어: 전일 전체 로그를 재처리해 협업 필터링 모델을 재학습하고 오프라인 피처를 확정한다
  - 로직 이중화 부채가 실제 문제다. 스트리밍과 배치에서 같은 피처의 창(window) 경계 처리가 어긋나면 추천 품질이 하락한다

○ **광고 플랫폼의 실시간 집계와 일별 정산**
  - 실시간 대시보드는 근사치, 자정 이후 배치 재집계는 확정치다. 정산 오차율을 지표로 추적한다
  - 리플레이로 과금 분쟁을 해결한다. 로그를 되감아 재집계한 결과를 증거로 제시한다

○ **이커머스 이벤트 기반 아키텍처**
  - 주문 이벤트를 재고·결제·알림 서비스가 각자 구독해 처리한다. 한 서비스 장애가 다른 서비스로 번지지 않는 격리가 핵심이다
  - 골든 시그널(지연·트래픽·오류·포화) 4가지가 SRE(사이트 신뢰성 엔지니어링) 대시보드의 기본 구성이다
