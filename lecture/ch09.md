### 1. 실험 재현성의 의미 (15분)

#### 1-1. "답할 수 없는 상태"가 기본값이다

○ **재현성 문제의 출발점**
  - 석 달 전 배포한 모델의 성능이 떨어졌을 때 "그때 모델을 다시 만들자"가 첫 수
  - 다시 만들려면 네 가지를 알아야 한다 — 어느 데이터, 어느 피처, 어느 파라미터, 어느 코드
  - 아무것도 기록하지 않았으면 "다시 만든 모델"은 재현이 아니라 **새 모델** → 비교 실험 자체가 성립하지 않음

○ **기록이 없는 이유는 게으름이 아니다**
  - 실험은 하루에 파라미터를 다섯 번 바꾸고, 데이터를 두 번 갈아끼우는 것이 정상
  - "나중에 정리해야지"는 반드시 실패
  - 기록은 실험 **후**의 문서화가 아니라 실험 **중**의 자동 기록이어야 함

#### 1-2. 훈련도 함수다 — 7장 재현성의 확장

○ **모델 = f(코드, 데이터, 파라미터, 환경)**
  - 7장: 같은 입력 파일 → 같은 산출물(해시 동일)
  - 9장: 같은 설정 → 같은 모델(메트릭·계수 동일)
  - 난수를 쓰는 알고리즘이면 seed도 입력에 포함해 고정해야 함수가 됨

**표 9.1** 재현 4요소와 기록 수단

| 요소 | 재현 실패의 전형 | 실습의 기록 수단 |
|---|---|---|
| 코드 | 훈련 스크립트가 수정됨 | 버전 관리(git) |
| 데이터 | 원천이 정정·추가로 변함 | **데이터 지문**(sha256)을 파라미터로 기록 |
| 파라미터 | "그때 뭘 줬더라" | run에 `log_params`로 자동 기록 |
| 환경 | 라이브러리 버전 차이 | 모델과 함께 의존성 기록(MLflow가 동봉) |

#### 1-3. 재현 실패의 원인 분리 절차

○ 두 run을 나란히 놓고 요소별로 대조한다 — **값싼 대조부터, 비싼 대조는 나중에**
  1. **파라미터 대조**: 기록된 파라미터를 필드별 비교 → 다르면 종결
  2. **데이터 지문 대조**: 파라미터가 같아도 `data_sha256_16`이 다르면 데이터가 바뀐 것
  3. **환경 대조**: 라이브러리 버전(의존성 기록) 비교 → 부동소수점 수준 차이 가능
  4. **난수 확인**: 셋 다 같은데 다르면 seed 미고정이 원인

○ 절차 전체가 성립하려면 1~2단계의 기록이 **훈련 시점에** 이미 남아 있어야 함

#### 1-4. 정직한 반대 논거 — 언제 과한가

○ 탐색 초기·버릴 것이 뻔한 스케치 실험까지 전부 남기면 **소음 비용**이 문제
  - run 수백 개 속에서 의미 있는 것을 못 찾으면 기록이 없는 것과 같음
○ 현실적인 선: 기록 자체는 자동이므로 켜 두되, 의미 있는 run에 태그·이름을 붙여 구분
  - "모든 run을 기록"(실험의 안전망) ≠ "선별된 후보만 등록"(운영의 관문)

#### 1-5. 공공 맥락

○ 정보공개 청구·감사에서 "이 모델의 판단 근거를 소명하라"는 요구가 올 수 있음
  - 모델 파일만 있으면 "어떻게 만들어졌는가"에 답할 수 없음
  - 실험 기록이 있으면 run을 열어 데이터 지문·파라미터·성능 지표·훈련 일시를 제시
  - 재현성은 연구자의 결벽이 아니라 **책임 소재의 전제 조건**

### 2. 파라미터, 메트릭, 아티팩트 기록 (15분)

#### 2-1. run의 세 기록 항목

○ **run**: 훈련 한 번의 기록 단위. experiment(실험)는 run들을 묶는 폴더

○ **파라미터(params)** — 훈련의 입력 설정
  - 모델 종류, 하이퍼파라미터, 데이터 지문(`data_sha256_16`), 표본 수
  - "무엇을 넣었나"

○ **메트릭(metrics)** — 훈련의 결과 수치
  - 실습은 훈련 MAE(Mean Absolute Error, 평균 절대 오차)
  - "무엇이 나왔나"

○ **아티팩트(artifacts)** — 결과 파일
  - 모델 자체, 훈련 데이터 사본, 그림 등 수치로 환원되지 않는 실물
  - "무엇이 만들어졌나"

○ **구분이 중요한 이유**: 질의 방식이 다르다
  - "학습률 0.01인 run 전부" → 파라미터 검색
  - "MAE 최소 run" → 메트릭 정렬
  - "그 run의 훈련 데이터를 열어 보자" → 아티팩트 다운로드

#### 2-2. 실측: 후보 2개의 기록

○ 훈련 데이터: 8장 피처 원천(9행 = 3지역 × 3일)에서 만든 **(전일 건수 → 당일 건수) 쌍 6개**
  - 강남(11680): 8→6, 6→9 / 마포(11440): 5→5, 5→6 / 관악(11620): 5→5, 5→5

**표 9.2** 후보별 기록(실제 실행, MLflow 3.14.0)

| 기록 항목 | 후보 1: baseline_mean | 후보 2: linear |
|---|---|---|
| 파라미터(모델) | DummyRegressor, strategy=mean | LinearRegression, fit_intercept=True |
| 파라미터(데이터) | n_samples=6, data_sha256_16=96f6b6b3ce9dcdd1 | 동일(같은 데이터) |
| 메트릭 train_mae | **1.0000** | **1.0455** |
| 학습된 계수 | (평균 6.0) | slope **0.4091**, intercept **3.6818** |
| 아티팩트 | 훈련 CSV, 모델 | 훈련 CSV, 모델 |

○ **손 검산**
  - 베이스라인: y 평균 = (6+9+5+6+5+5)/6 = 36/6 = **6.0**, 잔차 합 6 ÷ 6 = MAE **1.0**
  - 선형회귀: 최소제곱으로 slope = 9/22 = **0.4091**, intercept = 81/22 = **3.6818**
  - **더 복잡한 모델이 졌다**(1.0455 > 1.0000) — 6쌍으로는 유의미한 기울기를 배울 수 없음

#### 2-3. 재현성 실측

○ 선형회귀 후보를 같은 데이터(지문 동일)·같은 파라미터로 재훈련
  - train_mae 1.0455 = 1.0455, 계수 동일 → `mae_equal=true`, `coef_equal=true`
  - 7장 "재실행 해시 동일"의 모델판
  - 역으로 읽으면 **회귀 검사**: 아무것도 안 바꿨는데 메트릭이 달라졌으면 입력이 몰래 바뀐 것

#### 2-4. 데이터 지문의 이중 기록

○ 훈련 데이터를 **아티팩트**(CSV 사본)로도, **파라미터**(sha256 지문)로도 기록
  - 지문: 가볍고 비교 가능 → "같은 데이터였나"의 즉답
  - 사본: 무겁지만 실물 → "그 데이터를 다시 보자"
  - 중복이 아니라 용도 분리

#### 2-5. 정직한 표기

○ 이 실습의 MAE는 **훈련 데이터 위의 훈련 오차**
  - 6쌍을 훈련/평가로 쪼개는 것은 무의미하므로 분리하지 않음
  - 실무라면 승격 판정의 근거는 **보류(holdout) 데이터의 평가 지표**여야 함
  - 관찰 대상은 모델 품질이 아니라 기록·등록 메커니즘

### 3. 모델 레지스트리 단계와 승인 흐름 (15분)

#### 3-1. 실험실과 관문은 다른 장소다

○ run은 수십·수백 개가 쌓이는 것이 정상 — 서빙 시스템에 "알아서 좋은 걸 골라라"고 할 수 없음
○ **모델 레지스트리**: 배포 후보를 이름·버전으로 관리하는 관문
  - run이 실험 노트라면, 레지스트리는 제품의 출고 대장
  - 같은 이름 아래 v1, v2, v3가 쌓이고 각 버전은 자기를 만든 run을 가리킴

#### 3-2. 별칭(alias) — 현행 방식

○ MLflow 현행: stage API 대신 **별칭(alias)** 사용
  - 버전에 champion 같은 가변 이름표를 붙임
  - 소비자는 `models:/이름@champion`으로 로드 → 버전 번호를 몰라도 됨
  - 별칭을 v1에서 v2로 옮기면 운영 모델이 교체되고, 소비자 코드는 안 바뀜

**표 9.3a** 단계 개념과 별칭 구현의 대응

| 단계 개념(전통) | 뜻 | 별칭 방식(현행) |
|---|---|---|
| 개발(None) | 등록만 된 후보 | 별칭 없는 버전 |
| 검증(Staging) | 운영 투입 전 평가 중 | challenger 별칭을 관례로 부여 |
| 운영(Production) | 서빙이 소비 중 | **champion 별칭** — 소비자가 이것만 바라봄 |
| 폐기(Archived) | 더는 후보 아님 | 별칭 제거(기록 자체는 남음) |

#### 3-3. 승격 게이트 실측

○ 등록 모델: `complaint_daily_forecaster`
○ 승격 규칙: ① 절대 게이트 — train_mae ≤ 1.05, ② 상대 조건 — 기존 champion보다 개선

**표 9.3** 레지스트리 실측(등록·게이트·별칭)

| 버전 | 후보 | train_mae | 게이트(≤1.05) | champion 대비 | 판정 |
|---|---|---|---|---|---|
| v1 | baseline_mean | 1.0000 | 통과 | (최초) | **champion 별칭 부여(승격)** |
| v2 | linear | 1.0455 | 통과 | 1.0455 > 1.0000, 개선 없음 | **승격 반려** — 등록은 유지 |

○ v2의 교훈
  - 게이트는 통과했지만 상대 조건에서 탈락 → "절대 기준 통과"와 "교체 가치"는 다른 판단
  - 반려된 v2는 삭제되지 않고 **버전으로 남음** → 감사 기록("시도했고, 이 수치로 반려됨")

#### 3-4. 별칭의 다른 얼굴 — 롤백

○ 별칭 이동이 승격이면, 역방향이 **롤백**
  - v2를 champion으로 올렸다가 문제 발생 → 별칭을 v1으로 되돌리면 서빙 복귀
  - 소비자 코드는 이번에도 바뀌지 않음
○ 롤백의 전제 두 가지: 반려·교체된 버전을 지우지 않고 보존, 각 버전이 run과 연결

#### 3-5. 실제로 겪은 오류 — 등록 경로는 반환값에서 받아라

○ `runs:/<run_id>/model`로 문자열 경로를 조립해 등록 → 등록은 성공, 별칭 로드 시 예외 발생
  - `Could not find an 'MLmodel' configuration file`
  - MLflow 3의 저장 위치가 관례 경로와 달라졌기 때문
○ 수정: `log_model` 반환값(`model_info.model_uri`)을 등록에 넘김
○ 교훈: 등록(쓰기) 성공 ≠ 로드(읽기) 성공 → **별칭 로드·예측까지가 등록 검증**

### 4. 공공 모델 운영 메타데이터 (5분)

#### 4-1. 감사는 성능표가 아니라 책임표를 요구한다

○ 기술 조직의 기록: "어떻게 만들었고 얼마나 좋은가"
○ 공공 감사가 추가로 묻는 것: **누가** 만들었고, **무슨 목적**으로, **어느 기간의 어떤 출처** 데이터로, **어떤 제한** 아래 쓰이는가
○ 소급 작성이 사실상 불가능(담당자 이동·기억 소실) → 훈련 시점에 run 태그로 함께 기록

#### 4-2. 승격 검수 기록

**표 9.4** 모델 승격 검수 기록 양식(실습 자동 생성, 실측 값)

| 항목 | 실측 값 | 왜 필요한가 |
|---|---|---|
| 모델 이름 / champion | complaint_daily_forecaster / v1 | "지금 운영 중인 것"의 정본 답 |
| 승격 규칙 | train_mae ≤ 1.05 + champion 대비 개선 | 판정 기준의 사전 명시 |
| 판정 이력 | v1 승격(1.0000), v2 반려(1.0455) | 반려 포함 전체 이력 |
| 재현성 확인 | 재실행 메트릭·계수 동일(true) | "우연히 좋은 run" 승격 방지 |
| 데이터 지문 | 96f6b6b3ce9dcdd1… (sha256) | 훈련 데이터의 증명 가능한 동일성 |
| 검수자 | 검수 담당(가상) | 승인 행위의 주체 |
| 제한 사항 | 6쌍 극소 데이터 — 메커니즘 관찰용 | 모델의 유효 범위 명시 |

#### 4-3. 모델 등록 체크리스트

- [ ] run에 파라미터·메트릭·아티팩트가 완결 기록되어 있는가 — 특히 **데이터 지문**
- [ ] 운영 메타데이터 태그(소유·목적·출처·기간)가 있는가
- [ ] 같은 설정 재실행으로 재현성이 확인되었는가
- [ ] 승격 규칙(절대 게이트 + 상대 조건)이 사전에 문서화되어 있는가
- [ ] 등록 후 **별칭 로드·예측까지** 검증했는가
- [ ] 승격 검수 기록이 생성·보존되는가

### 실습 9.1: MLflow 실험 기록과 모델 등록

#### 실습 목표
- 8장 피처를 입력으로 후보 2개를 훈련하고 run으로 기록한다(파라미터·메트릭·아티팩트·데이터 지문·운영 태그)
- 재현성을 실측 검증하고, 레지스트리 등록 → 승격 게이트 → champion 별칭 → 별칭 로드·예측의 전 흐름을 실행한다

#### 실행 환경
- Python 3.10 이상(3.13에서 검증), 서버 상주 없음
- 추적·레지스트리 백엔드: 로컬 SQLite(`sqlite:///data/output/mlflow.db`)

#### 실행 명령

```bash
cd practice/chapter9
python3 -m venv venv && source venv/bin/activate
pip install -r code/requirements.txt
python run_chapter9.py
```

| 시나리오 | 내용 | 대응 절 |
|---|---|---|

#### 관찰 과제

○ **관찰 1**: 훈련 코드 vs 기록 코드의 비율

## 비즈니스 적용 노트

> 이 장의 기법이 민간 비즈니스에서 어떤 지표·목표·도구로 쓰이는지 정리한다.

### 공공 → 비즈니스 대응표

| 공공 맥락 | 비즈니스 맥락 | 차이점 |
|---|---|---|
| 모델 승인 = 감사·소명 대비 | 모델 승인 = A/B 테스트 통과 후 프로덕션 투입 | 공공은 절차 준수와 책임 소재가 핵심, 비즈니스는 수익 지표 개선 여부가 판정 기준 |
| 재현 4요소 기록 = 행정 감사에 답할 수 있는 이력 | 재현 4요소 기록 = 실험 디버깅과 팀 간 지식 공유 | 공공은 법적·행정적 소명이 동기, 비즈니스는 실험 속도와 효율이 동기 |
| 승격 게이트 = 절대 기준 + champion 대비, 사람 검수 | 승격 게이트 = 비즈니스 KPI(CTR(클릭률), CVR(전환율)) 기반 자동 판정 | 공공은 사람 승인 필수, 비즈니스는 통계적 유의성 자동 판정이 일반적 |
| 모델 레지스트리 = 단일 모델의 이력 관리 | 모델 레지스트리 = 수십~수백 모델의 병렬 실험·배포 관리 | 비즈니스는 다수 모델을 피처 플래그와 연동해 관리한다 |

### 비즈니스에서의 핵심 지표

○ **CTR(Click-Through Rate, 클릭률)** — 추천·광고 모델의 1차 판정 지표
  - 새 모델이 기존보다 CTR을 올리는가를 A/B 테스트로 검증한다
  - 이 장의 "champion MAE 대비 개선 여부"가 "대조군 대비 CTR 상승 여부"로 바뀐다

○ **CVR(Conversion Rate, 전환율)** — 구매·가입·신청 등 최종 행동 전환 비율
  - CTR이 올라도 CVR이 내려가면 실패한 모델이다
  - 이 장의 "절대 기준 + 상대 기준" 이중 게이트가 CTR과 CVR을 함께 거는 형태로 적용된다

○ **ARPU(Average Revenue Per User, 사용자당 평균 매출)** — 모델이 수익에 미치는 종합 영향
  - 예측 정확도(MAE)가 올라도 ARPU가 안 오를 수 있다: 훈련 오차와 비즈니스 성과 사이에 간극이 있다

○ **실험 속도(Experiment Velocity)** — 주당·월당 실행하는 실험(run) 수
  - 실험 추적이 잘 갖춰진 조직이 run을 더 자주, 더 빨리 돌린다

### 실무 적용 사례

○ **A/B 테스트 플랫폼과 모델 레지스트리 연동**
  - 레지스트리의 challenger 모델을 A/B 플랫폼에 자동 연결한다
  - 이 장의 "별칭으로 로드하는 소비자 코드"가 A/B에서는 "실험군에 challenger, 대조군에 champion 라우팅"이 된다
  - 통계적 유의성이 확인되면 별칭을 이동시켜 자동 승격한다

○ **데이터 지문의 비즈니스 활용**
  - "지난달 모델이 더 나았다"는 주장에 대해 데이터 지문이 없으면 비교가 성립하지 않는다
  - 사용자 행동 데이터는 계절·이벤트·정책 변경으로 빠르게 바뀌므로 지문 기록이 더 중요하다

○ **모델 성능 비교 자동 리포트**
  - 매일·매주 run 간 메트릭 비교 리포트를 자동 생성한다
  - 이 장의 표 9.2가 수백 개 run으로 확장된 것이며, MLflow UI나 W&B(Weights & Biases) 대시보드가 그 도구다
