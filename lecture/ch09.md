## 1. 오늘의 질문

□ 석 달 전에 배포한 모델을 지금 다시 만들 수 있는가. 무엇을 알아야 다시 만들 수 있는가.  
□ 훈련 한 번에 무엇을 남겨야 "어떻게 만들었는가"에 답이 되는가.

## 3. run 하나에 무엇을 남기는가

□ 훈련을 한 번 돌릴 때마다 기록 한 묶음을 만들며, 이 묶음을 **run**이라 함  
  ○ 이 장에서 훈련을 두 번 돌렸으므로(`baseline_mean`, `linear`) run이 둘 생김  
  ○ **실험(experiment)** 은 관련된 run들을 모아 부르는 이름임  
□ run 하나에는 세 종류를 나누어 적음  
  ○ **파라미터(params)**: 훈련에 넣은 설정. 글자나 숫자로 적음. 예: `model_type = LinearRegression`  
  ○ **메트릭(metrics)**: 훈련 결과로 나온 숫자. 이 장에서는 훈련 오차인 `train_mae` 하나임. MAE(평균 절대 오차)는 예측과 실제의 차이를 절댓값으로 바꿔 평균한 값이며, 작을수록 잘 맞음. 예: `linear`는 1.0455  
  ○ **아티팩트(artifacts)**: 결과로 남기는 파일. 예: 훈련에 쓴 CSV 파일, 저장한 모델 파일  
□ 세 종류를 나누는 이유는 나중에 run을 찾는 질문이 세 가지로 갈리기 때문임  
  ○ "`model_type`이 `LinearRegression`인 run만 보여 달라" → 파라미터 칸의 글자를 맞춰 찾음  
  ○ "`train_mae`가 가장 작은 run은 무엇인가" → 메트릭 칸의 숫자를 작은 순으로 나열함. 이 장에서는 `baseline_mean`(1.0)이 `linear`(1.0455)보다 앞에 옴  
  ○ "그 run이 쓴 훈련 CSV를 다시 열어 보자" → 아티팩트 칸에 저장된 파일을 내려받음  
  ○ 오차를 숫자가 아니라 글자로 적어 두었다면 두 번째 질문처럼 작은 순서로 나열할 수 없음  

□ 훈련 결과를 정하는 입력은 코드·데이터·파라미터·환경 넷이며, 이 중 데이터만 자동으로 기록되지 않음  
  ○ 코드는 git이 버전으로 남기고, 파라미터와 메트릭은 기록 도구가 남김  
  ○ 훈련 데이터는 **파일 경로가 같아도 내용이 바뀜** — 7주차의 정정 재실행이 그런 경우임  
  ○ 그래서 훈련 데이터를 정해진 형식의 CSV 텍스트로 만든 뒤 sha256이라는 계산 방식으로 64자의 값을 만들어 두며, 이 값을 **지문**이라 함  
  ○ sha256은 내용이 한 글자만 달라도 전혀 다른 64자를 내므로, 두 지문이 같으면 같은 데이터라고 판단함  
  ○ 이 지문을 파라미터에 넣어 두면 run마다 어느 데이터를 썼는지 남음  
□ 같은 훈련 데이터를 지문과 사본 두 가지로 남기는 것은 쓰임이 다르기 때문임  
  ○ 지문(64자)은 짧아서 두 run의 지문을 나란히 놓고 "같은 데이터였나"를 바로 확인함  
  ○ 사본(CSV 파일)은 크지만 열어 볼 수 있어서 "그 데이터를 다시 보자"에 쓰임

## 4. 훈련도 함수다 — 같은 입력이면 같은 모델

□ 6주차에서 배치는 같은 입력을 넣으면 산출물 해시까지 같았음. 훈련에도 같은 성질이 있어야 함  
  ○ 모델을 만드는 데 들어간 입력은 코드·데이터·파라미터·환경(라이브러리 버전 등) 넷이고, 넷이 전부 같으면 같은 모델이 나와야 함  
  ○ 예: 이 장에서 같은 6쌍으로 `linear`를 두 번 훈련하면 두 번 모두 오차 1.0455가 나옴(아래 출력 [5])  
  ○ 입력이 하나 더 있을 수 있음 — 훈련 알고리즘이 난수(무작위 숫자)를 쓰면 난수의 시작값(seed)도 같게 고정해야 같은 모델이 나옴. 코드에 눈에 띄게 적히지 않아 놓치기 쉬움  
  ○ 이 장의 후보 둘은 난수를 쓰지 않으므로 seed 없이도 같은 값이 나옴  
□ 훈련 때 기록을 남기지 않으면 나중에 같은 모델을 다시 만들 수 없음  
  ○ 석 달 전 모델의 성능이 떨어져 "그때 모델을 다시 만들어 비교하자"고 할 때, 데이터·파라미터·코드 중 하나라도 확실하지 않으면 다시 만든 모델은 그때 모델과 다른 모델임  
  ○ 그러면 "그때와 지금이 어떻게 다른가"를 비교할 수 없음  
□ 실험 중에 기록을 자동으로 남겨야 하는 이유는 실험 속도임  
  ○ 하루에 파라미터를 다섯 번 바꾸고 데이터를 두 번 바꾸는 일이 흔함  
  ○ 그 속도에서 "나중에 정리하자"고 하면 어떤 설정이었는지 기억하지 못하므로, 기록은 실험이 끝난 뒤에 쓰는 문서가 아니라 훈련을 돌리는 코드가 그 자리에서 남기는 기록이어야 함  

□ 두 번째 코드를 실행함. 후보 둘을 훈련하고 같은 설정으로 한 번 더 훈련함

    – 4단계, 셋 다 같은데 결과가 다르면 seed를 고정하지 않은 난수를 찾음  
□ 1·2단계의 기록은 **훈련할 때** 남겨 두어야 하고, 오차가 다르다는 신고가 들어온 뒤에는 만들 수 없음  
  ○ 정보공개 청구나 감사에서 "이 모델의 판단 근거를 소명하라"는 요구가 오면, 모델 파일만 가진 기관은 어떤 데이터와 설정으로 만들었는지 답하지 못함  
  ○ 그러므로 재현성은 연구자의 취향이 아니라, 문제가 생겼을 때 누가 무엇을 근거로 결정했는지 밝히기 위한 조건임  

## 5. 승격 게이트는 통과 규칙이 아니라 교체 규칙이다

□ 이 절은 세 가지를 차례로 다룸 — 모델 레지스트리, 별칭, 승격 게이트  
  ○ 세 가지는 "운영 중인 모델이 무엇인가"라는 질문 하나에서 차례로 나옴  

### 5.1 모델 레지스트리 — 후보에 이름과 번호를 붙인다

□ 4절까지 훈련하면 run이 둘 생겼음 — `baseline_mean`(train_mae 1.0)과 `linear`(train_mae 1.0455)  
  ○ 실험을 계속하면 run은 수십, 수백 개로 늘어남  
  ○ 서빙 시스템(운영 중 예측 요청을 받는 프로그램)에 "run 목록에서 알아서 좋은 것을 골라 쓰라"고 하면, 어느 run을 쓰는지 아무도 모르게 됨  
□ 그래서 배포 후보만 따로 등록하는 저장소를 두며, 이것이 **모델 레지스트리(registry)** 임  
  ○ 등록할 때 모델에 이름 하나를 붙임 — 이 장의 이름은 `complaint_daily_forecaster`임  
  ○ 같은 이름으로 등록할 때마다 번호가 1씩 늘어난 **버전**이 생김 — `baseline_mean`은 v1, `linear`는 v2가 됨  
  ○ 각 버전에는 그 버전을 만든 run의 번호가 적혀 있어서, 3절에서 남긴 파라미터·메트릭·데이터 지문을 버전에서 바로 찾아감  

### 5.2 별칭 — 서빙 코드가 버전 번호를 모르게 한다

□ 버전이 여러 개이면 "지금 운영 중인 것은 v1인가 v3인가"를 한 곳에서 답해야 함  
  ○ 서빙 코드에 `v1`을 적어 두면, 모델을 바꿀 때마다 서빙 코드를 고쳐서 다시 배포해야 함  
  ○ 그래서 버전에 **별칭(alias)** 을 붙임 — 별칭은 버전 하나에 붙이는 이름표이며, 같은 별칭을 다른 버전으로 옮길 수 있음  
□ 이 장은 운영 중인 버전에 `champion`이라는 별칭을 붙임  
  ○ 서빙 코드(`9-1-mlflow-tracking.py` 220행)는 버전 번호 없이 이름과 별칭만 적어 모델을 불러옴  

```python
loaded = mlflow.pyfunc.load_model(f"models:/{MODEL_NAME}@champion")
```

□ `champion`을 v1에서 v3으로 옮기면 위 한 줄은 그대로인데 불러오는 모델이 v3으로 바뀜  
  ○ 이 장의 로그에서는 같은 입력(강남구 전일 건수 9.0)에 v1이 6.00, v3이 7.50을 냄(아래 출력 [6])  
  ○ 그래서 별칭을 옮기는 일은 코드 수정 없이 일어나는 **배포**이고, 옮긴 이력을 남겨야 함  
  ○ 7주차에서 서빙이 피처를 정의 이름으로 조회했듯, 여기서는 모델을 별칭으로 조회함  

### 5.3 승격 게이트 — 별칭을 옮겨도 되는지 정하는 규칙

□ 새 후보가 등록될 때마다 `champion`을 옮길지 사람이 그때그때 정하면 기준이 사람마다 달라짐  
  ○ 그래서 옮기는 조건을 미리 적어 두며, 이 조건이 **승격 게이트**임  
  ○ 게이트의 조건은 두 종류임  
□ **절대 조건**은 후보 하나만 보고 정함  
  ○ 예: "train_mae가 1.05 이하일 것"  
  ○ 질문은 "이 모델을 운영에 써도 되는 수준인가"임  
□ **상대 조건**은 지금 `champion`과 비교해서 정함  
  ○ 예: "train_mae가 현재 champion(1.0)보다 작을 것"  
  ○ 질문은 "지금 모델을 이 모델로 바꿀 이유가 있는가"임  
□ 두 질문은 서로 다르므로 하나만 두면 빠지는 경우가 생김  
  ○ 절대 조건만 두면 지금보다 나쁜 모델이 조건만 맞춰 들어옴  
  ○ 상대 조건만 두면 업무 기준에 못 미치는 모델끼리 바뀌기만 함  
  ○ 아래 실행에서 두 경우를 숫자로 확인함  

□ 세 번째 코드를 실행함. 같은 후보에 규칙 셋을 각각 적용해 판정이 갈리는지 봄

  ○ **상대 조건만 두면 못 쓸 모델끼리 교체가 계속됨** — 업무가 요구하는 오차가 0.8이라면 `baseline_mean`도 `linear`도 미달임. 그런데 둘 중 나은 쪽으로 바꾸는 규칙은 계속 작동해, 운영에 쓸 수 없는 모델이 바뀌기만 함  

```text

    반려된 v2를 지우지 않았기 때문에 되돌아갈 수 있는 버전이 v1·v2 둘이다
```

□ [6]에서 읽을 것  
  ○ **별칭을 옮기면 같은 입력의 답이 바뀜** — 강남구 전일 건수 9.0에 champion v1은 6.00을, v3은 7.50을 냄. 소비자 코드는 그대로인데 결과가 달라지므로, 별칭 이동은 배포 행위이며 이력이 남아야 함  
  ○ **반려된 버전을 지우지 않아야 롤백할 수 있음** — 롤백은 `champion`을 이전 버전으로 되돌리는 일임. 이 출력에서는 v3으로 옮겼다가 v1로 되돌렸고, 지우지 않은 v1·v2가 되돌아갈 수 있는 버전으로 남아 있음. 버전을 지우면 되돌아갈 곳이 없어짐

```text
[7] 지표가 좋아졌다고 끝나지 않는다 — district_mean의 조건
```

## 6. 승격은 기술 행위가 아니라 승인 행위다

□ 앞의 세 절에서 남긴 기록은 "어떤 데이터와 설정으로 만들었고 오차가 얼마인가"에 답함  
  ○ 공공 기관의 감사(기록이 규정에 맞는지 외부에서 점검하는 일)는 여기에 네 가지를 더 물음  
  ○ **누가** 만들었는가, **무슨 목적**으로 만들었는가, **어느 기간의 어떤 출처** 데이터를 썼는가, **어떤 제한** 아래 쓰는가  
□ 이 네 가지는 오차와 무관하지만 책임을 가리는 데 쓰이고, 나중에 쓰려 하면 쓸 수 없음  
  ○ 담당자가 다른 부서로 옮기면 목적과 데이터 출처를 아는 사람이 없어짐  
  ○ 그래서 훈련할 때 run에 태그(tag, 이름표 형태로 적는 짧은 글자 항목)로 함께 적어 둠  
  ○ 이 장의 실습이 적는 태그는 소유자·목적·데이터 출처·데이터 기간 네 개임  
□ 승격을 결정한 기록도 남김  
  ○ 공공 기관에서 승격은 "이 모델을 운영에 써도 된다"는 승인이므로, 누가 어떤 규칙으로 어떤 근거를 보고 통과시켰는지를 기록으로 남겨야 함  
  ○ 이 기록은 사람이 나중에 쓰는 보고서가 아니라, 판정하는 코드가 판정하는 순간에 출력한 것이어야 함. 나중에 쓰면 기억으로 채우게 되기 때문임  
□ 검수 기록에는 "같은 설정으로 다시 돌리면 같은 결과가 나오는가"라는 항목도 들어감  
  ○ 게이트는 오차 수치를 보고 통과 여부를 정하고, 재현성 항목은 그 수치를 믿어도 되는지를 확인함  
  ○ **다시 돌렸을 때 같은 수치가 나오지 않는 run은 오차가 좋아도 승격하지 않음** — 그 오차가 코드와 데이터 때문에 나온 것인지 우연히 나온 것인지 가릴 수 없기 때문임  

□ 네 번째 코드를 실행함. 승격 검수 기록이 감사 질문에 답할 수 있는지 점검함  

```bash
python3 code/9-5-review-record-check.py
```

```text
# 출처: practice/chapter9/results/9-5-review-record-check.log
[2] 감사 질문별 점검
    통과  항목 model_name          어느 모델인가
    통과  항목 champion_version    지금 운영 중인 것은 몇 번인가

    통과  항목 reproducibility_check 그 수치가 다시 나오는가
    통과  항목 data_fingerprint_sha256 어느 데이터로 훈련했는가
    통과  항목 reviewer            누가 확인했는가
    통과  항목 notes               어떤 제한이 붙는가
```

□ [2]에서 읽을 것  
  ○ **점검 항목 하나가 감사 질문 하나와 짝을 이룸** — 13개 항목 각각이 "어느 모델인가", "누가 확인했는가" 같은 질문 하나에 대응함. 감사에서 나올 질문을 먼저 목록으로 적고, 그 질문마다 기록 파일에 칸을 하나씩 만들면 이 점검표가 됨  
  ○ **지문을 다시 계산해 맞춰 보면 기록이 사실인지 확인됨** — 기록에 적힌 64자를 원천 자료에서 다시 계산해 비교함. 기록만 읽는 점검은 "값이 적혀 있다"까지만 확인하고, 다시 계산하는 점검은 "그 값이 맞다"까지 확인함  
  ○ **12/13에서 걸린 한 칸이 사람 칸임** — 나머지는 자동으로 채워지는데 검수자만 비었음. 교육용이라 가상 표기로 두었지만, 행정 처분이나 자원 배분에 쓰이는 모델이라면 이 칸이 비면 안 됨  

```text
# 출처: practice/chapter9/results/9-5-review-record-check.log ([3])
```

  ○ **점검이 실제로 잡아냄** — 검수자를 빼고 지문을 다른 값으로 바꾼 사본은 10/13으로 내려감. 통과 수가 줄어드는 것을 확인해야 그 점검이 형식이 아님을 알 수 있음  

□ 이 점검표를 실제 기관에 적용하려면 세 가지를 정해야 함  
  ○ 게이트를 통과하면 승격을 자동으로 할 것인가, 사람이 확인한 뒤에 할 것인가  
  ○ 게이트에 못 미치는데 승격해야 하는 사정이 생기면 누가 예외를 승인하는가  
  ○ `champion` 별칭을 옮길 권한을 누가 갖는가  
□ 세 번째가 특히 중요함  
  ○ **모델을 훈련한 사람이 별칭도 옮기면 게이트를 통과시키는 사람과 통과하는 사람이 같아져, 외부 확인 없이 자기가 자기를 승인하게 됨**  

## 7. 핵심 요약

□ **1. run 하나에는 파라미터·메트릭·아티팩트를 나누어 남기고, 훈련 데이터는 지문을 직접 계산해 적어야 한다.** (3절)  
  ○ 입력 설정과 결과 수치와 결과 파일은 찾는 방식이 달라 나누어 남김  
  ○ 코드는 git이, 파라미터는 도구가 자동으로 남기지만 훈련 데이터는 경로가 같아도 내용이 바뀌므로 sha256 지문을 파라미터로 실어 보냄  
  ○ 원천 한 칸을 6에서 7로 고쳤더니 지문 앞 16자 중 일치하는 글자가 0개였음  
□ **2. 같은 입력이면 같은 모델이 나오고, 안 나오면 무엇이 바뀌었는지 기록으로 가려낼 수 있다.** (4절)  
  ○ 선형회귀를 다시 훈련해도 오차 1.0455와 계수 (0.4091, 3.6818)가 그대로였음  
  ○ 입력을 한 건만 바꾸자 지문이 달라지고 오차가 1.0000에서 1.2222로 바뀌었음  
  ○ 파라미터 → 지문 → 환경 → 난수 순으로 대조하되, 앞의 둘은 훈련 시점에 남겨야만 존재함  
□ **3. 절대 게이트와 상대 조건은 다른 질문에 답하므로 둘 다 필요하다.** (5절)  
  ○ 절대 게이트만 두면 1.0455가 임계 1.05를 통과해 1.0000인 현행 모델이 교체됨  
  ○ 상대 조건만 두면 업무 기준 0.8에 둘 다 미달인 후보끼리 교체가 계속됨  
  ○ 둘을 함께 둔 규칙 C에서만 linear가 반려되고 district_mean이 승격됐음  
□ **4. 별칭 이동이 배포이고, 반려 버전을 남기는 것이 롤백 준비다.** (5절)  
  ○ 같은 입력 9.0에 champion v1은 6.00을, v3은 7.50을 냈고 소비자 코드는 바뀌지 않았음  
  ○ 반려된 v2를 지우지 않았기에 되돌아갈 수 있는 버전이 둘로 남았음  
□ **5. 승격은 승인 행위이고, 검수 기록은 감사 질문 목록을 파일로 옮긴 것이다.** (6절)  
  ○ 13개 점검 중 12개가 자동으로 통과했고 걸린 한 칸이 검수자였음  
  ○ 지문을 원천에서 다시 계산해 맞춰야 기록의 진위까지 확인됨  
  ○ 훈련하는 사람과 champion 별칭을 옮기는 사람이 같으면 게이트는 자기 검사에 그침
