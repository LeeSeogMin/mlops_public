# 제9장 실험 추적과 모델 레지스트리

---

## [전반부] 이론 강의
---

### 학습 목표

- 실험 추적의 필요성과 핵심 기록 항목(파라미터·메트릭·아티팩트)을 이해한다
- MLflow로 실험 파라미터와 지표를 기록하고 재현성(reproducibility)을 검증한다
- 모델 레지스트리와 승격 절차(별칭·게이트·반려)를 설명한다
- 요구사항에서 승격 게이트 규칙(판정 지표·임계값·상대 조건·승인 주체)을 도출하고 근거를 적는다

---

### 1. 실험 재현성의 의미
#### 1-1. "답할 수 없는 상태"가 기본값이다

○ **재현성 문제의 출발점**
  - 석 달 전 배포한 모델의 성능이 떨어졌을 때 "그때 모델을 다시 만들자"가 첫 수
  - 다시 만들려면 네 가지를 알아야 한다 — 어느 데이터, 어느 피처, 어느 파라미터, 어느 코드
  - 아무것도 기록하지 않았으면 "다시 만든 모델"은 재현이 아니라 **새 모델** → 비교 실험 자체가 성립하지 않음

○ **기록이 없는 이유는 게으름이 아니다**
  - 실험은 하루에 파라미터를 다섯 번 바꾸고, 데이터를 두 번 갈아끼우는 것이 정상
  - "나중에 정리해야지"는 반드시 실패
  - 기록은 실험 **후**의 문서화가 아니라 실험 **중**의 자동 기록이어야 함

#### 1-2. 훈련도 함수다 — 7장 재현성의 확장

○ **모델 = f(코드, 데이터, 파라미터, 환경)**
  - 7장: 같은 입력 파일 → 같은 산출물(해시 동일)
  - 9장: 같은 설정 → 같은 모델(메트릭·계수 동일)
  - 난수를 쓰는 알고리즘이면 seed도 입력에 포함해 고정해야 함수가 됨

**표 9.1** 재현 4요소와 기록 수단

| 요소 | 재현 실패의 전형 | 실습의 기록 수단 |
|---|---|---|
| 코드 | 훈련 스크립트가 수정됨 | 버전 관리(git) |
| 데이터 | 원천이 정정·추가로 변함 | **데이터 지문(data fingerprint)**(sha256)을 파라미터로 기록 |
| 파라미터 | "그때 뭘 줬더라" | run에 `log_params`로 자동 기록 |
| 환경 | 라이브러리 버전 차이 | 모델과 함께 의존성 기록(MLflow가 동봉) |

#### 1-3. 재현 실패의 원인 분리 절차

○ 두 run을 나란히 놓고 요소별로 대조한다 — **값싼 대조부터, 비싼 대조는 나중에**
  1. **파라미터 대조**: 기록된 파라미터를 필드별 비교 → 다르면 종결
  2. **데이터 지문 대조**: 파라미터가 같아도 `data_sha256_16`이 다르면 데이터가 바뀐 것
  3. **환경 대조**: 라이브러리 버전(의존성 기록) 비교 → 부동소수점 수준 차이 가능
  4. **난수 확인**: 셋 다 같은데 다르면 seed 미고정이 원인

○ 절차 전체가 성립하려면 1~2단계의 기록이 **훈련 시점에** 이미 남아 있어야 함

#### 1-4. 정직한 반대 논거 — 언제 과한가

○ 탐색 초기·버릴 것이 뻔한 스케치 실험까지 전부 남기면 **소음 비용**이 문제
  - run 수백 개 속에서 의미 있는 것을 못 찾으면 기록이 없는 것과 같음
○ 현실적인 선: 기록 자체는 자동이므로 켜 두되, 의미 있는 run에 태그(tag)·이름을 붙여 구분
  - "모든 run을 기록"(실험의 안전망) ≠ "선별된 후보만 등록"(운영의 관문)

○ **기록의 동기는 도메인이 바꾼다** — 항목은 같다
  - 공공: 감사·정보공개 청구에 답하는 이력
  - 민간: 성능이 나빠졌을 때 원인을 빨리 찾고 팀원끼리 실험 설정을 주고받는 수단
  - 민간은 기록의 양 자체를 지표로 삼기도 함 — 주당·월당 run 수를 **실험 속도(experiment velocity)**로 부르고 팀 생산성의 대리 지표로 읽음

#### 1-5. 공공 맥락

○ 정보공개 청구·감사에서 "이 모델의 판단 근거를 소명하라"는 요구가 올 수 있음
  - 모델 파일만 있으면 "어떻게 만들어졌는가"에 답할 수 없음
  - 실험 기록이 있으면 run을 열어 데이터 지문·파라미터·성능 지표·훈련 일시를 제시
  - 재현성은 연구자의 결벽이 아니라 **책임 소재의 전제 조건**

### 2. 파라미터, 메트릭, 아티팩트 기록
#### 2-1. run의 세 기록 항목

○ **run**: 훈련 한 번의 기록 단위. experiment(실험)는 run들을 묶는 폴더

○ **파라미터(params)** — 훈련의 입력 설정
  - 모델 종류, 하이퍼파라미터(hyperparameter), 데이터 지문(`data_sha256_16`), 표본 수
  - "무엇을 넣었나"

○ **메트릭(metrics)** — 훈련의 결과 수치
  - 실습은 훈련 MAE(Mean Absolute Error, 평균 절대 오차)
  - "무엇이 나왔나"

○ **아티팩트(artifacts)** — 결과 파일
  - 모델 자체, 훈련 데이터 사본, 그림 등 수치로 환원되지 않는 실물
  - "무엇이 만들어졌나"

○ **구분이 중요한 이유**: 질의 방식이 다르다
  - "학습률 0.01인 run 전부" → 파라미터 검색
  - "MAE 최소 run" → 메트릭 정렬
  - "그 run의 훈련 데이터를 열어 보자" → 아티팩트 다운로드

#### 2-2. 실측: 후보 2개의 기록

○ 훈련 데이터: 8장 피처 원천(9행 = 3지역 × 3일)에서 만든 **(전일 건수 → 당일 건수) 쌍 6개**
  - 강남(11680): 8→6, 6→9 / 마포(11440): 5→5, 5→6 / 관악(11620): 5→5, 5→5

**표 9.2** 후보별 기록(실제 실행, MLflow 3.14.0)

| 기록 항목 | 후보 1: baseline_mean | 후보 2: linear |
|---|---|---|
| 파라미터(모델) | DummyRegressor, strategy=mean | LinearRegression, fit_intercept=True |
| 파라미터(데이터) | n_samples=6, data_sha256_16=96f6b6b3ce9dcdd1 | 동일(같은 데이터) |
| 메트릭 train_mae | **1.0000** | **1.0455** |
| 학습된 계수 | (평균 6.0) | slope **0.4091**, intercept **3.6818** |
| 아티팩트 | 훈련 CSV, 모델 | 훈련 CSV, 모델 |

○ **손 검산**
  - 베이스라인: y 평균 = (6+9+5+6+5+5)/6 = 36/6 = **6.0**, 잔차 합 6 ÷ 6 = MAE **1.0**
  - 선형회귀: 최소제곱으로 slope = 9/22 = **0.4091**, intercept = 81/22 = **3.6818**
  - **더 복잡한 모델이 졌다**(1.0455 > 1.0000) — 6쌍으로는 유의미한 기울기를 배울 수 없음

#### 2-3. 재현성 실측

○ 선형회귀 후보를 같은 데이터(지문 동일)·같은 파라미터로 재훈련
  - train_mae 1.0455 = 1.0455, 계수 동일 → `mae_equal=true`, `coef_equal=true`
  - 7장 "재실행 해시 동일"의 모델판
  - 역으로 읽으면 **회귀 검사**: 아무것도 안 바꿨는데 메트릭이 달라졌으면 입력이 몰래 바뀐 것

#### 2-4. 데이터 지문의 이중 기록

○ 훈련 데이터를 **아티팩트**(CSV 사본)로도, **파라미터**(sha256 지문)로도 기록
  - 지문: 가볍고 비교 가능 → "같은 데이터였나"의 즉답
  - 사본: 무겁지만 실물 → "그 데이터를 다시 보자"
  - 중복이 아니라 용도 분리

#### 2-5. 정직한 표기

○ 이 실습의 MAE는 **훈련 데이터 위의 훈련 오차**
  - 6쌍을 훈련/평가로 쪼개는 것은 무의미하므로 분리하지 않음
  - 실무라면 승격 판정의 근거는 **보류(holdout) 데이터의 평가 지표**여야 함
  - 관찰 대상은 모델 품질이 아니라 기록·등록 메커니즘

### 3. 모델 레지스트리 단계와 승인 흐름
#### 3-1. 실험 기록과 배포 승인은 다른 층이다

○ run은 수십·수백 개가 쌓이는 것이 정상 — 서빙 시스템에 "알아서 좋은 걸 골라라"고 할 수 없음
○ **모델 레지스트리**: 배포 후보를 이름·버전으로 관리하는 관문
  - run은 개별 실행의 기록이고, 레지스트리는 배포 후보를 버전으로 관리하는 별도 저장소
  - 같은 이름 아래 v1, v2, v3가 쌓이고 각 버전은 자기를 만든 run을 가리킴

#### 3-2. 별칭(alias) — 현행 방식

○ MLflow 현행: stage API 대신 **별칭(alias)** 사용
  - 버전에 champion 같은 가변 이름표를 붙임
  - 소비자는 `models:/이름@champion`으로 로드 → 버전 번호를 몰라도 됨
  - 별칭을 v1에서 v2로 옮기면 운영 모델이 교체되고, 소비자 코드는 안 바뀜

○ **규모가 커지면 이름표 규약이 곧 관리 체계** — 모델 수십·수백 개를 굴리는 민간 조직은 별칭을 배포 스위치(피처 플래그)와 묶어 "어느 버전이 어느 트래픽에 걸려 있는가"를 한 곳에서 조회. 공공은 모델 하나의 이력을 길게 관리하는 쪽이라 이름표 수는 적지만, 시스템이 답해야 한다는 요구는 같음

**표 9.3a** 단계 개념과 별칭 구현의 대응

| 단계 개념(전통) | 뜻 | 별칭 방식(현행) |
|---|---|---|
| 개발(None) | 등록만 된 후보 | 별칭 없는 버전 |
| 검증(Staging) | 운영 투입 전 평가 중 | challenger 별칭을 관례로 부여 |
| 운영(Production) | 서빙이 소비 중 | **champion 별칭** — 소비자가 이것만 바라봄 |
| 폐기(Archived) | 더는 후보 아님 | 별칭 제거(기록 자체는 남음) |

#### 3-3. 승격 게이트 실측

○ 등록 모델: `complaint_daily_forecaster`
○ 승격 규칙: ① 절대 게이트 — train_mae ≤ 1.05, ② 상대 조건 — 기존 champion보다 개선

**표 9.3** 레지스트리 실측(등록·게이트·별칭)

| 버전 | 후보 | train_mae | 게이트(≤1.05) | champion 대비 | 판정 |
|---|---|---|---|---|---|
| v1 | baseline_mean | 1.0000 | 통과 | (최초) | **champion 별칭 부여(승격)** |
| v2 | linear | 1.0455 | 통과 | 1.0455 > 1.0000, 개선 없음 | **승격 반려** — 등록은 유지 |

○ v2의 교훈
  - 게이트는 통과했지만 상대 조건에서 탈락 → "절대 기준 통과"와 "교체 가치"는 다른 판단
  - 반려된 v2는 삭제되지 않고 **버전으로 남음** → 감사 기록("시도했고, 이 수치로 반려됨")

#### 3-4. 게이트 값은 어디서 오는가

○ 규칙 두 줄(train_mae ≤ 1.05, champion 대비 개선)은 주어진 값이 아니라 **네 가지 선택의 결과**

  1. **어떤 지표로 판정하는가** — MAE를 고르면 큰 오차 하나와 작은 오차 여럿을 같은 무게로 세겠다는 선언. 한 번의 큰 빗나감이 인력 배치 실패로 이어지는 업무라면 RMSE가 그 실패를 더 무겁게 셈. 지표 선택 = **업무 손실의 모양을 고르는 일**
  2. **임계값을 어디서 끌어오는가** — "지금 사람이 하는 방식의 오차가 얼마인가" 또는 "오차가 얼마를 넘으면 현장 배치가 틀어지는가" 중 하나에 닿아야 함. 둘 다 아니면 반올림한 관행
  3. **단일 조건인가 복합 조건인가** — 조건을 늘리면 승격이 어려워져 오래된 모델이 계속 남고, 줄이면 "우연히 좋은 run"이 운영에 들어감. 실무에서 더 붙는 조건: 재현성 확인, 데이터 지문 일치, 집단별 오차 격차(16장)
  4. **게이트가 막았을 때 누가 예외를 승인하는가** — 예외 경로가 없으면 급할 때 임계를 조용히 낮추게 됨. 있으면 그 사용 이력이 감사 대상으로 남음(관리 가능한 쪽)

○ **민간이 같은 자리에 쓰는 값은 사업 지표**
  - **CTR(Click-Through Rate, 클릭률)** — 추천·광고 모델의 1차 판정 지표. 게이트는 "대조군 대비 CTR이 통계적으로 유의하게 올랐는가"
  - CTR 단독의 함정: 클릭만 늘리고 구매·가입은 줄이는 모델이 통과 → **CVR(Conversion Rate, 전환율)**을 함께 검. 두 지표를 동시에 거는 것이 이 장의 "절대 + 상대" 이중 게이트와 같은 구조
  - **ARPU(Average Revenue Per User, 사용자당 평균 매출)**까지 보면 공공·민간 공통 문제가 드러남 — **훈련 지표가 좋아지는 것과 목적이 달성되는 것은 다르다**. MAE가 내려가도 인력 배치가 나아지지 않을 수 있고, CTR이 올라도 매출은 그대로일 수 있음

#### 3-5. 별칭의 다른 얼굴 — 롤백(rollback)

○ 별칭 이동이 승격이면, 역방향이 **롤백**
  - v2를 champion으로 올렸다가 문제 발생 → 별칭을 v1으로 되돌리면 서빙 복귀
  - 소비자 코드는 이번에도 바뀌지 않음
○ 롤백의 전제 두 가지: 반려·교체된 버전을 지우지 않고 보존, 각 버전이 run과 연결

#### 3-6. 실제로 겪은 오류 — 등록 경로는 반환값에서 받아라

○ `runs:/<run_id>/model`로 문자열 경로를 조립해 등록 → 등록은 성공, 별칭 로드 시 예외 발생
  - `Could not find an 'MLmodel' configuration file`
  - MLflow 3의 저장 위치가 관례 경로와 달라졌기 때문
○ 수정: `log_model` 반환값(`model_info.model_uri`)을 등록에 넘김
○ 교훈: 등록(쓰기) 성공 ≠ 로드(읽기) 성공 → **별칭 로드·예측까지가 등록 검증**

### 4. 공공 모델 운영 메타데이터
#### 4-1. 감사는 성능표가 아니라 책임표를 요구한다

○ 기술 조직의 기록: "어떻게 만들었고 얼마나 좋은가"
○ 공공 감사가 추가로 묻는 것: **누가** 만들었고, **무슨 목적**으로, **어느 기간의 어떤 출처** 데이터로, **어떤 제한** 아래 쓰이는가
○ 소급 작성이 사실상 불가능(담당자 이동·기억 소실) → 훈련 시점에 run 태그로 함께 기록

#### 4-2. 승격 검수 기록

**표 9.4** 모델 승격 검수 기록 양식(실습 자동 생성, 실측 값)

| 항목 | 실측 값 | 왜 필요한가 |
|---|---|---|
| 모델 이름 / champion | complaint_daily_forecaster / v1 | "지금 운영 중인 것"의 정본 답 |
| 승격 규칙 | train_mae ≤ 1.05 + champion 대비 개선 | 판정 기준의 사전 명시 |
| 판정 이력 | v1 승격(1.0000), v2 반려(1.0455) | 반려 포함 전체 이력 |
| 재현성 확인 | 재실행 메트릭·계수 동일(true) | "우연히 좋은 run" 승격 방지 |
| 데이터 지문 | 96f6b6b3ce9dcdd1… (sha256) | 훈련 데이터의 증명 가능한 동일성 |

○ **가장 자주 비는 칸이 검수자** — 설계할 때 정할 것 셋
  - 게이트 통과 시 승격을 자동으로 둘 것인가, 사람 확인을 요구할 것인가
  - 게이트 미달인데 승격해야 하는 상황에서 누가 예외를 승인하는가
  - champion 별칭을 옮길 권한을 누가 갖는가 — 훈련하는 사람과 별칭을 옮기는 사람이 같으면 게이트는 자기 검사에 그침

#### 4-3. 모델 등록 체크리스트

- [ ] run에 파라미터·메트릭·아티팩트가 완결 기록되어 있는가 — 특히 **데이터 지문**
- [ ] 운영 메타데이터 태그(소유·목적·출처·기간)가 있는가
- [ ] 같은 설정 재실행으로 재현성이 확인되었는가
- [ ] 승격 규칙(절대 게이트 + 상대 조건)이 사전에 문서화되어 있는가
- [ ] 등록 후 **별칭 로드·예측까지** 검증했는가
- [ ] 승격 검수 기록이 생성·보존되는가

#### 4-4. 역방향 — 이 장의 기록 규율을 민간 현장으로

○ **A/B 테스트 플랫폼과 레지스트리 연동** — 별칭이 트래픽 라우팅의 스위치가 됨
  - 대조군에 champion, 실험군에 challenger를 물림. 별칭 이동 = 승격이라는 구조는 그대로
  - 바뀌는 것은 **이동의 방아쇠** — 공공은 검수자 승인, 민간은 실험 결과의 통계적 유의성
  - 공공은 시민마다 다른 모델을 태우기 어려워 A/B 대신 **섀도(shadow)** — 전원에게 champion으로 응답하고 challenger 예측은 로그로만 남김(10장)

○ **모델 비교 리포트 자동화** — 표 9.2를 손으로 만들 수 없어지는 지점에서 시작
  - run이 수백 개가 되면 파라미터·메트릭을 자동 추출해 정기 리포트로 뽑음
  - 읽는 방향이 하나 더 생김: 어떤 피처 조합·하이퍼파라미터가 사업 지표를 가장 올렸는가
  - 파라미터를 구조화해 기록해 둔 보상이 여기서 돌아옴 — 자유 서술 로그의 설정은 집계되지 않음

○ **데이터 지문은 민간에서 오히려 더 자주 쓰임**
  - 사용자 행동 데이터는 계절·프로모션·정책 변경으로 빠르게 변함
  - 지문이 없으면 "지난달 모델이 더 나았다"가 모델 비교인지 데이터 비교인지 갈라지지 않음

○ **관통하는 하나** — 게이트 지표 / 임계 / 태그 항목 / 별칭 이동 권한, 이 네 결정은 어느 현장에서도 똑같이 내린다. **근거만 도메인이 바꾼다**(공공: 감사·형평성·법적 의무 / 민간: 매출·비용·실험 속도)

○ **방향은 비대칭** — 공공용 검수 기록·지문 기록을 민간으로 가져가면 벗겨 낼 것이 없다(검수 기록 → 사후 분석 자료, 지문 → 실험 비교의 전제)

### 실습 9.1: 승격 게이트 설계와 MLflow 실험 기록·모델 등록

**진행 순서: 설계 → 실행 → 대조 → 위험 식별**

MLflow를 어떻게 호출하는지에는 고를 것이 없다 — 기록 API는 정해진 절차다. 반면 "무엇이 얼마나 좋아져야 운영 모델을 바꾸는가"는 전부 선택이고, 그 선택을 실행 결과를 본 뒤에 하면 규칙이 아니라 사후 합리화가 된다. 그래서 승격 규칙을 먼저 확정하고, 실측 메트릭에 자기 규칙을 적용해 판정이 맞았는지 본다. 감사·검수는 마지막 4단계에서 다룬다.

#### 실습 목표
- 요구사항에서 승격 게이트 규칙(판정 지표·임계값·상대 조건·태그·승인 주체)을 **스스로 정하고 근거를 적는다**(설계)
- 8장 피처를 입력으로 후보 2개를 훈련하고 run으로 기록한다(파라미터·메트릭·아티팩트·데이터 지문·운영 태그)
- 재현성을 실측 검증하고, 레지스트리 등록 → 승격 게이트 → champion 별칭 → 별칭 로드·예측의 전 흐름을 실행한다(실행)
- 자기 게이트를 실측 메트릭에 적용해 스크립트 판정과 맞춰 보고 어긋난 원인을 설명한다(대조)

- 감사 요구: 운영 모델이 바뀔 때마다 "왜 바꿨는가"에 답할 수 있어야 한다
- 훈련 데이터 원천은 7장 확정 집계이며, 정정 재실행으로 과거 값이 바뀔 수 있다

#### 3단계 대조 — 내 게이트를 실측 메트릭에 적용하기

예측표의 "실제" 줄을 채운다. 실측은 baseline_mean 1.0000 / linear 1.0455(표 9.2), 스크립트 판정은 v1 승격·v2 반려(표 9.3). 여기에 **자기 게이트를 다시 적용**해 판정이 같은지 본다.

○ **절대 게이트만 걸었다면** — 임계 1.05면 둘 다 통과, 1.0이면 linear만 탈락. 어느 쪽이든 절대 기준 하나로는 "교체할 이유"를 판정하지 못한다는 것이 v2에서 드러난다. 게이트를 통과했는데도 교체하지 않는 것이 정답인 경우가 있다.

○ **상대 조건에 개선 폭을 적었다면** — 이번 실행에서는 판정이 달라지지 않는다. linear는 개선이 아니라 악화(1.0455 > 1.0000)라 어떤 폭을 요구하든 반려. 폭 규정의 효과는 반대 상황에서 드러난다 — 후보가 0.9990을 냈다면 "개선되면 승격"은 교체하고 "0.05 이상 개선되면"은 교체하지 않는다. 인력 운영 계획을 바꿔 가며 얻을 만한 차이인가가 그 폭의 근거다.

○ **예측을 "새 후보가 이긴다"로 적었다면** — 복잡한 모델이 단순한 기준선을 이긴다는 보장은 없다. 6쌍으로 기울기를 배우려 한 선형회귀가 평균 예측기보다 나빴고, 이것은 예외가 아니라 ML Test Score가 정기 점검 항목으로 요구하는 상황 그대로다. 게이트는 새 후보를 통과시키는 장치가 아니라, 교체할 이유가 없을 때 교체하지 않게 막는 장치다.

○ **재현성·지문 요건을 넣었다면** — 이번 실행에서는 둘 다 충족(`mae_equal=true`, `coef_equal=true`, 지문 동일). 안 넣었다면 지금 한 줄 추가한다. 이 요건은 통과할 때 아무 일도 하지 않고, 데이터가 몰래 바뀐 실행에서만 작동한다.

○ **판정 지표를 MAE가 아닌 것으로 골랐다면** — 이번 증거로는 검증되지 않는다(기록된 메트릭이 train_mae 하나). 표 9.5의 "깨지는 조건"에 "판정에 필요한 지표가 run에 기록되지 않으면 게이트가 작동하지 않는다"를 적는다 — 게이트 설계와 기록 설계가 붙어 있다.

→ 표 9.5의 "이 게이트가 깨지는 조건" 칸을 지금 다시 쓴다. **제출하는 설계표는 이 수정을 반영한 최종본이다.**

#### 4단계 위험 식별 — 설계와 증거를 검수 언어로

검수·감사가 요구하는 형태는 "무엇이 잘못될 수 있는가 / 근거가 어느 산출물의 어느 값인가 / 무엇으로 막는가"다. 앞 네 행은 실행 증거에서, 마지막 행은 1단계 설계에서 나온다.

| 위험 | 실습 근거 | 대응 방향 |
|---|---|---|
| 재현 불가 모델 | 지문·파라미터 기록 + 재실행 동일 실측 | 4요소 기록을 훈련 코드에 상시 편입 |
| 우연한 좋은 수치의 승격 | 게이트 통과 후 재현성 확인을 승인 검수 요건으로 추가(표 9.4) | 승격 규칙 사전 문서화 + 보류 데이터 평가 |
| 등록-실물 불일치 | source 경로 오류 → 로드 실패(3-6) | 등록 후 별칭 로드·예측까지 검증 |
| 운영 모델 불명 | champion 별칭이 단일 정답 제공 | 버전 고정 대신 별칭 소비, 이동 이력 보존 |
| 게이트 규칙 자체의 결함 | 1단계 표 9.5 + 3단계 대조: 훈련 오차 단독 게이트는 과적합을 못 거르고, 개선 폭을 안 정하면 0.001 차이로도 교체됨 | 판정 지표를 보류 데이터 평가로 교체, 최소 개선 폭 명시, 별칭 이동 권한을 훈련 담당과 분리 |

대응 방향에 "모니터링한다"만 적으면 그 행은 검수 문서에서 쓸모가 없다. **바꿀 규칙이나 바꿀 값**을 적는다.
