### 1. 스트리밍 DataFrame과 trigger
#### 1-1. 핵심 발상 — 스트림 = 무한히 자라는 테이블

○ **배치 질의를 그대로 쓴다**
  - Structured Streaming은 스트림을 "행이 계속 추가되는, 끝이 없는 테이블"로 간주
  - 이미 아는 테이블 질의(DataFrame 연산)를 그 위에 그대로 적용
  - 엔진이 새 행이 추가될 때마다 결과를 **증분으로**(전체를 다시 계산하지 않고 바뀐 부분만) 갱신

○ **증분 계산과 상태(state)**
  - 예: "강남구 2"라는 중간 상태를 들고 있다가 새 이벤트 1건 반영 → 3으로 고침
  - 이 중간 상태를 **상태(state)** 라고 부름 → 상태가 쌓이므로 "언제 버릴 것인가"(watermark, 6.3)가 문제가 됨

| 시점 | 입력에 쌓인 행 | 결과(지역구별 건수) |
|---|---|---|
| 도착 1 후 | 강남구 1건 | 강남구 1 |
| 도착 2 후 | + 마포구 1건, 강남구 1건 | 강남구 2, 마포구 1 |
| 도착 3 후 | + 강남구 1건 | 강남구 **3**, 마포구 1 |

#### 1-2. 핵심 개념 4가지

○ **스트리밍 DataFrame**: `spark.readStream`으로 만드는 무한 테이블 참조. 소스는 Kafka·파일 디렉터리 등. 실습은 파일 소스 사용

○ **micro-batch**: 흐름을 잘게 쪼갠 "작은 배치의 연속"으로 처리
  - 검증된 배치 실행 엔진을 재사용할 수 있고, 배치 단위로 실패 복구가 단순해짐
  - 대신 최소 지연이 배치 주기만큼 생김 — 공공 대시보드 수준(초~분)에서는 문제 안 됨
  - 4장의 폴링 루프(poll→처리→커밋)와 구조가 닮았지만 루프를 엔진이 돌림

○ **trigger**: micro-batch를 "언제" 돌릴지 결정

| trigger | 의미 | 적합한 경우 |
|---|---|---|
| 기본(미지정) | 앞 배치 끝나면 바로 다음 배치 | 최저 지연 목표 |
| `processingTime="1 minute"` | 1분마다 실행 | 대시보드 갱신 주기 |
| `availableNow` | 쌓인 것 처리 후 종료 | 정기 증분 작업(7장 접점) |

○ **output mode**: 집계 결과에서 "무엇을" 내보낼지 결정

| 모드 | 내보내는 것 | 적합한 싱크(sink) |
|---|---|---|
| complete | 결과 표 전체를 매번 | 작은 결과의 대시보드 |
| update | 이번 배치에서 바뀐 행만 | 키 기반 저장소(Upsert, 5장) |
| append | 다시는 안 바뀔 확정 행만 | 불변 로그·파일 |

  - update 모드: 같은 키(창+지역구)의 행이 여러 번 나옴 → 받는 쪽에 5장의 Upsert가 필요
  - append 모드: watermark 없이는 집계에 쓸 수 없음 — "이 창은 다시 안 바뀐다"는 판단 근거가 watermark

#### 1-3. 이론이 정리한 네 가지 질문: what·where·when·how

○ Akidau 외(2015)의 Dataflow 모델이 정리한 네 질문

| 질문 | 의미 | 이 장에서 대응하는 개념 |
|---|---|---|
| **what** | 무엇을 계산하는가 | 집계 질의(groupBy + count) |
| **where** | 어느 이벤트 시간 구간으로 묶는가 | 6.2의 윈도우(tumbling/sliding) |
| **when** | 언제 결과를 내보내는가 | trigger + 6.3의 watermark |
| **how** | 갱신을 어떻게 반영하는가 | output mode(complete/update/append) |

  - 네 질문을 따로 답할 수 있다는 것이 핵심 → "10분 창을(where) 1분마다 갱신하되(when) 바뀐 행만 내보낸다(how)"처럼 조합이 독립적

#### 1-4. 배치 질의와의 비교

| 항목 | 배치 질의 | 스트리밍 질의 |
|---|---|---|
| 질의 작성 | DataFrame 연산 | 동일 |
| 읽기/쓰기 | `read` / `write` — 한 번 | `readStream` / `writeStream` — 계속 |
| 실행 | 호출 시 1회 후 종료 | `start()` 후 상주하며 증분 계산 |
| 중간 상태 | 없음(매번 전체 계산) | 있음(집계 상태 유지) |
| "어디까지 했나" | 사람이 관리 | 엔진이 체크포인트로 기록 |
| 실패 시 | 다시 돌림(7장, 멱등 필요) | 체크포인트에서 이어서 재개 |

  - 4장 Consumer의 커밋된 오프셋 = 스트리밍 쿼리의 체크포인트 — 도구가 바뀌어도 "진행 위치 기록" 문제는 동일

#### 1-5. 공공 사례 — output mode에 책임성이 얹힌다

○ 재난 상황판: "지금까지의 지역별 신고 건수" 계속 갱신 → update 또는 complete
○ 사후 감사용 적재: "확정된 10분 단위 집계"를 불변 파일로 → append + watermark
○ 같은 스트림·같은 질의라도 output mode가 다르면 산출물 성격이 달라짐
○ 납품 문서에 "실시간 집계를 제공한다"고 적혀 있다면 검수자가 물어야 할 세 가지:
  - trigger 주기(지연의 하한), output mode(수치가 갱신인지 확정인지), 저장소가 갱신을 감당하는 구조인지
  - 세 답이 없는 "실시간"은 명세가 아니라 수사(修辭)

### 2. tumbling window와 sliding window
#### 2-1. 왜 시간 창(window)이 필요한가

○ 무한 테이블에서 그냥 세면 수는 영원히 증가 → 운영에서 궁금한 것은 "최근 10분에 몇 건"
○ 기준 시각은 **이벤트 시간**(발생 시각)이어야 함 — 지연 도착한 민원도 "발생한 10분"에 들어가야 보고가 정확(2장)

#### 2-2. 두 가지 창 방식

○ **tumbling window(구르는 창)**
  - 시간축을 겹치지 않게 자름: 22:00–22:10, 22:10–22:20, ...
  - 모든 이벤트는 정확히 한 창에 속함
  - 용도: 정기 보고·확정 통계

○ **sliding window(미끄러지는 창)**
  - 창 크기는 같지만 일정 간격으로 밀어서 창이 겹침
  - 크기 10분·슬라이드 5분 → 한 이벤트가 정확히 2개 창에 속함(= 창 크기 ÷ 슬라이드)
  - 용도: 추세 감시·조기 경보 — tumbling은 창이 끝나야 보이지만, sliding은 중간에 증가 추이를 보여 줌

○ **세션 창(session window)** — 선택지는 셋 이상
  - 시간축을 고정 간격으로 자르지 않고, 행동이 일정 시간 끊기면 거기서 창을 끊음(경계를 시계가 아니라 데이터의 공백이 정함)
  - 민간: 클릭스트림(clickstream)에서 "세션당 페이지뷰 수", "세션 체류 시간" 집계
  - 공공: 한 민원의 접수부터 종결까지를 묶어 처리 소요를 볼 때 같은 발상
  - 이 장은 tumbling·sliding만 실측 — 다만 "10분마다"라는 요구가 실은 "한 건의 처리 과정 단위로"인 경우가 있음

○ **경계 규칙**
  - 창은 시작을 포함하고 끝을 포함하지 않음: [22:00:00, 22:10:00)
  - 정확히 22:10:00에 발생한 이벤트 → 다음 창(22:10–22:20)에 속함
  - 수작업 검산과 엔진 결과가 1건 어긋나는 흔한 원인 → 집계 명세서에 경계 포함 여부를 명시

#### 2-3. 워크드 예제(worked example) — 같은 이벤트 7건, 두 가지 창(실측)

강남구 이벤트 7건(발생 시각 22:01, 22:03, 22:04, 22:08, 22:11, 22:14, 22:24)

○ 이벤트별 창 배정

| 발생 시각 | tumbling(10분) 창 | sliding(10분·5분) 창 |
|---|---|---|
| 22:01 | 22:00–22:10 | 21:55–22:05, 22:00–22:10 |
| 22:03 | 22:00–22:10 | 21:55–22:05, 22:00–22:10 |
| 22:04 | 22:00–22:10 | 21:55–22:05, 22:00–22:10 |
| 22:08 | 22:00–22:10 | 22:00–22:10, 22:05–22:15 |
| 22:11 | 22:10–22:20 | 22:05–22:15, 22:10–22:20 |
| 22:14 | 22:10–22:20 | 22:05–22:15, 22:10–22:20 |
| 22:24 | 22:20–22:30 | 22:15–22:25, 22:20–22:30 |

○ **표 6.2** 집계 비교(실측)

| 방식 | 창별 건수 | 건수 합 |
|---|---|---|
| tumbling (10분) | 22:00–22:10 → **4**, 22:10–22:20 → **2**, 22:20–22:30 → **1** | **7** |
| sliding (10분·5분) | 21:55–22:05 → 3, 22:00–22:10 → 4, 22:05–22:15 → 3, 22:10–22:20 → 2, 22:15–22:25 → 1, 22:20–22:30 → 1 | **14** |

○ 핵심 관찰
  - tumbling 합계 = 7(이벤트 수 그대로)
  - sliding 합계 = 14 = 7 x 2 — 슬라이드가 창 크기의 절반이라 모든 이벤트가 정확히 두 창에 세어짐
  - **sliding 창의 건수를 합하면 이벤트 수가 아님** → 보고서에 실을 때 반드시 유의
  - 슬라이드를 2분으로 줄이면 합 = 7 x 5 = 35

#### 2-4. 핵심 코드

```python
F.window("event_time", "10 minutes")                 # tumbling: 슬라이드 없음
F.window("event_time", "10 minutes", "5 minutes")    # sliding: 5분마다 새 창
events.groupBy(F.window("event_time", "10 minutes"), "district").count()
```

#### 2-5. 공공 사례 — sliding 합산 함정

○ 민원 월간 보고서: 겹치지 않는 확정 수치 → tumbling
○ 상황실 "최근 1시간 신고 추이(10분마다 갱신)": → sliding
○ 민간도 같은 두 갈래: 광고는 5분 tumbling 확정 수치로 광고주에게 정산하고, 클릭률(CTR)·전환율(CVR)은 sliding으로 감시 — 급락하면 광고 소재 문제나 도착 페이지 장애
○ **실무 함정**: 두 수치를 한 문서에 섞을 때 — sliding 합계를 총 건수처럼 읽으면 이벤트가 두 배로 부풀려 보임
○ 감사에서 "대시보드는 14건인데 보고서는 7건"이라는 질문을 피하려면 → 집계표에 창 방식·크기·슬라이드를 반드시 병기

### 3. 지연 이벤트와 watermark
#### 3-1. 근본 긴장

○ 창을 빨리 확정하면 → 늦게 온 이벤트를 놓침
○ 영원히 기다리면 → 아무것도 확정 못 하고 열린 창의 상태를 메모리에 계속 유지해야 함
○ watermark는 이 긴장을 **선언 하나로** 타협

#### 3-2. watermark의 정의

○ **watermark = 관측된 최대 이벤트 시각 − 지연 허용**
  - "이보다 오래된 이벤트는 더 안 온다고 간주한다"는 기준선
  - 창의 끝이 watermark보다 오래되면 → 창을 닫고 상태 정리, 이후 지연 이벤트는 폐기

○ **핵심: watermark는 시계가 아니라 데이터에서 계산됨**
  - "지금 시각 − 10분"이 아니라 "**지금까지 본 이벤트 중 가장 최근 것의 이벤트 시각** − 10분"
  - 데이터가 안 들어오면 watermark 멈춤(창 계속 열림)
  - 데이터가 몰려 들어오면 watermark 빠르게 전진(창 빨리 닫힘)

○ 코드로는 한 줄:
```python
events.withWatermark("event_time", "10 minutes")
      .groupBy(F.window("event_time", "10 minutes"), "district").count()
```

#### 3-3. watermark 전진 과정(실측)

| 파일 처리 후 | 관측된 최대 이벤트 시각 | watermark (= 최대 − 10분) | 닫힌 창(끝 < watermark) |
|---|---|---|---|
| 파일 1 | 22:09 | 21:59 | 없음 |
| 파일 2 | 22:18 | 22:08 | 22:00에 끝나는 창까지 |
| 파일 3 | 22:24 | 22:14 | 22:10에 끝나는 창까지 |

#### 3-4. 워크드 예제 — 수용과 폐기(실측)

○ **수용된 지연 이벤트(LATE_OK)** — 발생 22:04, 파일 2에서 도착
  1. 도착 시점 watermark = 22:09(파일 1까지의 최대) − 10분 = **21:59**
  2. 속한 창: 22:00–22:10. 창의 끝(22:10) > watermark(21:59) → 창이 열려 있음
  3. 실측: 창 22:00–22:10 강남구 건수 **3 → 4로 갱신**

○ **폐기된 지연 이벤트(LATE_DROP)** — 발생 21:49, 파일 3에서 도착
  1. 도착 시점 watermark = 22:18(파일 2까지의 최대) − 10분 = **22:08**
  2. 속한 창: 21:40–21:50. 창의 끝(21:50) < watermark(22:08) → 창이 이미 닫힘
  3. 실측: 어떤 창도 갱신 안 됨, **`numRowsDroppedByWatermark`가 0 → 1로 증가**

○ **증거가 남는 채널이 다름**
  - 수용 → 집계 결과(행 갱신)에서 보임
  - **폐기 → 집계 결과에 흔적 없음** — 엔진 메트릭(`numRowsDroppedByWatermark`)으로만 확인
  - 4장 시나리오 B의 유실과 같은 구조: **사라지는 데이터는 스스로 알리지 않음**

#### 3-5. watermark = 폐기 규칙 + 청소 규칙

○ watermark가 없으면 엔진이 모든 창의 상태를 영원히 유지해야 함 — 메모리 폭발
○ watermark는 닫힌 창의 상태를 **버려도 되는 시점**이기도 함
○ watermark를 길게 잡으면: 지연 수용 증가 + 메모리에 상태를 오래 유지(비용 증가)
○ "넉넉하게 하루로 잡자"가 공짜가 아닌 이유

#### 3-6. watermark 값을 정하는 방법

○ **데이터의 실제 지연 분포를 관찰하고 정한다**
  - 4장 실측: 평균 3.5ms, 최대 110.7ms(로컬 환경이라 극히 짧음)
  - 운영에서는 이벤트 시간 vs 도착 시간 차이의 분포(중앙값·상위 분위수·최댓값)를 그려 꼬리를 덮도록 설정
  - 에어코리아처럼 원천이 30분 뒤에 게시하는 구조라면 → 그 구조적 지연이 watermark의 하한

○ **하한은 원천이, 상한은 하류 판단의 시급성이 정함**
  - 상한 예: 실시간 광고 입찰(RTB)은 수십 밀리초 안에 결정 → 지연 허용 0, 늦은 이벤트는 버림(부정확보다 늦은 결정이 비쌈)
  - 공공 재난 센서도 시급성은 같지만 "반영하지 못한 분량"을 기록으로 남겨야 함

○ **운영 중 재검토**: 폐기 카운터를 지표로 감시 → 폐기가 늘면 지연 분포가 변했다는 신호
  - `numRowsDroppedByWatermark`는 도메인 무관 운영 대시보드 지표 — 민간은 수집 지연 신호로, 공공은 거기에 더해 감사 제출 항목으로

○ **여러 스트림 조인 시 주의**
  - 지연 특성이 다른 두 소스를 합치면 → 엔진이 느린 쪽의 watermark 최솟값을 전체 기준으로 삼음
  - 빠른 소스의 창도 느린 소스만큼 늦게 닫힘

#### 3-7. Spark만의 것이 아님 — Flink 대조

○ Flink도 watermark를 같은 의미로 씀: "이벤트 시간이 T에 도달했으며 T보다 이른 이벤트는 더 안 온다"
○ 차이: Spark는 `withWatermark` 한 줄로 선언, Flink는 watermark 생성 전략을 더 세밀히 지정 가능
○ **개념을 이해하면 엔진이 바뀌어도 옮겨감** — 문법은 달라도 뼈대는 같음

#### 3-8. 공공 사례 — 잠정치와 확정치의 분리

○ 행정 보고는 "22시 대 민원 건수"처럼 정시 확정 수치를 요구 → 소급 수정은 신뢰를 흔듦
○ watermark는 **잠정치와 확정치의 경계를 데이터에서 계산된 규칙으로** 만들어 줌
  - 상황판의 잠정 수치(watermark 안 근사치) vs 마감 후 배치의 확정 수치(7장)를 서로 다른 산출물로 둠
○ 검수 관점에서 좋은 시스템: 지연을 완벽히 처리하는 시스템이 아니라, **지연 처리 규칙이 문서화되고 그 예외(폐기)가 관측되는** 시스템

### 4. 실시간 알림 조건 설계
#### 4-1. 알림 = 집계 위의 필터 + 세 가지 함정

○ 규칙 예시: "10분 창에서 같은 지역구 민원이 N건 이상이면 알린다"

○ **함정 1 — 미확정 창의 알림**
  - update 모드에서 창의 수치는 지연 이벤트로 계속 자람
  - 실측: 강남구 22:00–22:10 → 처음 3이었다가 지연분 수용으로 4
  - 빠른 알림(미확정 수치 기준)과 정확한 알림(확정 수치 기준)은 다른 설계

○ **함정 2 — 알림 중복**
  - 갱신마다 조건을 재평가하면 같은 창이 조건을 두 번 만족할 수 있음(4에서 알림, 5에서 또 알림)
  - 4·5장의 중복 문제가 알림 계층에서 재현된 것
  - 해법: 알림의 중복 제거 키(예: 창 시작 시각+지역구+규칙 ID) + 유니크 제약(5장)

○ **함정 3 — 침묵**
  - "데이터가 아예 안 옴"(수집 장애)은 어떤 창도 임계를 넘지 않으므로 조용함
  - 이벤트가 없으면 창 자체가 만들어지지 않음 → "0건이면 경보" 조건을 집계 결과 위에서 쓸 수 없음
  - 별도 장치(하트비트·유입량 하한 감시)가 필요 — 11장
  - **없는 데이터는 스스로 알리지 않음**(4장 유실, 6.3 폐기에 이은 세 번째 교훈)

#### 4-2. 워크드 예제 — 실습 데이터로 알림 따라가기

- 임계: "10분 창에서 같은 지역구 4건 이상"
  1. 파일 1 처리: 강남구 = 3. 임계(4) 미달 → 알림 없음
  2. 파일 2 처리: 지연 이벤트 수용 → 3→4 갱신. 임계 도달 — 창이 끝난 지(22:10) 한참 뒤에 발화
  3. "창 확정 후 평가"를 택하면: 파일 3 처리 후(watermark 22:14 > 창 끝 22:10) 알림 → 더 늦어짐

#### 4-3. 알림 설계표(예시)

| 항목 | 예시 | 설계 질문 |
|---|---|---|
| 대상 집계 | 10분 tumbling, 지역구별 건수 | 창 방식·크기는 목적에 맞는가 |
| 임계 | 동일 지역구 ≥ 10건 | 평시 분포 대비 몇 배인가 |
| 평가 시점 | 갱신마다(빠름) / 창 확정 후(정확) | 오경보와 지연 중 무엇이 비싼가 |
| 중복 제거 키 | 창 시작+지역구+규칙 ID | 같은 경보의 재발송을 무엇으로 막는가 |
| 침묵 감시 | 하트비트·유입량 하한 감시 | "안 오는 장애"는 누가 잡는가 |

#### 4-4. 공공 특수성 — 형평성과 책임성

○ **형평성**: 임계를 절대 건수로 잡으면 대도시만 경보, 소도시 상대적 급증은 묻힘
  - 임계를 "평시 분포 대비 몇 배"로 잡아야 함

○ **책임성**: 공공의 대피 경보 오발령은 시민 신뢰를 깎음
  - "빠른 알림"과 "정확한 알림" 중 무엇을 택했는지, 누가 승인했는지 알림마다 문서로 남겨야 함

○ 재난 초기 대응 예시
  - 못 보내는 비용 > 잘못 보내는 비용 → 평가 시점을 "갱신마다(빠름)"로 두고 오경보 감수
  - 언론 브리핑용 수치 → 확정 후에만 제공
  - 같은 스트림에서 두 정책이 공존 → 각 알림이 어느 정책인지 문서화, 수신자가 성격을 앎

#### 4-5. 역방향 — 이 장의 설계를 민간 현장으로

○ **실시간 추천의 피처 집계**
  - 최근 10분 조회 범주를 sliding 창으로 집계 → 추천 모델 입력
  - 출력 구조는 실습 6.1과 동일: update 모드 → 피처 스토어(8장)에 키 기반 Upsert(5장)
  - 바뀌는 것은 창 크기의 근거 — 공공은 "보고 주기 10분", 추천은 "관심이 유지되는 시간"

○ **사기 탐지 파이프라인** — 4-3의 알림 설계표를 그대로 채우는 현장
  - Kafka 수집(4장) → 1분 tumbling, 카드 번호별 집계 → 임계 "같은 카드, 1분 안에 3건 이상"
  - 중복 제거 키 = 카드 번호 + 창 시작 시각 + 규칙 ID(공공의 "지역구" 자리에 "카드")
  - 임계 결정 = 정밀도(precision)와 재현율(recall)의 비용 비교 — 낮추면 정상 거래를 막고, 높이면 사기를 놓침

○ **광고 입찰의 캠페인 예산 소진 감시** — 평가 시점이 공공과 반대로 기움
  - 캠페인 ID별 5분 tumbling → 남은 예산 대비 소진 속도 → 임계 초과 시 입찰가 인하·캠페인 정지
  - 지연 허용 0으로 즉시 확정이 합리적 — 노출 몇 건 누락보다 예산 초과가 비쌈

○ **A/B 테스트 실시간 대시보드** — 6.2의 함정 재현
  - 전환율을 10분 sliding으로 비교 → 창끼리 더하면 두 배(감사 지적 대신 잘못된 실험 판정)
  - 대응 동일: 확정 통계는 tumbling + 배치(7장), 대시보드 수치에는 "잠정 추세" 표기

○ **관통하는 하나**
  - 창 방식·크기 / watermark 지연 허용값 / output mode / 알림의 임계·평가 시점·중복 제거 키 — 네 결정은 어느 도메인에서도 똑같이 내림
  - **근거만 도메인이 바꿈** — 공공: 감사·형평성·법적 보고 의무 / 민간: 매출·비용·응답 속도
  - 방향은 비대칭: 공공 설계를 민간으로 옮길 때는 증거의 겹을 벗겨도 손해 없음 — 폐기 카운터는 수집 품질 지표로, 알림 승인 기록은 오경보 원인 분석 자료로 남음

### 실습 6.1: 지역별 민원 이벤트 윈도우 집계(난이도 ★★★☆☆)

#### 실습 목표

#### 데이터 표기
- 민원 이벤트 14건은 시뮬레이션 입력(개인정보 포함 실제 민원 사용 불가)
- 관찰 대상은 데이터 내용이 아니라 **실제 엔진의 윈도우·watermark 동작**

- 브로커 불필요 — 파일 소스로 단독 실행

#### 실행 명령

#### 입력 구성

| 파일 | 이벤트(발생 시각 기준) | 실험 의도 |
|---|---|---|
| 파일 1 | 정시 6건: 강남 22:01·22:03·22:08, 마포 22:02·22:09, 관악 22:05 | 창 22:00–22:10 초기 집계 |
| 파일 2 | 정시 4건: 강남 22:11·22:14, 마포 22:12·22:18 + **LATE_OK(강남, 발생 22:04)** | 수용 관찰 |
| 파일 3 | **LATE_DROP(마포, 발생 21:49)** + 정시 2건: 관악 22:21, 강남 22:24 | 폐기 관찰 |

#### 핵심 코드

```python
counts = (events.withWatermark("event_time", "10 minutes")
          .groupBy(F.window("event_time", "10 minutes"), "district").count())
query = counts.writeStream.outputMode("update").foreachBatch(sink).start()
query.processAllAvailable()   # 파일 투입 후 배치 경계 고정
```

_전체 코드: practice/chapter6/code/6-1-streaming-window-aggregation.py_

#### 실행 중 확인 체크리스트
- [ ] 파일 1 처리 후: 창 22:00–22:10에 지역구 3개 행이 나왔는가(초기 집계)
- [ ] 파일 2 처리 후: 창 22:00–22:10 강남구가 3에서 4로 **다시** 출력됐는가(지연 수용)
- [ ] 파일 3 처리 후: 21:40–21:50 창이 출력에 **없고**, dropped 카운터가 1인가(지연 폐기)
- [ ] sliding 결과의 건수 합이 tumbling의 두 배인가(중첩 창의 정의)

#### 실행 결과(실측)

○ micro-batch별 출력(update 모드 — 바뀐 행만)
  - 배치 0(파일 1): 창 22:00–22:10 → 강남구 3, 마포구 2, 관악구 1
  - 배치 2(파일 2): 창 **22:00–22:10 → 강남구 4**(지연분 수용으로 갱신), 창 22:10–22:20 → 강남구 2, 마포구 2
  - 배치 4(파일 3): 창 22:20–22:30 → 강남구 1, 관악구 1 — 21:40–21:50 창은 **어디에도 없음**
  - 배치 1·3·5: 출력 0행(파일 처리 직후 도는 빈 확인 배치)

○ 배치 2 출력 읽는 법
  - "22:00–22:10 강남구 4" = **과거 창의 갱신**(지연 수용 결과)
  - "22:10–22:20"의 두 행 = **새 창의 첫 등장**
  - update 모드는 이 둘을 구분 없이 "바뀐 행"으로 내보냄 → 받는 쪽은 5장의 Upsert로 통일

**표 6.4** 지연 이벤트 처리 평가표(실측 — watermark 10분)

| 이벤트 | 발생(이벤트 시간) | 도착 시점 watermark | 속한 창 | 판정 | 증거(실측) |
|---|---|---|---|---|---|
| LATE_OK | 22:04 | 21:59 (= 22:09 − 10분) | 22:00–22:10 (끝 > watermark) | **수용** | 강남구 창 건수 3 → 4 갱신 |
| LATE_DROP | 21:49 | 22:08 (= 22:18 − 10분) | 21:40–21:50 (끝 < watermark) | **폐기** | numRowsDroppedByWatermark 0 → 1 |

#### 관찰 과제

○ **관찰 1**: 수용과 폐기의 증거 채널
  - 수용은 집계 행 갱신(3→4)으로 결과에 보임
  - 폐기는 결과에 흔적 없음, 엔진 메트릭의 카운터(1)로만 확인 → 폐기 모니터링 없이 운영하면 지연 데이터 손실을 인지할 방법이 없음

○ **관찰 2**: update 모드의 중복 출력
  - 같은 키(창 22:00–22:10, 강남구)의 행이 두 번 출력됨(3, 그리고 4)
  - naive INSERT로 받으면 같은 창이 두 행이 되어 왜곡 → 5장 Upsert가 필요

○ **관찰 3**: watermark는 "얼마나 늦었나"가 아니라 "엔진이 최근에 무엇을 봤나"에서 계산
  - 스트림 전체가 함께 늦으면(수집 장애 후 몰아서 도착) watermark도 함께 늦게 전진 → 폐기 안 됨
  - 폐기는 "일부만 유독 늦을 때" 생김

○ **관찰 4**: checkpoint/ 디렉터리
  - 스트리밍 쿼리가 "어디까지 처리했고 상태가 무엇인지"를 남긴 기록
  - 4장 커밋된 오프셋의 스트리밍판 — 운영에서는 장애 복구의 근거

○ **환경 주의사항**: 시스템 기본 python3와 venv의 파이썬이 다르면 `PYTHON_VERSION_MISMATCH` 오류 발생 가능
  - 해법: 실습 코드 상단의 `os.environ.setdefault("PYSPARK_PYTHON", sys.executable)`
