# 제14장 통합 사례 연구: 공공 실시간 민원/재난 시스템

---

## [전반부] 이론 강의 (50분)

---

### 학습 목표

- DE(데이터 엔지니어링)와 MLOps의 부품을 엔드투엔드(end-to-end) 운영 흐름으로 연결하는 구조를 이해한다
- 연결부에서 생기는 고장(중복·오염·부분 실패)을 격리하는 원칙을 실측으로 설명한다
- 장애 시나리오와 대응 절차를 runbook(장애 대응 절차서)으로 문서화하고 드릴(모의 장애 훈련)로 검증한다
- 인수 검수표를 실행 증거에서 자동 생성하는 방식을 이해한다
- 앞 장들이 각각 정한 계층별 결정을 한 표로 모아 충돌 지점을 찾고, 그 조합이 깨지는 조건을 적는다

### 1. 시스템 요구사항 정의 (9분)

#### 1-1. 기능 요구와 비기능 요구

○ **가상 발주 상황**
  - "구 단위 민원 접수를 실시간으로 수집·집계하고, 다음 날 민원 규모를 예측해 자원 배치 판단을 지원하는 시스템"

○ **기능 요구** — 시스템이 "무엇을 하는가"
  - 민원 이벤트 수집(스트림), 정제·표준코드 매핑, 일별 확정 집계, 익일 예측, 예측 사후 채점

○ **비기능 요구** — "어떤 조건에서도 하는가"
  - 이벤트를 유실하지 않는다
  - 중복 접수·재전송이 집계를 오염시키지 않는다
  - 구성 요소 하나의 장애가 전체를 멈추지 않는다
  - 모든 판단이 사후 감사 가능하다
  - 폐쇄망에서도 배포된다

○ **핵심**: 기능은 시연으로 확인되지만, 비기능은 **고장을 일부러 내 봐야** 확인된다 → 14.5 드릴이 그 확인 절차

**표 14.1** 요구사항 정의표

#### 1-2. "실시간"의 정직한 정의

○ 발주 문서의 "실시간"은 두 속도로 나누어 정의해야 한다
  - **접수는 스트림**: 이벤트가 오는 대로 수신·반영(초 단위)
  - **확정과 예측은 일 배치**: 하루가 마감되어야 집계가 확정되고 예측이 나감
  - 3장에서 배운 하이브리드 구조가 이것 — 같은 시스템 안에 두 개의 시계가 있음
  - 재난 프레이밍이면 분 단위 창(6장 윈도우 집계)이 필요해 아키텍처 선택지가 달라짐

○ **마감 주기는 도메인이 정한다** — 이커머스는 일 단위, 결제 사기 탐지는 초 단위, 물류 재고는 시간 단위
  - 정하는 근거가 다름: 공공은 행정 주기·감사 단위, 민간은 손실이 얼마나 빨리 커지는가
  - 계약의 형태는 같음: 민간은 이벤트 발생→산출물 확정까지를 E2E 지연으로 정의해 SLA(Service Level Agreement, 서비스 수준 계약)에 적는다
  - 표 14.1의 셋째 열이 그 SLA를 무엇으로 확인할지 적어 둔 자리

#### 1-3. 공공 사례

○ 공공 정보시스템 구축·운영 지침(행정안전부)에는 AI 특화 항목(모델 신원 확인, 드리프트 감시, 재학습 조건)이 아직 명세되지 않음
  - 발주자와 수행사가 스스로 채워야 하는 공백 → 표 14.1처럼 비기능 요구를 발주 문서에 명시

### 2. 부품의 재조립과 교차 검증 (16분)

#### 2-1. 아키텍처: 부품의 재조립

○ 통합 MVP(Minimum Viable Product — 핵심 경로만 포함한 최소 운영 시스템) 구조

```text
[ingester]──발행──▶ [Kafka: complaints.raw] ──소비──▶ [processor]──HTTP──▶ [model-api]
 (수집)                 (단일 파티션 토픽)            │  정제(7장 규약)         (champion 고정)
                                                     │  멱등 반영(5장 UPSERT)
                                                     ▼
                                       [/data/out]: 일별 확정 집계·예측 스냅샷·격리 큐
                                                     ▼
                                       [monitor]: 통합 리포트 + 인수 검수표(자동 생성)
```

○ ML 시스템에서 모델 코드는 전체의 작은 부분이고, 유지 부담은 주변 구성(데이터 흐름·연결·설정)에서 온다(Sculley et al., 2015)

**표 14.2** 컴포넌트 통합 매핑

| 부품 | 원 장 | MVP에서의 형태 | 축소된 것 |
|---|---|---|---|
| 이벤트 수집 | 1·4장 | ingester가 7장 민원 원천을 Kafka로 발행 | 실제 접수 채널 → 파일 재생 |
| 메시지 버스 | 3·4장 | Kafka+Zookeeper, 단일 파티션 | 3파티션 → 1(마감 순서 보장) |
| 중복 방지 | 5장 | complaint_id UPSERT(SQLite) | 동일 — 5장 규약 그대로 |
| 정제·매핑 | 2·7장 | 공백·약칭 보정, 표준코드 매핑, 4갈래 분리 보고 | 동일 — 7장 규약 그대로 |
| 일 마감·확정 | 7장 | day_close 제어 이벤트 → 집계 확정 → `_SUCCESS` | Airflow 스케줄 → 제어 이벤트 |
| 피처 | 8장 | 당일 확정 건수 = 익일 예측의 입력(전일 건수) | Feast → 집계 산출물 직접 계산 |
| 모델·레지스트리 | 9장 | bootstrap이 동일 지문 데이터로 재구성, champion 승격 | 공용 추적 서버 → 로컬 SQLite |
| 서빙 | 10장 | app.py 바이트 동일 복사 + champion 고정 이미지 | shadow는 off(단순화) |
| 감시 | 11장 | 지연 레이블 채점(일별 MAE)·운영 카운터·검수표 | 대시보드 → JSON 리포트 |

#### 2-2. 하루의 일생 — 흐름 한 바퀴

○ **스트림의 시계**(이벤트 도착 즉시)
  - ingester가 민원 20건을 토픽에 발행
  - processor가 정제: 공백 보정, 약칭 보정("강남"→"강남구"), 미기재·미매핑 분리, complaint_id 기준 UPSERT

○ **배치의 시계**(일 마감 후)
  - ingester가 day_close 제어 이벤트 발행
  - processor가 확정 집계(마포 5·관악 5·강남 8), 품질 회계 기록, `_SUCCESS` 마커 작성
  - 확정된 오늘 건수를 입력으로 모델 API 호출 → 내일 예측 생성
  - 다음 날 마감에서 어제 예측을 채점(지연 레이블 평가)

○ 이 리듬(확정 → 채점 → 예측)이 매일 반복됨

#### 2-3. 재조립의 증명: 5개의 교차 검증

○ "옮겨 붙이다 뭔가 달라지지 않았나"에 값으로 답한다

**표 14.3** 재조립 교차 검증 5종

| # | 검증 항목 | 기대값(원 장 커밋 실측) | 이 장 실측 | 판정 |
|---|---|---|---|---|
| 1 | 서빙 앱 동일성 | 10장 app.py sha256 `ec7ec653…` | 복사본 sha256 일치 | 일치 |
| 2 | 훈련 데이터 동일성 | 9장 피처 지문 `96f6b6b3…` | bootstrap 지문 일치 | 일치 |
| 3 | 집계 재구현 | 7장 확정치 3일(마포5·관악5·강남8 등) | 스트림 경로 집계 동일 | 3일 전부 일치 |
| 4 | 예측 동일성 | 9·10장 champion 예측 6.0 | 호출 9건 전부 6.0 | 일치 |
| 5 | 평가 동일성 | 9장 훈련 MAE 1.0 | 지연 채점 6건 전체 MAE 1.0 | 일치 |

○ 검증 3이 핵심: 7장은 배치(Airflow 파일 처리)로, 이 장은 스트림(Kafka 소비)으로 집계했는데 확정치가 같다
  - 처리 방식이 바뀌어도 업무 규칙(정제·멱등 키·집계 기준)이 같으면 결과가 같아야 한다
  - Lambda 아키텍처(3장)의 배치·스트림 불일치 문제를 검증 가능한 형태로 다룬 것

○ 검증 5: 채점된 예측 6건은 9장 훈련 쌍과 같은 데이터·같은 모델이므로 지연 MAE = 훈련 MAE = 1.0은 필연

○ **같은 대조를 민간에서는 파이프라인 교체 때 쓴다** — 웨어하우스 이전, 배치→스트림 전환 시 원본·대상 집계를 맞춰 보고 불일치면 배포를 자동 차단(회귀 검증)
  - 절차는 표 14.3과 같고, 결과를 다루는 방식만 다름 — 공공은 감사 증빙으로 보관, 민간은 배포 차단 근거로 쓰고 버림

#### 2-4. 피처 스토어 없이 피처 일관성이 유지되는 조건

○ 이 MVP에는 8장의 Feast가 없다
  - 확정 집계가 피처의 단일 진실 원천이고, `_SUCCESS` 마커가 "피처로 써도 된다"는 신호
  - 피처 1종(전일 건수), 소비자 1개(이 모델)일 때만 성립하는 축소
  - 피처가 수십 개, 소비 모델이 여럿이면 8장(피처 스토어)·13장(피처 거버넌스)이 필요

#### 2-5. 계층별 결정은 서로 모순되지 않아야 한다

○ 통합에서 터지는 것은 부품의 결함이 아니라 **계층별 결정의 불일치**
  - 4장 파티션 수·키 / 5장 중복 제거 키 / 6장 창·워터마크 / 7장 배치 주기·마커 / 9장 승격 게이트 / 11장 감시 임계·판정 주기 / 13장 접근 등급
  - 각 값은 자기 장 안에서 근거가 분명했으나, 한 시스템에 모으면 서로를 무효로 만드는 조합이 나옴

○ **이 MVP에서 실제로 걸린 조합 3가지**
  - 파티션 3개(4장 처리량) ↔ 일 마감(7장: 그날 이벤트가 전부 도착한 뒤 마감 신호) → 파티션 1개로 줄임(처리량을 마감 순서와 맞바꿈, 표 14.5에 기록)
  - 승격 게이트 MAE 1.05(9장) ↔ 하루 표본 3건(11장) → 표본 3건 MAE로 게이트를 판정하면 하루의 우연이 재학습을 부름(7/3의 1.3333). 이 MVP는 판정 주기를 늘려 "감시 강화 신호"로만 읽음
  - 멱등 키 `complaint_id`(5장) ↔ 예측 재시도 키 (대상일, 지역)(이 장) → 서로 다른 층인데 둘 다 멱등이라 D3 재시도가 안전. 한쪽만 아니어도 복구가 새 오염을 만듦

○ **공통 형태**: 한 계층의 최적값이 다른 계층의 전제를 깬다
  - 통합 설계의 첫 작업은 새 값을 정하는 것이 아니라, 정해진 값을 한 표에 모아 충돌을 찾는 것(실습 1단계)

### 3. 정책 의사결정 지원과 정책 분석·평가 (9분)

#### 3-1. 예측의 소비자는 시스템이 아니라 사람이다

○ 공공 AI는 **정책 결정 시스템이 아니라 정책 의사결정 지원** — 예측은 판단의 입력이고, 판단과 집행은 사람이 한다

○ 경계 설계의 세 요소
  - **자동 집행 금지 지점**: 예측이 임계를 넘어도 시스템이 집행하지 않음 — 기록만 남김
  - **사람 개입 지점**: "왜 6건인가"에 대한 근거 — champion(v1)은 평균 예측기라서 "최근 평균"이 전부
  - **평가지표 주입**: 재학습 게이트(9장 1.05)와 감시 임계(11장)를 운영 조직 밖에서 정함(17장)

#### 3-2. 운영 로그가 정책 평가의 원자료가 된다

○ 매일 남기는 기록(예측·실제·절대 오차·일별 MAE)은 운영 감시 자료이자 정책 평가의 원자료
  - 운영의 언어: "감시 강화 신호" (단, 하루 표본 3건 — 소표본 주의)
  - 평가의 언어: "이 도구의 유효성을 어느 주기·어느 표본으로 재판정할 것인가"

○ **예측 오차의 평가 ≠ 정책효과 평가**
  - "민원 건수를 잘 맞혔다"와 "이 예측으로 행정이 개선되었다"는 다른 질문
  - 후자는 개입·비교집단·시차를 다루는 정책 분석 방법론이 필요
  - MLOps 지표를 정책효과 증거로 승격시키는 비약이 공공 AI 보고서의 흔한 오류

### 4. MVP 범위와 장애 시나리오 (16분)

#### 4-1. MVP 범위 표

○ MVP의 가치는 작음이 아니라 **경계의 명시** — 무엇을 뺐는지, 왜 뺐는지, 언제 다시 넣는지를 문서로 남겨야 한다

**표 14.5** 통합 MVP 포함/제외 범위표(주요 항목)

| 항목 | 판정 | 대체물 | 운영 승격 시 |
|---|---|---|---|
| 이벤트 버스(Kafka) | 포함 | 단일 브로커·단일 파티션 | 다중 파티션·복제 |
| 멱등 소비 | 포함 | complaint_id UPSERT | 동일 원칙, 저장소만 교체 |

| 모델 서빙 | 포함 | champion 고정 이미지 1대 | 복수 인스턴스 + 무중단 교체 |
| 워크플로 스케줄러 | 제외 | 오케스트레이션 스크립트 | Airflow(실패 전파·재실행 이력) |
| 피처 스토어 | 제외 | 확정 집계 직접 계산 | 피처 다종·다소비자 시 Feast |

#### 4-2. 장애 드릴 3종 — 카오스 엔지니어링의 공공 적용

○ **카오스 엔지니어링(chaos engineering)**: 분산 시스템에 의도적으로 장애를 주입하고 실험하는 규율
  - 넷플릭스의 Chaos Monkey가 대표 사례 — 프로덕션 인스턴스를 무작위로 종료해 복원력을 검증
  - 5원칙: ① 정상 상태 가설 ② 실세계 사건 주입 ③ 프로덕션 실험 ④ 자동화 ⑤ 폭발 반경 최소화
  - 상용 도구: Gremlin, AWS Fault Injection Simulator, LitmusChaos — 도구가 맡는 것은 주입 자동화와 폭발 반경 제한뿐이고, 계획된 시나리오와 감사 가능한 이력은 운영 규칙이 만든다

○ **공공 적용**: 민간의 "프로덕션 무작위" → 공공의 "계획된 드릴 + 감사 가능한 이력"
  - 프로덕션 대신 스테이징·드릴 환경에서 실행
  - 무작위 대신 계획된 시나리오로 실행
  - 드릴 이력을 기록으로 남김

○ **드릴 D1: 오염 이벤트**
  - 정상 이벤트 사이에 JSON 파싱 불가 1건 주입
  - 실측: 격리 큐(quarantine.jsonl)에 원문과 사유(json_parse_error) 보존, 파이프라인 지속, 집계 온전
  - 원칙: 나쁜 데이터는 버리지도, 통과시키지도 않는다. **분리해서 보존한다**(2장)
  - 민간 대응물: DLQ(Dead Letter Queue, 처리에 실패한 메시지를 따로 모아 두는 큐) — 이름만 다르고 판단은 같다
  - 운영 지표도 같음: 격리 건수(늘면 상류 형식이 바뀐 것)와 체류 시간(길면 재처리 절차가 안 도는 것)

○ **드릴 D2: 중복 재전송**
  - 7/2 이벤트 18건 발행 후 마지막 10건을 한 번 더 발행(at-least-once 재현)
  - 실측: 물리 수신 28건 → 고유 17건(중복 흡수 11건) → 매핑 집계 16건(7장 확정치와 동일)
  - 수송 계층 중복(재전송 10건)과 업무 계층 중복(접수 1건)이 같은 멱등 키로 흡수됨
  - 회계 보존식: 물리 28 = 고유 17 + 흡수 11, 고유 17 = 매핑 16 + 미기재 0 + 미매핑 1
  - 민간에서는 같은 키가 주문 ID·거래 ID — 흡수에 실패하면 곧바로 이중 결제·이중 출고
  - 민간 지표 **중복 처리율**(전체 대비 흡수 비율): 평소 수준을 벗어나면 상류 재전송 로직이 바뀐 신호. 회계 보존식이 그 지표의 원자료

○ **드릴 D3: 의존 서비스 중단**
  - 7/3 마감 직전에 모델 API 컨테이너 정지 후 마감 진행
  - 실측: 집계 확정 + 어제 예측 채점(모델 불필요)은 완료, 내일 예측(모델 필요)만 `pending_retry`로 기록
  - **부분 실패 격리**: 실패를 가장 작은 단위(예측 3건)로 잘라 상태로 기록, 나머지는 확정
  - 복구: 컨테이너 재기동 → /health 확인 → predict_retry 발행 → 대기 3건 성공 → 대기 0건으로 수렴
  - 재시도가 안전한 이유: 예측 기록이 (대상일, 지역) 키의 멱등 쓰기
  - 민간 표준 부품은 서킷 브레이커(circuit breaker, 실패가 이어지는 의존 호출을 일정 시간 끊는 장치) — 이 MVP는 그 자리에 `pending_retry` 기록을 둠(끊지 않고 실패를 값으로 남김)
  - 계약의 언어: 가용률과 MTTR(Mean Time To Recovery, 평균 복구 시간) — 99.9%는 연간 8.7시간 중단만 허용. D3의 재기동→재시도→대기 0건이 MTTR을 재는 구간

#### 4-5. 역방향 — 이 장의 통합 설계를 민간 현장으로

○ **이커머스 주문 파이프라인** — 구조가 거의 그대로 겹침
  - 주문 ID 멱등 소비 → 일별 마감으로 매출·환불·반품 확정 → 확정치로 익일 수요 예측
  - "확정 → 채점 → 예측"이 "매출 확정 → 예측 정확도 채점 → 익일 재고 예측"으로 이름만 바뀜
  - 도구도 겹침: Kafka·Airflow·MLflow + Flink 또는 Spark Structured Streaming

○ **핀테크 실시간 결제 사기 탐지** — 스트림의 시계가 초 단위로 당겨진 경우
  - 일 마감이라는 접점이 사라지고 판정이 곧 집행 → D3가 훨씬 무겁다
  - `pending_retry`로 미룰 수 없으므로 장애 시 기본 정책(전부 허용/전부 거부/최근 판정 재사용)을 미리 정해야 함
  - 공공의 "집행은 사람이 한다"는 경계가 성립하지 않고, 그 자리를 기본 정책이 대신함

○ **물류 추적** — 격리 큐가 가장 바쁜 현장
  - GPS 오류, 통신 단절 후 몰려 들어오는 비정상 좌표가 섞임
  - `_SUCCESS` 마커 = "이 구간의 배송 상태가 확정되었다", 격리한 좌표를 뺀 나머지로 경로 재구성

○ **관통하는 하나** — 계층 경계의 위치 / 멱등 키의 선택 / 실패를 자를 단위 / 확정의 신호, 이 네 결정은 어느 현장에서도 똑같이 내린다. **근거만 도메인이 바꾼다**(공공: 감사·형평성·법적 의무 / 민간: 매출·비용·SLA)
  - 인수 검수표도 같음 — 민간에서는 CI/CD의 E2E 테스트 스위트가 되어 배포 전 자동 실행되고, 배포 성공률·롤백 비율이 그 커버리지를 되짚는 지표가 됨. 공공에서는 같은 표가 계약 이행 증빙으로 남음

○ **방향은 비대칭** — 민간→공공은 증거 산출·드릴 이력이 한 겹 얹히지만, 공공→민간은 그 겹을 벗겨도 손해가 없다(검수표 → 배포 게이트, 드릴 이력 → 신뢰성 보고서, 회계 보존식 → 정산 정확도)

3. **스모크**: `predict(전일 9) → 6.0`과 `잘못된 입력 → 422`
4. **2일차 마감**: `물리수신 28 / 고유 17 (중복 흡수 11) → 매핑 16`(드릴 D2)
5. **드릴 D3**: `마감 확정(_SUCCESS) + 예측 대기 3건` → `복구 수렴: 대기 0건`
6. **인수 검수표**: 16항목 전부 `[PASS]`, 마지막 줄 `CH14_RUN_PASS`
7. **설계 선행**: 실행 전에 표 14.8과 드릴 예측표를 적어 두었는가(실행 후에 적으면 대조가 성립하지 않는다)

#### 3단계 대조(10분) — 예측과 실측 맞춰 보기

○ 1단계 드릴 예측표의 "실제" 칸을 위 실측 표와 표 14.6의 값으로 채운다. 예측이 어긋나는 자리가 셋이다

○ **D1을 집계 오차로 예측했다면** — 격리 큐를 셈에 넣지 않은 것
  - 실측: 7/3 매핑 20건 온전, 오염 1건은 집계 밖 파일에 남음
  - 오염이 집계를 흔드는 것은 격리 큐가 없을 때뿐. 있으면 계층 옆으로 빠진다

○ **D2를 집계 증가로 예측했다면** — 물리 수신과 고유를 같은 것으로 본 것
  - 실측: 물리 28 → 고유 17 → 매핑 16, 7장 확정치와 동일. 늘어난 것은 수신 건수뿐
  - 배울 것은 "중복이 없었다"가 아니라 **중복이 있었는데도 값이 같다는 것을 회계로 증명할 수 있다**는 점

○ **D3를 마감 실패로 예측했다면** — 그 예측이 오히려 대부분의 시스템에서 맞다
  - 마감이 살아남은 것은 운이 아니라 확정 가능한 일과 모델이 필요한 일을 나눠 둔 설계 때문
  - 예측이 빗나간 지점이 곧 설계가 한 일이다

○ 표 14.8의 마지막 행("이 조합이 깨지는 조건")을 다시 쓴다 — 파티션을 3개로 올리면 일 마감이 어느 조건에서 틀리는지, 표본 3건 MAE로 게이트를 판정하면 7/3의 1.3333이 무엇을 부르는지를 실측 옆에 적는다. **제출본은 이 수정을 거친 최종본**

#### 4단계 검수(5분) — 관찰 과제

○ **관찰 1**: 드릴 D2에서 중복 흡수 11건의 내역
  - 수송 계층 중복(재전송 10건)과 업무 계층 중복(접수 1건)은 원인이 다른데, 소비자 앞에서는 같은 complaint_id가 다시 온 것
  - 5장의 멱등 키(UPSERT)가 원인 구분 없이 둘 다 무해화하고, seen_count에 관찰 흔적만 남김

○ **관찰 2**: 드릴 D3에서 부분 실패 격리가 가능했던 이유
  - 집계 확정(모델 불필요)과 예측(모델 필요)을 분리해 설계
  - 실패를 값(`pending_retry`)으로 기록하고 나머지를 확정
  - 복구의 안전성은 복구 코드가 아니라 평시의 멱등 설계에서 나옴

○ **관찰 3**: 검증 3(배치·스트림 경로의 집계 일치)이 실패한다면
  - 정제 규칙이 다르면: 한쪽에서 약칭 보정이 누락되어 건수가 어긋남
  - 멱등 키가 다르면: 중복 흡수 건수가 달라져 고유 건수가 다름
  - 집계 기준이 다르면: 같은 고유 건수에서 다른 합계가 나옴
