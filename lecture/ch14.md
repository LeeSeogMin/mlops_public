# 제14장 통합 사례 연구: 공공 실시간 민원/재난 시스템

---

## [전반부] 이론 강의 (50분)

---

### 학습 목표

- DE(데이터 엔지니어링)와 MLOps의 부품을 엔드투엔드 운영 흐름으로 연결하는 구조를 이해한다
- 연결부에서 생기는 고장(중복·오염·부분 실패)을 격리하는 원칙을 실측으로 설명한다
- 장애 시나리오와 대응 절차를 runbook(장애 대응 절차서)으로 문서화하고 드릴(모의 장애 훈련)로 검증한다
- 인수 검수표를 실행 증거에서 자동 생성하는 방식을 이해한다

### 1. 시스템 요구사항 정의 (10분)

#### 1-1. 기능 요구와 비기능 요구

○ **가상 발주 상황**
  - "구 단위 민원 접수를 실시간으로 수집·집계하고, 다음 날 민원 규모를 예측해 자원 배치 판단을 지원하는 시스템"

○ **기능 요구** — 시스템이 "무엇을 하는가"
  - 민원 이벤트 수집(스트림), 정제·표준코드 매핑, 일별 확정 집계, 익일 예측, 예측 사후 채점

○ **비기능 요구** — "어떤 조건에서도 하는가"
  - 이벤트를 유실하지 않는다
  - 중복 접수·재전송이 집계를 오염시키지 않는다
  - 구성 요소 하나의 장애가 전체를 멈추지 않는다
  - 모든 판단이 사후 감사 가능하다
  - 폐쇄망에서도 배포된다

○ **핵심**: 기능은 시연으로 확인되지만, 비기능은 **고장을 일부러 내 봐야** 확인된다 → 14.5 드릴이 그 확인 절차

**표 14.1** 요구사항 정의표

| 구분 | 요구 | 검증 방법(실측) | 근거 장 |
|---|---|---|---|

| 기능 | 정제·표준코드 매핑 | 매핑 18/16/20, 미기재·미매핑 분리 보고 | 2·7장 |

| 비기능 | 폐쇄망 배포 | 모델을 이미지에 고정, 실행 중 외부 참조 없음 | 10장 |

#### 1-2. "실시간"의 정직한 정의

○ 발주 문서의 "실시간"은 두 속도로 나누어 정의해야 한다
  - **접수는 스트림**: 이벤트가 오는 대로 수신·반영(초 단위)
  - **확정과 예측은 일 배치**: 하루가 마감되어야 집계가 확정되고 예측이 나감
  - 3장에서 배운 하이브리드 구조가 이것 — 같은 시스템 안에 두 개의 시계가 있음
  - 재난 프레이밍이면 분 단위 창(6장 윈도우 집계)이 필요해 아키텍처 선택지가 달라짐

#### 1-3. 공공 사례

○ 공공 정보시스템 구축·운영 지침(행정안전부)에는 AI 특화 항목(모델 신원 확인, 드리프트 감시, 재학습 조건)이 아직 명세되지 않음
  - 발주자와 수행사가 스스로 채워야 하는 공백 → 표 14.1처럼 비기능 요구를 발주 문서에 명시

### 2. 부품의 재조립과 교차 검증 (15분)

#### 2-1. 아키텍처: 부품의 재조립

○ 통합 MVP(Minimum Viable Product — 핵심 경로만 포함한 최소 운영 시스템) 구조

```text
[ingester]──발행──▶ [Kafka: complaints.raw] ──소비──▶ [processor]──HTTP──▶ [model-api]
 (수집)                 (단일 파티션 토픽)            │  정제(7장 규약)         (champion 고정)
                                                     │  멱등 반영(5장 UPSERT)
                                                     ▼
                                       [/data/out]: 일별 확정 집계·예측 스냅샷·격리 큐
                                                     ▼
                                       [monitor]: 통합 리포트 + 인수 검수표(자동 생성)
```

○ ML 시스템에서 모델 코드는 전체의 작은 부분이고, 유지 부담은 주변 구성(데이터 흐름·연결·설정)에서 온다(Sculley et al., 2015)

**표 14.2** 컴포넌트 통합 매핑

| 부품 | 원 장 | MVP에서의 형태 | 축소된 것 |
|---|---|---|---|
| 이벤트 수집 | 1·4장 | ingester가 7장 민원 원천을 Kafka로 발행 | 실제 접수 채널 → 파일 재생 |
| 메시지 버스 | 3·4장 | Kafka+Zookeeper, 단일 파티션 | 3파티션 → 1(마감 순서 보장) |
| 중복 방지 | 5장 | complaint_id UPSERT(SQLite) | 동일 — 5장 규약 그대로 |
| 정제·매핑 | 2·7장 | 공백·약칭 보정, 표준코드 매핑, 4갈래 분리 보고 | 동일 — 7장 규약 그대로 |
| 일 마감·확정 | 7장 | day_close 제어 이벤트 → 집계 확정 → `_SUCCESS` | Airflow 스케줄 → 제어 이벤트 |
| 피처 | 8장 | 당일 확정 건수 = 익일 예측의 입력(전일 건수) | Feast → 집계 산출물 직접 계산 |
| 모델·레지스트리 | 9장 | bootstrap이 동일 지문 데이터로 재구성, champion 승격 | 공용 추적 서버 → 로컬 SQLite |
| 서빙 | 10장 | app.py 바이트 동일 복사 + champion 고정 이미지 | shadow는 off(단순화) |
| 감시 | 11장 | 지연 레이블 채점(일별 MAE)·운영 카운터·검수표 | 대시보드 → JSON 리포트 |

#### 2-2. 하루의 일생 — 흐름 한 바퀴

○ **스트림의 시계**(이벤트 도착 즉시)
  - ingester가 민원 20건을 토픽에 발행
  - processor가 정제: 공백 보정, 약칭 보정("강남"→"강남구"), 미기재·미매핑 분리, complaint_id 기준 UPSERT

○ **배치의 시계**(일 마감 후)
  - ingester가 day_close 제어 이벤트 발행
  - processor가 확정 집계(마포 5·관악 5·강남 8), 품질 회계 기록, `_SUCCESS` 마커 작성
  - 확정된 오늘 건수를 입력으로 모델 API 호출 → 내일 예측 생성
  - 다음 날 마감에서 어제 예측을 채점(지연 레이블 평가)

○ 이 리듬(확정 → 채점 → 예측)이 매일 반복됨

#### 2-3. 재조립의 증명: 5개의 교차 검증

○ "옮겨 붙이다 뭔가 달라지지 않았나"에 값으로 답한다

**표 14.3** 재조립 교차 검증 5종

| # | 검증 항목 | 기대값(원 장 커밋 실측) | 이 장 실측 | 판정 |
|---|---|---|---|---|
| 1 | 서빙 앱 동일성 | 10장 app.py sha256 `ec7ec653…` | 복사본 sha256 일치 | 일치 |
| 2 | 훈련 데이터 동일성 | 9장 피처 지문 `96f6b6b3…` | bootstrap 지문 일치 | 일치 |
| 3 | 집계 재구현 | 7장 확정치 3일(마포5·관악5·강남8 등) | 스트림 경로 집계 동일 | 3일 전부 일치 |
| 4 | 예측 동일성 | 9·10장 champion 예측 6.0 | 호출 9건 전부 6.0 | 일치 |
| 5 | 평가 동일성 | 9장 훈련 MAE 1.0 | 지연 채점 6건 전체 MAE 1.0 | 일치 |

○ 검증 3이 핵심: 7장은 배치(Airflow 파일 처리)로, 이 장은 스트림(Kafka 소비)으로 집계했는데 확정치가 같다
  - 처리 방식이 바뀌어도 업무 규칙(정제·멱등 키·집계 기준)이 같으면 결과가 같아야 한다
  - Lambda 아키텍처(3장)의 배치·스트림 불일치 문제를 검증 가능한 형태로 다룬 것

○ 검증 5: 채점된 예측 6건은 9장 훈련 쌍과 같은 데이터·같은 모델이므로 지연 MAE = 훈련 MAE = 1.0은 필연

#### 2-4. 피처 스토어 없이 피처 일관성이 유지되는 조건

○ 이 MVP에는 8장의 Feast가 없다
  - 확정 집계가 피처의 단일 진실 원천이고, `_SUCCESS` 마커가 "피처로 써도 된다"는 신호
  - 피처 1종(전일 건수), 소비자 1개(이 모델)일 때만 성립하는 축소
  - 피처가 수십 개, 소비 모델이 여럿이면 8장(피처 스토어)·13장(피처 거버넌스)이 필요

### 3. 정책 의사결정 지원과 정책 분석·평가 (10분)

#### 3-1. 예측의 소비자는 시스템이 아니라 사람이다

○ 공공 AI는 **정책 결정 시스템이 아니라 정책 의사결정 지원** — 예측은 판단의 입력이고, 판단과 집행은 사람이 한다

○ 경계 설계의 세 요소
  - **자동 집행 금지 지점**: 예측이 임계를 넘어도 시스템이 집행하지 않음 — 기록만 남김
  - **사람 개입 지점**: "왜 6건인가"에 대한 근거 — champion(v1)은 평균 예측기라서 "최근 평균"이 전부
  - **평가지표 주입**: 재학습 게이트(9장 1.05)와 감시 임계(11장)를 운영 조직 밖에서 정함(17장)

#### 3-2. 운영 로그가 정책 평가의 원자료가 된다

○ 매일 남기는 기록(예측·실제·절대 오차·일별 MAE)은 운영 감시 자료이자 정책 평가의 원자료
  - 운영의 언어: "감시 강화 신호" (단, 하루 표본 3건 — 소표본 주의)
  - 평가의 언어: "이 도구의 유효성을 어느 주기·어느 표본으로 재판정할 것인가"

○ **예측 오차의 평가 ≠ 정책효과 평가**
  - "민원 건수를 잘 맞혔다"와 "이 예측으로 행정이 개선되었다"는 다른 질문
  - 후자는 개입·비교집단·시차를 다루는 정책 분석 방법론이 필요
  - MLOps 지표를 정책효과 증거로 승격시키는 비약이 공공 AI 보고서의 흔한 오류

### 4. MVP 범위와 장애 시나리오 (15분)

#### 4-1. MVP 범위 표

○ MVP의 가치는 작음이 아니라 **경계의 명시** — 무엇을 뺐는지, 왜 뺐는지, 언제 다시 넣는지를 문서로 남겨야 한다

**표 14.5** 통합 MVP 포함/제외 범위표(주요 항목)

| 항목 | 판정 | 대체물 | 운영 승격 시 |
|---|---|---|---|
| 이벤트 버스(Kafka) | 포함 | 단일 브로커·단일 파티션 | 다중 파티션·복제 |
| 멱등 소비 | 포함 | complaint_id UPSERT | 동일 원칙, 저장소만 교체 |
| 일 마감·확정 | 포함 | day_close 제어 이벤트 | 스케줄러(Airflow)가 마감 발행 |
| 모델 서빙 | 포함 | champion 고정 이미지 1대 | 복수 인스턴스 + 무중단 교체 |
| 워크플로 스케줄러 | 제외 | 오케스트레이션 스크립트 | Airflow(실패 전파·재실행 이력) |
| 피처 스토어 | 제외 | 확정 집계 직접 계산 | 피처 다종·다소비자 시 Feast |
| 감시 시각화·알림 | 제외 | JSON 리포트·콘솔 | Prometheus·Grafana·on-call |
| 부하 대응·스케일링 | 제외 | 실측 없음(정직 표기) | 부하 테스트(12장)로 한계 실측 후 설계 |

#### 4-2. 장애 드릴 3종 — 카오스 엔지니어링의 공공 번역

○ **카오스 엔지니어링(chaos engineering)**: 분산 시스템에 의도적으로 장애를 주입하고 실험하는 규율
  - 넷플릭스의 Chaos Monkey가 대표 사례 — 프로덕션 인스턴스를 무작위로 종료해 복원력을 검증
  - 5원칙: ① 정상 상태 가설 ② 실세계 사건 주입 ③ 프로덕션 실험 ④ 자동화 ⑤ 폭발 반경 최소화

○ **공공 번역**: 민간의 "프로덕션 무작위" → 공공의 "계획된 드릴 + 감사 가능한 이력"
  - 프로덕션 대신 스테이징·드릴 환경에서 실행
  - 무작위 대신 계획된 시나리오로 실행
  - 드릴 이력을 기록으로 남김

○ **드릴 D1: 오염 이벤트**
  - 정상 이벤트 사이에 JSON 파싱 불가 1건 주입
  - 실측: 격리 큐(quarantine.jsonl)에 원문과 사유(json_parse_error) 보존, 파이프라인 지속, 집계 온전
  - 원칙: 나쁜 데이터는 버리지도, 통과시키지도 않는다. **분리해서 보존한다**(2장)

○ **드릴 D2: 중복 재전송**
  - 7/2 이벤트 18건 발행 후 마지막 10건을 한 번 더 발행(at-least-once 재현)
  - 실측: 물리 수신 28건 → 고유 17건(중복 흡수 11건) → 매핑 집계 16건(7장 확정치와 동일)
  - 수송 계층 중복(재전송 10건)과 업무 계층 중복(접수 1건)이 같은 멱등 키로 흡수됨
  - 회계 보존식: 물리 28 = 고유 17 + 흡수 11, 고유 17 = 매핑 16 + 미기재 0 + 미매핑 1

○ **드릴 D3: 의존 서비스 중단**
  - 7/3 마감 직전에 모델 API 컨테이너 정지 후 마감 진행

## 비즈니스 적용 노트

> 이 장의 기법이 민간 비즈니스에서 어떤 지표·목표·도구로 쓰이는지 정리한다.

### 공공 → 비즈니스 대응표

| 공공 맥락 | 비즈니스 맥락 | 차이점 |
|---|---|---|
| 민원 이벤트 실시간 수집 → 일별 확정 집계 → 익일 예측 | 이커머스 주문 수집 → 매출 집계 → 수요 예측, 핀테크 거래 → 이상 탐지 → 리스크 집계 | 공공은 행정 주기에 맞춘 일 단위 마감이 자연스럽다. 민간은 비즈니스에 따라 마감 주기가 다르다 — 결제 사기 탐지는 초 단위, 물류 재고는 시간 단위 |
| 중복 방지(멱등 소비 — complaint_id UPSERT) | 주문 ID·거래 ID 기반 멱등 처리 | 공공은 민원 건수 정확성이 목표다. 민간은 중복 과금·이중 출고가 직접 금전 손실이므로 사업적 긴급도가 높다 |
| 오염 이벤트 격리(격리 큐) | DLQ(Dead Letter Queue, 처리 실패 메시지 보존 큐)로 파싱 실패 메시지를 분리, 원인 분석 후 재처리 | 공공은 버린 이벤트가 감사 문제다. 민간은 버린 주문이 매출 손실이다 |
| 부분 실패 격리(모델 중단 시 집계는 확정, 예측만 대기) | 마이크로서비스 장애 격리 — 서킷 브레이커(circuit breaker, 장애 전파 차단 장치) 패턴 | 공공은 행정 산출물 보호가 우선이다. 민간은 핵심 수익 경로(결제·배송)와 부수 경로(추천·알림)를 분리한다 |
| 인수 검수표(실행 증거에서 자동 생성) | CI/CD E2E(End-to-End) 테스트 — 배포 전 자동 검증 스위트 | 공공은 계약 이행 증빙이다. 민간은 배포 안전성(production readiness) 게이트이며, 사람 승인 없이 자동 판정한다 |
| 장애 드릴(중복·오염·서비스 중단 시나리오) | 카오스 엔지니어링 — Gremlin, AWS Fault Injection Simulator, LitmusChaos 등 | 공공은 사전 검수 절차로 수행한다. 민간은 운영 중 정기 드릴로 수행하며, 자동화된 카오스 실험을 상시 실행한다 |
| 재조립 교차 검증(배치·스트림 경로의 확정치 일치) | 데이터 파이프라인 마이그레이션 시 원본-대상 수치 대조, 람다 아키텍처에서 배치 뷰와 스피드 뷰 일치 검증 | 공공은 값 일치를 감사 증빙으로 남긴다. 민간은 회귀 검증(regression testing)으로 불일치 시 배포를 자동 차단한다 |

### 비즈니스에서의 핵심 지표

○ **E2E 지연 시간** — 이벤트 발생부터 산출물 확정까지 걸리는 시간. SLA(Service Level Agreement, 서비스 수준 계약)로 관리한다

○ **중복 처리율** — 멱등 키로 흡수된 중복 이벤트의 비율. 갑자기 높아지면 상류 시스템의 재전송 로직에 문제가 있다는 신호다

○ **DLQ 체류 건수·시간** — 격리 큐에 머무는 메시지 수와 평균 체류 시간

○ **서비스 가용률과 MTTR(Mean Time To Recovery, 평균 복구 시간)** — 99.9% 가용률은 연간 8.7시간의 중단만 허용한다

○ **배포 성공률과 롤백 비율** — 검증 스위트를 통과해 배포된 비율과 배포 후 롤백이 필요했던 비율
