## 2. 이 장에서 실행할 것

□ 본보기로 쓰는 민원 통합 사례는 서울 3개 구의 민원 3일치(2026-07-01~07-03)를 처리함
  ○ 민원이 들어오고, 하루가 마감되면 구별 건수가 확정되며, 그 확정 건수로 다음 날 건수를 예측함
  ○ 다음 날 실제 건수가 확정되면 어제 만든 예측을 채점함
□ 처리 순서는 다음과 같음

1. 발행기(ingester)가 6주차의 민원 원천 파일을 하루치씩 Kafka 토픽에 발행함
2. 처리기(processor)가 이벤트를 하나씩 읽어 6주차 규칙으로 정제하고, 4주차 방식대로 `complaint_id`를 키로 저장함
3. 하루 마감 신호가 오면 처리기가 그날 집계를 확정하고 `_SUCCESS` 마커(marker) 파일을 남김
4. 처리기가 확정 건수를 모델 API(10주차 서빙 앱, 9주차 champion 모델)에 보내 다음 날 예측을 받음
5. 감시기(monitor)가 산출물을 읽어 통합 리포트와 인수 검수표를 계산함

□ 이 사례는 네 단계로 만들었고, 기말과제도 같은 네 단계로 만듦

| 단계 | 만드는 것 | 완성으로 판정하는 조건 | 절 |
| ---: | --- | --- | ---: |
| 1 | 앞 주차에서 옮겨 온 입력·규칙·모델 | 앞 주차가 남긴 값과 이번 실행의 값을 코드가 대조해 전부 일치함 | 3 |
| 2 | 일 마감 집계와 건수 회계 | 건수 등식 두 개가 날마다 성립함 | 4 |
| 3 | 고장 드릴(drill) | 고장을 넣은 날에도 마감이 확정되고, 고장 난 건이 사유와 함께 파일에 남음 | 5 |
| 4 | 검수표 | 모든 항목을 사람이 아니라 코드가 참·거짓으로 계산함 | 6 |

**표 14.2** 통합 사례를 만드는 네 단계와 단계별 완성 조건

□ 순서를 이렇게 정한 이유가 있음
  ○ 1단계가 통과하지 않으면 2단계의 집계가 틀렸을 때 원인이 옮겨 온 규칙인지 새로 쓴 코드인지 가릴 수 없음
  ○ 2단계의 건수 회계가 없으면 3단계에서 넣은 고장이 집계를 바꿨는지 확인할 기준이 없음
  ○ 4단계의 검수표는 1~3단계가 남긴 값을 읽어 계산하므로 마지막에 만듦

□ 실행하기 전에 네 가지를 먼저 적음
  ○ 산출물을 먼저 열면 거기 적힌 값을 정답으로 받아들이게 되어 "왜 이 값인가"를 묻지 않게 됨

## 3. 1단계 — 옮겨 온 것이 원본과 같은지 대조한다

□ 통합 사례의 구성요소는 새로 쓴 코드가 아니라 앞 주차에서 **복사해 온 파일과 규칙**임
  ○ 메시지 전달은 4주차의 Kafka이고, 중복 방지는 4주차의 `complaint_id` 업서트(UPSERT, 같은 키가 있으면 덮어쓰고 없으면 넣는 저장 방식)임
  ○ 정제·표준코드 매핑·`_SUCCESS` 마커는 6주차의 규칙임
  ○ 모델은 9주차가 승격한 champion이고, 서빙은 10주차의 `app.py`를 그대로 복사한 파일임
□ 복사한 파일은 이름이 같아도 내용이 다를 수 있음
  ○ 한 글자가 달라도 프로그램은 오류 없이 실행되므로, 눈으로 보아서는 차이를 찾지 못함
□ 그래서 1단계의 완성 조건은 "옮겼다"가 아니라 **앞 주차가 남긴 값과 대조해 일치했다**임
  ○ 대조는 사람이 하지 않고 코드가 두 파일을 열어 비교함

□ 첫 실습은 Kafka 없이 3일치를 다시 처리해 6주차 배치가 낸 확정치와 대조함

□ 화면에 나온 값에서 읽을 것

  ○ **서빙 앱은 바이트 단위로 같음** — `ec7ec653…`은 `practice/chapter10/code/10-1-model-api/app.py`와 이 장의 복사본에서 각각 계산한 값이 일치했다는 뜻임
  ○ **모든 예측이 6.0임** — 9주차 champion은 훈련 자료의 평균을 답하는 평균 예측기라서 입력이 달라도 같은 값을 냄
  ○ 키 이름의 `ch7`·`ch9`·`ch10`은 실습 코드가 붙여 둔 이름이며, 대조 대상 파일의 경로는 위에 적은 것과 같음

> - **해시는 그 실행 시점의 값이다.**
> - 10주차 `app.py`가 한 글자라도 바뀌면 `ec7ec653…`은 다른 값이 되고, 로그의 `일치`는 `불일치!`로 바뀐다.
> - 그래서 해시값을 문서에 적어 두고 믿는 것이 아니라 **실행할 때마다 다시 계산하도록** 코드에 넣어 둔다.

## 4. 2단계 — 건수가 어디로 갔는지 등식으로 남긴다

□ 메시지 전송은 대개 at-least-once(적어도 한 번 전달)로 설계됨
  ○ 보낸 쪽이 확인 응답을 받지 못하면 같은 메시지를 다시 보냄
  ○ 유실은 막지만 같은 메시지가 두 번 도착할 수 있음
□ 원천 자체에도 중복이 있음
  ○ 민원인이 같은 건을 두 번 접수하면 재전송이 아닌데도 같은 식별자가 두 번 들어옴
□ 두 중복은 원인이 다르지만 처리기에는 똑같이 도착함
  ○ 같은 `complaint_id`를 가진 이벤트가 한 번 더 오는 것임

□ 드릴 D2는 이 상황을 재현함
  ○ 7/2의 이벤트 18건을 발행한 뒤 마지막 10건을 한 번 더 발행했음
  ○ 3절의 실행에 이 드릴이 포함되어 있으므로 같은 로그의 7/2 줄을 다시 읽음

```text
# 출처: practice/chapter14/results/14-2-replay-accounting.log
[replay] 2026-07-02 마감: 물리수신 28 / 고유 17 (중복 흡수 11) → 매핑 16 · 미기재 0 · 미매핑 1 · 보존 True
  [PASS] 2026-07-02_정제회계가_6주차_배치와_일치
  [PASS] 2026-07-02_회계보존식_성립
```

```json
# 출처: practice/chapter6/data/output/daily/2026-07-02/quality.json
"physical": 18, "dup_removed": 1, "valid": 17,
"mapped": 16, "missing": 0, "unmapped": 1
```

□ 화면에 나온 값에서 읽을 것
  ○ **두 파일의 물리 수신이 다름** — 6주차 배치는 파일을 읽었으므로 18건이고, 이 장은 재전송 10건이 더 도착했으므로 28건임
  ○ **고유는 둘 다 17건임** — 6주차가 제거한 중복 1건은 원천 파일 안의 중복 접수이고, 이 장의 「중복 흡수 11」은 그 1건에 재전송 10건을 더한 값임
  ○ **매핑 16건이 변하지 않음** — 물리 수신이 10건 늘었는데 확정 집계는 6주차와 같음
  ○ **`보존 True`가 함께 출력됨** — 아래 두 등식이 성립했다는 표시임

□ 중복이 집계를 바꾸지 못한 이유는 4주차의 멱등(idempotent) 키에 있음
  ○ 멱등은 같은 입력을 여러 번 반영해도 결과가 한 번 반영한 것과 같다는 성질임
  ○ `complaint_id`를 키로 업서트하면 같은 식별자가 다시 와도 새 건으로 세지 않고 관찰 횟수만 올림
  ○ 재전송인지 중복 접수인지 가릴 필요가 없음 — 키가 같으면 둘 다 한 건으로 남음

### 회계 보존식

□ "집계가 변하지 않았다"만으로는 부족함
  ○ 중복이 들어왔다가 걸러진 것인지 처음부터 없었던 것인지 구분되지 않음
□ 그래서 마감마다 등식 두 개를 계산해 기록함
  ○ 물리 수신 = 고유 + 중복 흡수
  ○ 고유 = 매핑 + 미기재 + 미매핑
□ 7/2의 값을 넣으면 다음과 같음
  ○ 28 = 17 + 11
  ○ 17 = 16 + 0 + 1
□ 두 등식이 성립하면 들어온 건이 모두 어느 갈래에 속하는지 설명된 것임
  ○ 성립하지 않으면 어느 갈래에서 오류 메시지 없이 건수가 빠졌다는 뜻이므로 그날 마감을 믿지 않음

### 내 과제에서는

□ 내 데이터에서 **한 건을 가리키는 키**를 정함
  ○ 식별자 열이 있으면 그 열을 쓰고, 없으면 열 두세 개를 묶어 키로 삼음
  ○ 예: 1·2주차에 쓴 에어코리아 대기오염정보는 측정소 이름(`stationName`)과 측정 시각(`dataTime`)을 묶으면 한 건이 정해짐
□ 정제에서 건이 갈라지는 갈래를 정함
  ○ 민원 사례의 갈래는 매핑·미기재·미매핑 셋이었음
  ○ 대기질 자료라면 정상값·결측 표기·범위 밖 값으로 나눌 수 있음
□ 마감마다 두 등식을 출력하고, 성립 여부를 참·거짓으로 남김

  ○ 이 절의 값은 컨테이너로 완주한 실행이 남긴 산출물에서 옮겼음

### D1 — 읽을 수 없는 이벤트 1건

□ 7/3의 이벤트 사이에 JSON으로 읽히지 않는 문자열 1건을 끼워 발행했음

  ○ 처리기가 그 건에서 멈추지 않고 뒤의 이벤트를 계속 처리하는지를 확인하려는 것임
□ 처리기는 그 건을 격리 큐(quarantine queue) 파일에 원문과 사유를 함께 적고 다음 이벤트로 넘어갔음

□ 화면에 나온 값에서 읽을 것
  ○ **격리 뒤에 마감 줄이 나옴** — 읽을 수 없는 건 뒤의 이벤트가 계속 처리되어 그날 마감까지 끝났음
  ○ **매핑 20건이 3절의 값과 같음** — 격리된 1건은 집계와 다른 파일에 저장되어 확정치에 들어가지 않았음
  ○ **사유가 `json_parse_error`로 남음** — 사유가 기록되어 있어야 나중에 격리 건수를 사유별로 세고 원인을 찾을 수 있음

□ 격리 큐가 없으면 처리기가 할 수 있는 일은 둘뿐임
  ○ 그 건에서 멈추면 뒤의 정상 이벤트가 처리되지 않음
  ○ 그 건을 그대로 통과시키면 틀린 값이 집계에 들어감
□ 2주차의 원칙이 여기에 그대로 적용됨
  ○ **잘못된 데이터는 버리지도 통과시키지도 않고 따로 저장한다.**

### D3 — 모델 API가 멈춘 날의 마감

□ 7/3 마감 직전에 모델 API 컨테이너를 정지시키고 마감을 진행했음

[processor] 2026-07-03: _SUCCESS 확정

□ 화면에 나온 값에서 읽을 것
  ○ **모델 호출이 필요 없는 일은 끝났음** — 그날 집계 확정과 전날 예측의 채점은 모델 API가 멈춘 동안에도 완료되었음
  ○ **실패한 것은 예측 3건뿐임** — 구 3곳의 다음 날 예측만 `pending_retry` 상태로 남았고, 사유 `api_unreachable`이 함께 기록되었음
  ○ **`_SUCCESS`가 남았음** — 그날 집계는 확정본이므로 다음 날 처리가 이 값을 그대로 씀
  ○ **재시도 1회로 복구되었음** — `recovered_attempts`의 `[2]`는 3건이 모두 두 번째 시도에서 성공했다는 뜻이고, 복구 뒤 대기는 0건임

□ 이 설계를 **부분 실패 격리**라고 부름
  ○ 모델 API가 멈췄다고 그날 마감 전체를 실패로 처리하지 않음
  ○ 모델이 필요한 3건만 실패 상태로 기록하고 나머지는 확정함
□ 재시도가 중복 기록을 만들지 않은 이유는 예측 저장도 멱등이기 때문임
  ○ 예측 기록의 키가 (대상일, 지역)이므로 같은 예측을 다시 저장해도 한 건으로 남음
□ 드릴 세 개는 고장 난 건을 각각 다른 곳에 값으로 남김
  ○ 읽을 수 없는 이벤트는 격리 큐 파일에, 중복은 키별 관찰 횟수에, 모델 API 중단은 `pending_retry` 상태에 남음
  ○ 값으로 남아 있으므로 건수를 세고 검수표 항목으로 쓸 수 있음

## 6. 4단계 — 검수표를 코드로 계산한다

□ 검수표는 "이 시스템이 요구한 대로 동작했는가"를 항목별 참·거짓으로 적은 표임
□ 사람이 채우는 검수표는 두 가지가 문제임
  ○ 실행하지 않고도 "확인함"이라고 적을 수 있음
  ○ 코드를 고친 뒤 다시 확인했는지 알 수 없음
□ 그래서 이 사례는 16항목 전부를 감시기가 산출물에서 계산해 파일로 남김

```json
# 출처: practice/chapter14/data/output/ch14_acceptance_checklist.json
"04_회계_보존식_성립(물리=고유+중복,고유=매핑+미기재+미매핑)": true,
"05_중복_재전송_무해(물리28→매핑16_불변)": true,
"10_부분_실패_격리(중단_중_마감_확정+예측만_대기)": true,
"13_지연_MAE가_9장_훈련_MAE와_일치(1.0_손검산)": true,
"14_재조립_증명_서빙앱_바이트동일(10장_sha256)": true
```

□ 화면에 나온 값에서 읽을 것
  ○ **항목 이름에 판정 근거가 들어 있음** — 어떤 등식과 어떤 값으로 판정했는지가 이름에 적혀 있음
  ○ **값이 전부 계산된 참·거짓임** — 사람이 적어 넣는 칸이 없음
  ○ **3~5절의 결과가 항목으로 들어가 있음** — 04·05항은 4절의 회계, 10항은 5절의 D3, 14항은 3절의 해시 대조임
  ○ 항목 이름의 「9장」·「10장」은 실습 코드가 붙여 둔 이름이며 각각 9주차·10주차 실습을 가리킴

### 판정 기준을 정할 때 표본 수를 함께 본다

□ 검수 항목에는 기준값이 필요하고, 기준값은 앞 주차에서 가져오는 경우가 많음
□ 앞 주차의 기준값을 그대로 가져오면 맞지 않는 경우가 있음
  ○ 9주차의 승격 게이트는 평균 절대 오차(MAE) 1.05임
  ○ 이 사례의 지연 채점은 하루에 구 3곳, 곧 3건임
  ○ 3건으로 계산한 MAE를 1.05와 비교하면 다음 결과가 나옴

```text
# 출처: practice/chapter14/results/14-2-replay-accounting.log
[replay] 2026-07-02: 지연 레이블 도착 — 예측 3건 채점, 일 MAE 0.6667
[replay] 2026-07-03: 지연 레이블 도착 — 예측 3건 채점, 일 MAE 1.3333
  [PASS] 지연MAE가_통합실행과_일치
== 지연 평가: 일별 MAE {'2026-07-02': 0.6667, '2026-07-03': 1.3333}, 전체 1.0, 미채점 3건 ==
```

□ 화면에 나온 값에서 읽을 것
  ○ **하루치는 기준을 넘고 전체는 넘지 않음** — 7/3의 1.3333은 1.05보다 크지만 6건 전체의 MAE는 1.0임
  ○ **모델은 같은데 하루 사이에 0.6667과 1.3333이 나옴** — 표본이 3건이라 하루 값의 변동이 큼
  ○ **전체 1.0은 9주차 훈련 MAE와 같음** — 채점한 6건이 9주차 훈련 쌍과 같은 자료이고 모델도 같으므로 같은 값이 나와야 하며, 검수표 13항이 이 일치를 확인함
  ○ **미채점 3건이 함께 보고됨** — 7/4의 실제 건수가 아직 없으므로 7/4 예측 3건은 채점되지 않았음

□ 이 사례는 기준값 1.05를 바꾸지 않고 판정 단위를 바꿨음
  ○ 하루치 MAE가 기준을 넘으면 재학습을 결정하지 않고 감시를 강화하는 신호로만 씀
□ 같은 종류의 충돌이 하나 더 있음
  ○ 4주차는 처리량을 높이려고 파티션(partition)을 여러 개 두는 구성을 다뤘음
  ○ 6주차의 일 마감은 그날 이벤트가 모두 도착한 뒤에 마감 신호가 온다는 전제에서 동작함
  ○ 파티션이 여러 개면 도착 순서가 보장되지 않아 그 전제가 깨지므로, 이 사례는 파티션을 1개로 고정했음
□ 두 경우의 구조는 같음 — **한 주차에서 근거가 있던 값이 다른 주차의 전제를 깬다.**
  ○ 이 충돌은 실행 로그에 출력되지 않으므로, 가져온 값을 표 하나에 모아 사람이 서로 비교해야 찾을 수 있음

### 내 과제에서는

□ 검수표를 JSON 파일로 출력하고, 모든 항목의 값을 코드가 계산함
□ 항목 이름에 판정 근거(등식, 기준값, 대조 대상)를 적음
□ 모든 항목이 참일 때만 마지막 줄에 통과 표식을 출력함
  ○ 민원 사례의 `CH14_REPLAY_PASS`가 그 예임
□ 기준값을 쓴 항목에는 그 값을 몇 건으로 계산했는지를 함께 남김

## 7. 핵심 요약

□ **1. 통합 사례는 대조 → 회계 → 드릴 → 검수표 순서로 만든다.**
  ○ 앞 단계가 남긴 값이 뒤 단계의 판정 기준이 되므로 순서를 바꾸면 고장의 원인을 가릴 수 없음
  ○ 기말과제도 같은 네 단계로 만들고, 단계마다 완성 조건을 코드로 확인함(2절)

□ **2. 옮겨 온 구성요소는 앞 주차가 남긴 값과 대조해 같다는 것을 확인한다.**
  ○ 파일 전체를 읽은 6주차 배치와 이벤트를 하나씩 읽은 이 장의 재생이 3일치 확정치를 같게 냈고, 코드가 그 대조를 `[PASS]`로 출력했음
  ○ 서빙 앱은 sha256 해시로, 훈련 자료는 해시값 `96f6b6b3…`으로 앞 주차 기록과 일치를 확인했음(3절)

□ **3. 건수는 등식 두 개로 설명한다.**
  ○ 7/2에 물리 28건이 들어와 고유 17건, 매핑 16건으로 확정되었고 6주차 배치의 매핑 16건과 같았음
  ○ 28 = 17 + 11, 17 = 16 + 0 + 1이 성립했으므로 재전송 10건과 중복 접수 1건이 집계에 들어가지 않았다고 말할 수 있음(4절)

□ **4. 고장 난 건은 가장 작은 범위로 한정해 값으로 남긴다.**
  ○ 읽을 수 없는 이벤트 1건은 격리 큐 파일에 사유와 함께 남았고 그날 매핑 20건과 마감은 영향을 받지 않았음
  ○ 모델 API가 멈춘 7/3에도 집계는 확정되었고, 예측 3건만 `pending_retry`로 남았다가 두 번째 시도에서 대기 0건이 되었음(5절)

□ **5. 검수표는 코드가 계산하고, 기준값은 표본 수와 함께 정한다.**
  ○ 인수 검수표 16항목은 전부 산출물에서 계산한 참·거짓임
  ○ 하루 3건으로 계산한 MAE는 0.6667과 1.3333으로 달랐고 7/3은 기준 1.05를 넘었지만, 6건 전체는 1.0이었음(6절)

## 8. 기말과제

□ **과제** — 공공 데이터 하나를 골라, 3일치 이상을 하루 단위로 처리하는 통합 사례를 만들어 제출함
  ○ 이 과제는 기말고사를 대체함
  ○ Docker와 Kafka는 쓰지 않아도 됨 — 본보기인 `practice/chapter14/code/14-2-replay-accounting.py`는 Python 표준 라이브러리만 씀

□ 데이터는 다음 네 조건을 만족해야 함
  ○ 공공기관이 공개한 실제 자료이며 출처 주소를 적을 수 있음
  ○ 한 건을 가리키는 키를 정할 수 있음
  ○ 날짜나 시각 열이 있어 3일 이상으로 나눌 수 있음
  ○ 개인을 식별할 수 있는 정보가 들어 있지 않음
□ 지어낸 자료나 난수로 만든 자료는 쓰지 않음

**표 14.5** 기말과제가 갖춰야 할 여섯 요소

| 요소 | 최소 조건 | 본보기에서 볼 곳 |
|---|---|---|
| 입력 | 일자별 파일 3일치 이상, 출처 주소 기재 | `practice/chapter14/data/input/complaints/` |
| 정제와 멱등 반영 | 키를 명시하고, 같은 키가 다시 와도 집계가 변하지 않음 | 4절 |
| 일 마감과 회계 | 날마다 등식 두 개의 좌변·우변과 성립 여부를 출력 | 4절 |
| 예측과 지연 채점 | 확정치로 다음 날 값을 예측하고, 다음 날 확정치로 채점. 평균 예측기도 허용 | 6절 |
| 드릴 | 중복 재전송과 읽을 수 없는 레코드 두 종류. 위치·개수를 코드에 고정 | 5절 |
| 검수표 | 8항목 이상을 코드가 계산한 JSON 파일, 전 항목 통과 시 통과 표식 출력 | 6절 |

□ 제출물은 다섯 가지임

1. 실행 코드 — 한 번의 명령으로 처음부터 끝까지 실행되어야 함
2. 입력 자료와 출처 — 자료 파일(또는 받아 오는 코드)과 출처 주소, 받은 날짜
3. 실행 로그 — 본인 컴퓨터에서 실행한 화면 출력 전체를 저장한 파일
4. 검수표 JSON 파일
5. 보고서 — 아래 세 항목을 적음

□ 보고서에 적을 것
  ○ 고른 데이터, 키, 정제 갈래, 집계 단위를 각각 한 줄로 적고 그렇게 정한 이유를 적음
  ○ 본인 로그에서 드릴을 넣은 날의 두 등식을 숫자로 옮겨 적고, 드릴이 확정 집계를 바꾸지 못한 이유를 설명함
  ○ 검수표에서 기준값을 쓴 항목 하나를 골라, 그 값을 몇 건으로 계산했는지와 그 기준값이 다른 결정(마감 단위, 표본 수, 키)과 충돌하는지를 적음

□ 평가는 다음 다섯 가지를 봄
  ○ 제출한 코드를 다시 실행하면 제출한 검수표와 같은 결과가 나오는가
  ○ 두 등식이 날마다 성립하고, 그 값이 로그에 출력되는가
  ○ 드릴 두 종류가 들어 있고, 고장 난 건이 사유와 함께 파일에 남는가
  ○ 검수표의 모든 항목을 코드가 계산하는가
  ○ 보고서의 설명이 본인 로그의 값을 근거로 하는가
□ 집계 결과나 예측 정확도가 높고 낮음은 평가하지 않음

□ 이번 주 실습 제출물은 따로 있음
  ○ `python practice/chapter14/code/14-2-replay-accounting.py`를 실행해 만든 `practice/chapter14/data/output/ch14_replay_accounting.json`을 수업일 포함 7일 이내에 LMS에 업로드함
□ 기말과제는 15주차 수업일까지 LMS에 제출함
