### 1. Kafka 핵심 개념 (12분)

#### 1-1. 메시징 계층이 필요한 이유

○ **속도 차이 문제**
  - 생산 속도(민원 유입)와 소비 속도(처리 서버)는 거의 항상 다름
  - 재난 문자 발송 직후 → 민원 초당 수백 건 유입, 처리 서버는 따라가지 못함
  - 직접 연결하면 속도 차이가 곧 장애(요청 거부, 데이터 유실)

○ **Kafka의 해법: 추가 전용 로그(append-only log)**
  - 생산자는 이벤트를 로그에 붙이기만 하고, 소비자는 자기 속도로 읽음
  - 세 가지 능력:

| 능력 | 작동 방식 |
|---|---|
| 버퍼 | 소비가 밀려도 이벤트가 로그에 쌓여 버스트를 흡수 |
| 리플레이 | 읽어도 지워지지 않음 → 읽는 위치를 되돌려 과거 이벤트를 재처리 |
| 분리(decoupling) | 생산자는 소비자가 몇 개인지, 살아 있는지 알 필요 없음 → 감사용 적재기 등을 생산자 수정 없이 추가 |

#### 1-2. 이벤트 1건의 경로 — 핵심 개념 8가지

○ **토픽(topic)**: 이벤트가 들어가는 논리적 채널. 실습 토픽: `public.complaint.received.v1`

○ **파티션(partition)**: 토픽을 물리적으로 나눈 추가 전용 순서 로그. 실습은 파티션 3개

○ **키(key)와 파티셔닝**: 같은 키는 항상 같은 파티션으로 감(키 해시). 실습 키 = 지역구

○ **오프셋(offset)**: 파티션 안에서 이벤트가 받는 순번
  - **순서 보장은 파티션 안에서만 성립**
  - "강남구 민원끼리는 접수 순서 보존, 강남구와 관악구 사이 순서는 보장 안 됨"

○ **브로커(broker)**: 파티션을 저장·서빙하는 서버. 운영에서는 복제(replication)로 장애 대비. 실습은 1대

○ **컨슈머 그룹(consumer group)**: 같은 `group.id`를 가진 소비자들이 파티션을 나눠 맡음
  - 그룹이 다르면 같은 토픽을 독립적으로 읽음 → 처리용과 감사용 그룹이 서로 방해 안 함

○ **커밋된 오프셋(committed offset)**: "어디까지 읽었는지"를 브로커에 기록
  - 소비자가 죽었다 살아나면 이 기록부터 다시 읽음
  - **커밋 시점이 4.5절과 5장의 핵심 문제**

○ **보존 기간(retention)**: 소비 여부와 무관하게 설정된 기간 동안 이벤트 보존 → 리플레이 가능 범위

#### 1-3. 워크드 예제 — 이벤트 4건 경로(실측)

| 이벤트 | 키(지역구) | 배정 파티션 | 받은 오프셋 |
|---|---|---|---|
| #1 불법주차 | 중구 | 1 | 0 |
| #2 도로파손 | 강남구 | 1 | 1 |
| #3 도로파손 | 성동구 | 0 | 0 |
| #4 가로등고장 | 중구 | 1 | 2 |

○ 관찰 3가지
  - 오프셋은 파티션마다 따로 셈 — #3은 전체 세 번째지만 파티션 0에서는 오프셋 0
  - 같은 키(중구)는 같은 파티션(1)으로 감 → 순서(0→2) 보존
  - 중구와 강남구가 같은 파티션 1 공유 — 키가 달라도 해시가 같은 파티션을 가리킬 수 있음

**표 4.1** Kafka 핵심 개념 요약

| 개념 | 정의 | 운영 관찰 포인트 |
|---|---|---|
| 토픽 | 이벤트의 논리적 채널 | 명명 규칙, 스키마 계약 |
| 파티션 | 토픽을 나눈 순서 로그 | 개수(병렬성 상한), 부하 쏠림 |
| 키 | 파티션 배정 기준 | 같은 키→같은 파티션, 순서 보장 단위 |
| 오프셋 | 파티션 내 순번 | 커밋 위치, 컨슈머 랙 |
| 컨슈머 그룹 | 파티션을 나눠 맡는 소비자 집합 | 리밸런싱, 그룹별 진행 위치 |
| 보존 기간 | 이벤트 보존·리플레이 범위 | 감사 요구와의 정합 |

### 2. 토픽 명명과 파티션 키 설계 (10분)

#### 2-1. 토픽 명명 — 이름이 곧 거버넌스

○ **명명 예시 규칙** (표준이 아니라 합의의 예)
```
{도메인}.{데이터셋}.{이벤트}.{버전}
예: public.complaint.received.v1
```
  - 도메인/데이터셋: 소유 조직·데이터 종류 → 접근 권한·개인정보 등급을 토픽 단위로 묶는 기준
  - 이벤트: `received`, `updated`처럼 과거형 → 토픽이 상태 저장소가 아니라 사건 기록임을 명시
  - 버전: 호환 불가 스키마 변경 시 `v2` 토픽을 새로 만들어 신·구 소비자 공존

○ **데이터 계약(data contract)의 Kafka판**
  - 1장의 데이터 계약 — 생산자와 소비자가 필드·의미·변경 절차를 합의
  - 토픽 이름 = 계약의 표지, 스키마(버전) = 계약의 본문
  - 계약 없는 토픽 → 소비자가 필드를 오해해도 시스템은 죽지 않고 조용히 틀린 결과를 냄(침묵 실패)

#### 2-2. 파티션 키 — 순서 보장 단위의 선택

○ **키 선택은 업무 요구의 번역**

| 키 | 보장하는 것 | 적합한 용도 |
|---|---|---|
| 지역구 | 지역구별 접수·처리 순서 | 지역구 단위 집계·감사 |
| 민원 건 ID | 같은 민원의 상태 변화 순서 | 건 단위 이력 추적 |
| 없음 | 없음(부하는 고르게 분산) | 순서 불필요, 처리량 우선 |

○ **핫 파티션 — 키 편중의 대가**
  - 지역구 키가 평시에는 고르지만, 특정 지역구에 재난 → 그 구의 민원이 **전부 한 파티션에** 몰림
  - 가장 급한 순간에 한 파티션만 과부하, 나머지 파티션은 놀게 됨
  - 순서 보장 범위를 좁힐수록(세밀한 키) 부하가 고르게 퍼지지만, 넓은 범위 순서는 포기

○ **파티션 수 변경의 함정**
  - 파티션을 늘리면 키 해시→파티션 매핑이 바뀜 → 같은 키의 과거·현재 이벤트가 다른 파티션에 놓임
  - 초기 설계에서 파티션 수에 여유를 두는 이유

#### 2-3. 토픽 설계표(예시)

| 토픽 이름 | 파티션 키 | 순서 보장 단위 | 파티션 수 | 보존 | 설계 근거 |
|---|---|---|---|---|---|
| `public.complaint.received.v1` | 지역구 | 지역구별 접수 순서 | 3 | 7일 | 지역 단위 집계·감사, 재처리 여유 |
| `public.air.measured.v1` | 측정소 ID | 측정소별 시계열 순서 | 6 | 30일 | 월간 보고 재계산 |
| `public.disaster.alerted.v1` | 재난 유형 | 유형별 발령 순서 | 3 | 90일 | 사후 감사·재현 요구 |

### 3. Producer·Consumer 기본 동작 (15분)

#### 3-1. Producer 전송 경로

○ **4단계**: 직렬화(객체→바이트) → 파티셔닝(키 해시로 파티션 결정, Producer 쪽에서 계산) → 전송(배치로 묶어 비동기 전송) → 확인(acks)

○ **acks 설정 — "전송 성공"의 정의**

| 설정 | 의미 | 유실 위험 | 쓰임새 |
|---|---|---|---|
| `acks=0` | 확인을 기다리지 않음 | 브로커 장애 시 유실 | 손실 허용 메트릭 |
| `acks=1` | 리더 파티션 기록만 확인 | 리더 교체 직후 유실 가능 | 지연·안전 절충 |
| `acks=all` | 동기화된 복제본 전체 확인 | 가장 낮음 | 민원·재난 등 유실 불가 데이터 |

○ **공공 데이터 원칙**: 유실 불가 이벤트(민원, 재난)는 `acks=all`이 출발점

#### 3-2. 멱등 Producer(idempotent producer)

○ 문제: acks=all이어도, 브로커가 기록한 뒤 **확인 응답만 유실**되면 → Producer가 같은 메시지를 다시 보냄 → 중복
  - 안전 설정일수록 재시도가 적극적이라 중복이 더 잘 생김

○ 해법: `enable.idempotence=true` — Producer마다 고유 ID + 시퀀스 번호 → 브로커가 "이미 받은 시퀀스"를 알아보고 버림
  - KIP-679로 최신 Kafka 기본값이 됨(`enable.idempotence=true` + `acks=all`)

○ 한계: Producer 세션 하나의 재시도만 막음 — 앱 재시작 후 재전송, 소비 측 커밋 문제는 별개(4.5·5장)

#### 3-3. Producer 핵심 코드

```python
producer = KafkaProducer(bootstrap_servers=..., acks="all", ...)
future = producer.send(topic, key=event["district"], value=event)
meta = future.get(timeout=15)   # 브로커 확인 대기 → 파티션·오프셋 회신
```

#### 3-4. Producer 실행 결과(실측)

- 전송 200건, 소요 0.301초
- 파티션 분포: 파티션 0에 61건, 파티션 1에 76건, 파티션 2에 63건
- 8개 지역구 전부 단일 파티션에만 배정(`key_to_single_partition: true`)
- 분포(61/76/63)가 고르지 않음 → 키 해시는 지역구를 파티션에 나눌 뿐, 지역구별 이벤트 양을 균등하게 만들지 않음

#### 3-5. Consumer 동작 순환

○ **4단계 순환**: 그룹 참여(join) → 폴링(pull 방식) → 처리 → 커밋

○ **자동 커밋 vs 수동 커밋**
  - 자동 커밋(`enable.auto.commit=true`): 일정 주기로 백그라운드 커밋 → "처리 완료"와 무관한 시점에 커밋 → 유실·중복 모두 가능
  - 수동 커밋: 코드가 커밋 시점을 결정 → 4.5에서 시점을 바꿔 관찰

○ **컨슈머 랙(consumer lag)**
  - 계산: 파티션 마지막 오프셋 − 그룹이 커밋한 오프셋 = 아직 처리 못 한 이벤트 수
  - 고장이 터지기 전에 보이는 조기 경보 지표(SLI) — 11장에서 재등장

○ **하트비트·세션 타임아웃·리밸런싱**
  - 컨슈머가 죽으면 세션 타임아웃(실습 10초) 후 파티션을 다른 구성원에게 재할당
  - 크래시 직후 재시작한 컨슈머는 옛 자신이 타임아웃될 때까지 파티션을 못 받을 수 있음

#### 3-6. Consumer 핵심 코드

```python
consumer = KafkaConsumer(topic, group_id=..., enable_auto_commit=False,
                         auto_offset_reset="earliest", ...)
batch = consumer.poll(timeout_ms=1000)
consumer.commit()   # 커밋 시점은 코드가 결정
```

#### 3-7. Consumer 실행 결과(실측)

- 수신·처리 200건 — 유실 0, 중복 0
- 종단 지연: 평균 3.5ms, 최대 110.7ms
- 최대 110.7ms는 가장 첫 레코드에서 발생 — 첫 폴링의 파티션 할당·페치 준비 시동 비용

### 4. 실패와 재시도 — 전달 보증의 선택 (13분)

#### 4-1. 단계별 유실·중복·지연 발생 지점

**표 4.4**

| 단계 | 유실 | 중복 | 지연 |
|---|---|---|---|
| Producer→브로커 | `acks=0/1`에서 브로커 장애 | 확인 응답 유실 후 재시도 | 배치 대기, 과부하 |
| 브로커 | 복제 부족 상태의 디스크 장애 | — | — |
| 브로커→Consumer | **커밋 먼저, 처리 전 크래시** | **처리 먼저, 커밋 전 크래시** | 랙, 리밸런싱 |
| Consumer→저장소 | 저장 실패를 무시하고 커밋 | 저장 성공 후 커밋 실패 | 저장소 병목 |

#### 4-2. 커밋 시점이 전달 의미론(delivery semantics)을 결정

○ **at-most-once(최대 한 번)**: 커밋 먼저, 처리 나중
  - 처리 중 크래시 → 재시작 시 커밋 이후부터 읽음 → 처리 못 한 레코드는 다시 안 옴
  - **유실 가능, 중복 없음**

○ **at-least-once(최소 한 번)**: 처리 먼저, 커밋 나중
  - 커밋 전 크래시 → 재시작 시 옛 커밋 위치부터 다시 읽음 → 이미 처리한 레코드가 다시 옴
  - **유실 없음, 중복 가능**

○ **exactly-once(정확히 한 번)**: "전달"이 아니라 "반영"
  - 네트워크 위에서 물리적으로 "정확히 한 번 전달"은 근본적으로 어려움(ack 모호성)
  - Kafka의 exactly-once = "여러 번 전달되어도 정확히 한 번 반영된 것과 같은 결과"
  - 두 축: 멱등 Producer(재시도 중복 제거) + 트랜잭션(읽기-처리-쓰기-커밋을 원자 단위로)
  - 소비 종단(저장소)까지 협조가 필요하고 처리량 비용도 따름

○ **실무 기본값**: at-least-once + 하류에서 중복 제거(5장)

#### 4-3. 자동 커밋의 함정

- `enable_auto_commit=True`가 켜져 있으면, 자동 커밋이 내구 쓰기 전에 오프셋을 밀어 올릴 수 있음
- at-least-once를 의도했는데 코드가 조용히 **at-most-once로 강등** → 유실 발생, 오류 로그 없음
- 대응: 자동 커밋을 끄고, 내구 쓰기 완료 후 수동 커밋 → 재생 중복은 5장 멱등 설계로 흡수

#### 4-4. 유실과 중복의 비대칭

- **유실은 복구 불가능**, 중복은 교정 가능(중복 제거 키·Upsert)
- 이 비대칭이 공공 데이터에서 at-least-once가 기본값인 이유

#### 4-5. 민간 패턴의 공공 번역

**표 4.6**

| 민간 패턴 | 공공 대응물 | 전달 보증 | 공공 특수성 |
|---|---|---|---|
| 광고 노출·클릭 집계 | 민원 유입 실시간 현황판 | at-least-once + 하류 dedup | 집계가 인력 배치·예산 근거 → 중복 제거 증거까지 산출물로(7장) |
| 주문·결제 파이프라인 | 재난 문자·센서 이벤트 수집 | exactly-once(멱등 쓰기) | 유실은 인명 위험, 중복 경보는 신뢰 훼손 → 리플레이 보존 90일(표 4.2) |
| 실시간 추천 이벤트 | 방문·콜센터·온라인 채널 통합 | at-least-once + 멱등 키 | 같은 민원 다채널 중복 → `complaint_id` 멱등 키로 흡수 |

○ 공공에서 전달 보증은 **책임성의 결정**
  - "왜 이 보증 수준인가"가 검수 문서에 남아야 함
  - 유실·중복의 흔적이 실행 산출물로 증거화 → 감사·형평성 판단의 입력

#### 시나리오 3개

#### 실행 중 확인 체크리스트

- [ ] B·C 모두: 크래시 후 12초 대기 이유를 말할 수 있는가(세션 타임아웃)

|---|---|---|---|---|---|---|
| A. baseline | 200 | 200 | 200 | 0 | 0 | 지연 평균 3.5ms·최대 110.7ms |

#### 관찰 과제

○ **관찰 1**: 시나리오 B의 유실 20건 — 오류 로그가 남았는가?
  - 커밋 위치(30) 이후부터 읽으므로 아무것도 받지 못함 — 20건이 조용히 사라짐
  - 로그 없는 유실 → 운영에서 생산 건수와 처리 건수를 대사해야 탐지 가능

○ **관찰 2**: 시나리오 C의 중복 10건 — 버그인가?
  - at-least-once의 **정의대로의 동작**
  - 처리 기록 40 = 10(크래시 전) + 30(재시작 후 전체 재읽기), 고유 이벤트 30건, 유실 0
  - 이 중복을 어떻게 제거하는가가 5장의 주제

○ **관찰 3**: 크래시 후 재시작 지연
  - 죽은 옛 컨슈머가 세션 타임아웃(10초)으로 그룹에서 제외될 때까지 재할당이 미뤄짐
  - "장애 복구 시간"에는 프로세스 재기동 + 그룹 재할당 대기가 포함됨

## 비즈니스 적용 노트

> 이 장의 기법이 민간 비즈니스에서 어떤 지표·목표·도구로 쓰이는지 정리한다.

### 공공 → 비즈니스 대응표

| 공공 맥락 | 비즈니스 맥락 | 차이점 |
|---|---|---|
| 민원 이벤트 수집(토픽: `public.complaint.received.v1`) | 주문·결제·클릭 이벤트 수집(토픽: `ecommerce.order.created.v1` 등) | 토픽 명명 규칙의 구조는 같다. 도메인이 행정 단위에서 사업 단위(결제, 물류, 마케팅)로 바뀐다 |
| 파티션 키 = 지역구(지역별 순서 보장) | 파티션 키 = 고객 ID 또는 주문 ID | 공공은 행정 구역 단위 집계·감사가 핵심이고, 비즈니스는 고객 단위 순서 보장이 핵심이다 |
| 버스트(재난 신고 폭증) 대응 | 버스트(세일·플래시 세일 시작) 대응 | 부하 패턴은 같다. 비즈니스에서는 블랙프라이데이에 트래픽이 수십 배 폭증한다 |
| 전달 보증(at-most-once / at-least-once / exactly-once) | 동일한 전달 보증 선택 | 결제·과금은 반드시 at-least-once + 멱등 처리를 조합한다 |
| 감사용 컨슈머 그룹 | 분석용·ML 학습용 컨슈머 그룹 | 공공은 감사 재현이 목적이고, 비즈니스는 데이터 레이크 적재·BI(비즈니스 인텔리전스)·ML 학습이 목적이다 |
| 보존 기간을 감사 요구에서 역산 | 보존 기간을 비용·재처리 요구에서 역산 | 공공은 법적 보관 의무가 하한이고, 비즈니스는 비용과 리플레이 필요 기간의 균형으로 정한다 |

### 비즈니스에서의 핵심 지표

○ **Kafka 운영 지표**
  - 컨슈머 랙(consumer lag): 마지막 오프셋과 커밋 오프셋의 차이. 주문 처리 컨슈머 랙이 커지면 주문 확인 알림이 지연된다
  - 파티션별 처리량 편차: 핫 파티션이 발생하면 전체 처리량이 병목된다
  - 프로듀서 에러율: 전송 실패·타임아웃 비율. 브로커 과부하 또는 네트워크 문제의 신호다

○ **전달 보증 관련 지표**
  - 중복률: at-least-once 환경에서 중복 이벤트의 비율. 결제 시스템에서는 0.01% 미만을 목표로 잡는다
  - 유실률: 생산 건수와 소비 건수의 대사(reconciliation)로 측정한다. 오류 로그 없이 유실이 발생할 수 있으므로 건수 대사를 자동화해야 한다
  - 크래시 후 복구 시간: 세션 타임아웃 + 재할당 지연이 SLA의 일부가 된다

○ **비즈니스 영향 지표**
  - 주문-확인 지연: 주문 이벤트 발생부터 고객 알림 도달까지의 시간
  - 과금 정확도: 클릭 이벤트의 중복·유실이 과금액에 미치는 영향

### 실무 적용 사례

○ **이커머스 주문·결제 이벤트 스트리밍**
  - 주문 생성·결제 완료·배송 시작을 토픽으로 분리한다. 토픽 명명: `commerce.order.created.v1`, `commerce.payment.completed.v1`
  - 파티션 키를 주문 ID로 잡으면 같은 주문의 상태 변화 순서가 보존된다. 고객 ID로 잡으면 같은 고객의 주문들이 순서대로 처리된다
  - 플래시 세일 시작 시각의 주문 폭증은 재난 버스트와 같은 패턴이다. 특정 상품 ID 기반 키가 핫 파티션을 만든다

○ **실시간 클릭스트림 수집과 광고 과금**
  - acks=all + 멱등 Producer가 기본이다. 클릭 유실은 과소 청구, 중복은 과다 청구다
  - 컨슈머 그룹을 용도별로 분리한다: 실시간 대시보드용, 일별 정산 배치 적재용, ML 학습 적재용

○ **실시간 마케팅 이벤트 트리거**
  - 장바구니 이벤트의 시간 창 집계로 구매 미완료 사용자에게 쿠폰 알림을 보낸다
  - 커밋 시점 선택이 핵심이다. at-least-once(쿠폰 중복 발송 가능) vs at-most-once(쿠폰 미발송 가능). "두 번 보내는 것이 안 보내는 것보다 낫다"는 비즈니스 판단으로 at-least-once + 수신 측 중복 제거를 택하는 것이 일반적이다
