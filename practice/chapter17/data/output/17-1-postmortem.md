## INC-08-materialize-silent-empty — materialize_incremental 침묵 0건 적재
- **분류**: 실제 결함(코드) · **출처**: docs/chapter8.md:127, .ai/gotchas.md(Feast 0.64 materialize_incremental)
- **탐지 층**: 사용 지점(적재 성공 로그가 아님)
- **증상**: 온라인 조회가 에러 없이 None을 반환
- **영향**: 온라인 스토어가 빈 채로 서빙될 위험 — 사용 지점에서 TypeError로 발현
- **타임라인**:
  1. 적재를 materialize_incremental(기본 시작점 now−TTL)로 호출
  2. 실습 피처 타임스탬프가 그 창보다 과거라 0건 적재(에러 없음)
  3. 온라인 조회가 조용히 None 반환
  4. 값 사용 지점에서 TypeError로 뒤늦게 발현
- **근본 원인(3-why)**:
  - 왜 온라인이 비었나 — 적재 건수가 0이었다
  - 왜 0건인가 — materialize_incremental 기본 시작점이 now−TTL이라 과거 피처가 창 밖
  - 왜 몰랐나 — 적재 성공 로그만 확인하고 적재 건수를 확인하지 않음
  - **근본 원인**: 쓰기 성공 로그 ≠ 적재 완료. 적재 범위를 명시하지 않음.
- **조치**: materialize(start_date, end_date)로 범위 명시 + 적재 건수·온라인=오프라인 일관성 대조를 서빙 전에 자동화
- **재발 방지**: 적재 후 건수 확인 게이트 + 온라인·오프라인 일관성 대조(표 8.2)

## INC-09-runs-uri-load-fail — runs:/ 문자열 등록 후 별칭 로드 실패
- **분류**: 실제 결함(코드) · **출처**: docs/chapter9.md:179, .ai/gotchas.md(MLflow 3 모델 등록)
- **탐지 층**: 로드(읽기) — 등록(쓰기)은 성공 로그를 남김
- **증상**: 별칭 로드 시 'Could not find an MLmodel configuration file' 예외
- **영향**: 등록은 되었으나 배포 후보를 로드할 수 없음 — 서빙 불가
- **타임라인**:
  1. 버전 source를 runs:/<run_id>/model 문자열로 조립해 등록
  2. 등록까지 에러 없음(쓰기 성공)
  3. champion 별칭으로 로드하는 순간 MLmodel not found 예외
  4. 오류가 난 곳(로드)과 원인이 있는 곳(등록 경로)이 다름
- **근본 원인(3-why)**:
  - 왜 로드가 실패했나 — MLmodel 설정 파일 경로가 없음
  - 왜 경로가 없나 — MLflow 3의 저장 위치가 관례 경로 runs:/…와 다름
  - 왜 등록은 성공했나 — 등록(쓰기)이 경로의 로드 가능성을 검증하지 않음
  - **근본 원인**: 관례 경로 문자열을 손으로 조립. 쓰기 성공 로그를 신뢰.
- **조치**: log_model이 돌려주는 정본 참조 model_info.model_uri를 등록에 사용 + 등록 직후 별칭 로드·예측까지를 등록 검증으로
- **재발 방지**: 등록 직후 로드·예측 스모크(시나리오 4 통과가 PASS 조건)

## INC-10-container-path-indexerror — 컨테이너 경로 계산 import 즉사(IndexError)
- **분류**: 실제 결함(코드) · **출처**: docs/chapter10.md:188, .ai/gotchas.md(컨테이너와 모듈 레벨 경로 계산)
- **탐지 층**: 컨테이너 스모크(pytest·호스트 실행은 통과)
- **증상**: 컨테이너 /health 무응답 — import 시점 IndexError로 프로세스 즉사
- **영향**: 모든 사전 게이트를 통과한 이미지가 배포 직전 층에서 기동 실패
- **타임라인**:
  1. 설정 기본값을 파일 위치 기준 상위 디렉터리(parents[1])로 모듈 레벨에서 계산
  2. pytest 통과 — 저장소 배치 위에서 실행
  3. 호스트 uvicorn 통과 — 역시 저장소 배치 위
  4. 컨테이너에서 앱이 /app/app.py에 놓여 parents[1]가 없음 → import 시 IndexError
  5. --rm(자동 삭제)로 띄워 크래시 로그까지 삭제 → 진단 지연(90초 타임아웃 소진)
- **근본 원인(3-why)**:
  - 왜 컨테이너가 죽었나 — import 시점 IndexError
  - 왜 IndexError인가 — /app 얕은 배치에서 parents[1]가 존재하지 않음(저장소 깊이를 가정)
  - 왜 사전 게이트가 통과했나 — pytest·호스트는 저장소 배치 위라 그 가정이 항상 참이었음
  - **근본 원인**: 모듈 레벨 경로 계산이 저장소 깊이를 가정. --rm이 실패의 잔해(로그)를 삭제.
- **조치**: len(parents) >= N 가드로 안전화 + 진단 기동은 --rm 없이 명시적 정리 + 감시 루프가 타임아웃만 기다리지 말고 프로세스 생존을 함께 확인
- **재발 방지**: 컨테이너 스모크 독립 게이트 + 환경 동등성(호스트=컨테이너 예측) 실측

## INC-12-single-worker-saturation — 단일 워커 한 코어 포화로 처리량 천장
- **분류**: 용량 한계 · **출처**: practice/chapter12/data/output/ch12_load_report.json
- **탐지 층**: 부하 테스트(Locust 5시나리오)
- **증상**: 사용자 20→100 증가에도 처리량은 천장(≈2500–2800 RPS)에 머물고 지연만 증가
- **영향**: 단일 프로세스가 한 코어를 포화(CPU peak 106.3%)시켜 세로 확장 없이는 더 못 받음 — 단, 부하 중 정확성 유지(failures 0)
- **타임라인**:
  1. baseline(사용자 20): 2498.3 RPS, p99 18.0ms, CPU peak 106.3%
  2. spike(사용자 100): 2788.5 RPS, p99 66.0ms — 처리량 천장, 지연만 상승
  3. scale(워커 2): 3153.0 RPS(baseline 대비 1.26배), RSS 610.1MB
  4. io(shadow on): 1702.8 RPS(baseline 대비 0.68배) — 요청당 I/O 비용
- **근본 원인(3-why)**:
  - 왜 처리량이 안 오르나 — 단일 워커가 한 코어를 포화시킴
  - 왜 포화인가 — 프로세스 1개가 CPU 106.3%(한 코어 상한 근처)를 쓴다
  - 왜 사용자를 늘려도 같나 — 서비스율이 천장이라 대기만 늘어 지연으로 나타남(Little's law)
  - **근본 원인**: 단일 워커·단일 코어 서비스율 상한. 부하는 용량을 늘리지 않고 대기를 늘린다.
- **조치**: 워커 수평 증설(1→2로 처리량 1.26배 실측) 또는 인스턴스 수평 확장 — 용량 계획의 기준선을 실측 천장으로
- **재발 방지**: 배포 전 부하 프로파일로 처리량 천장·knee 지점 측정, 자동 스케일 임계 설정

## INC-15-openai-billing-429 — OpenAI 생성 전건 429(billing_not_active) — 인증 게이트≠결제 게이트
- **분류**: 벤더 장애 · **출처**: practice/chapter15/data/output/ch15_llm_snapshot.json
- **탐지 층**: 생성 엔드포인트(chat/completions) — 인증 엔드포인트가 아님
- **증상**: 인증(/v1/models)은 통과하나 생성(chat/completions) 8건 전건 실패(HTTP 429 billing_not_active)
- **영향**: gpt-4o-mini 생성 0/8 — 그러나 HCX-DASH-002가 8/8 응답해 서비스 지속
- **타임라인**:
  1. 동일한 결정적 코어(프롬프트 v2·근거 조문)를 두 제공자에 투입
  2. OpenAI: 인증은 통과, 생성은 8건 전건 HTTP 429 billing_not_active
  3. CLOVA: 8건 정상 응답 → 서비스 완주
- **근본 원인(3-why)**:
  - 왜 생성이 실패했나 — 계정 결제가 비활성(billing_not_active)이라 429
  - 왜 인증은 통과했나 — /v1/models(인증 게이트)와 chat/completions(결제 게이트)가 별개
  - 왜 서비스는 지속됐나 — 코어가 제공자 독립이라 한 벤더가 막혀도 다른 벤더로 완주
  - **근본 원인**: 인증 게이트 통과를 '사용 가능'으로 오판. 단일 벤더 종속 위험.
- **조치**: 키 유효성은 반드시 생성 엔드포인트 1콜로 확인 + 제공자 독립 코어로 멀티벤더 대체
- **재발 방지**: 생성 엔드포인트 헬스체크 + 멀티벤더 폴백
